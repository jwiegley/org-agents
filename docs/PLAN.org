## Context

"Is this heading an agent?" is spelled three different ways in `org-agents.el`,
each reading `AGENT_QUERY` from the entry at point:

- `org-agents--dblock-agent` — `(save-excursion (and (not
  (org-before-first-heading-p)) (progn (org-back-to-heading t)
  (org-agents--entry-get "AGENT_QUERY")) (org-agents--read-agent)))`;
- `org-agents--agent-marker` — the same shape, answering with a marker;
- `org-agents--buffer-agents` — `(when (org-agents--entry-get "AGENT_QUERY") …)`
  at each heading of a scan.

They agree today.  The reason to unify them is that they are the definition of
what this package acts on, and the definition is subtle: the drawer must be the
entry's **own** (no inheritance), and the property name appearing in body text
must not count — a rule the buffer scan's own docstring explains at length.  A
fourth caller written from the nearest example is how that rule gets lost.

## Evidence

- `org-agents.el`: `org-agents--dblock-agent`, `org-agents--agent-marker`,
  `org-agents--buffer-agents`, and `org-agents--read-agent`'s own
  `(unless q (user-error "No :AGENT_QUERY: at point"))`.
- `org-agents--entry-get` is already the single reader that pins the
  no-inheritance rule; the missing piece is a single *predicate* above it.

## What to do

- One helper — `org-agents--agent-at-point-p`, or let `org-agents--agent-marker`
  be it — carrying the rule and its docstring.
- The three call sites use it.  `--buffer-agents` keeps its own match-data
  ordering comment: reading the heading position **before** the property lookup is
  load-bearing (`org-entry-get` clobbers the match data), and that has already
  been a bug once.

## Acceptance Criteria

- [ ] exactly one place in the file decides whether an entry is an agent
- [ ] the existing tests pass unchanged, including the buffer-scan tests that
      pin marker positions
- [ ] the match-data ordering comment survives the refactor

## Context

`org-agents--scope-files` builds the skeleton and spawns the CLI *before*
anything looks at whether the scope is usable.  A malformed scope — a number, a
list holding a non-string — is diagnosed only later, by
`org-agents--scope-base-files`, which is reached after the round trip.

So a mistyped `:AGENT_SCOPE:` costs a subprocess and a database query before it
produces the message that was always going to be the answer.  Correctness is
unaffected; it is the diagnostics-first principle the rest of the package follows
("a value that cannot be used is diagnosed here rather than left to fail") not
being followed here.

Note the deliberate ordering that must survive any fix: the scope's **base files**
are gathered only where they will be used, because for an unbounded scope
gathering them is the very recursive walk the prefilter exists to avoid.  Checking
the scope's *shape* is not the same as gathering its files, so both properties can
hold at once.

## Evidence

- `org-agents.el` — `org-agents--scope-files`: the `skeleton`/`candidates`
  `let*` runs first, with its comment about deferring the base-file walk; the
  `(_ (user-error "org-agents: bad scope %S" scope))` arm lives in
  `org-agents--scope-base-files`.
- `org-agents--read-scope` reads the property, but a scope can also arrive as an
  inline dblock `:scope` parameter, which is where a bad shape survives longest.

## What to do

- Give the scope shape one validator, called before the skeleton is built:
  a member of `org-agents--scope-names`' symbols, a string, or a list of strings.
- Do not gather any files in it.

## Acceptance Criteria

- [ ] a malformed scope raises its `user-error` with no CLI invocation, proven by
      a test that stubs `call-process` to fail if called
- [ ] the base-file walk is still deferred for unbounded scopes (the existing test
      pinning that stays green)
- [ ] the message still names the bad scope

## Context

`org-db-cli-files-directory` is a user option that does nothing, and whose
docstring describes a convention the CLI does not use.

It says: "Directory against which relative `file` fields resolve.  When nil,
`org-directory` is used."  But the CLI's `file` field is **absolute and
canonicalized** — the store records `canonicalizePath` of each file it reads — so
the `(expand-file-name f base)` it feeds is a no-op on every real answer.  The
same file's own docstring for `org-db-cli-query-files`, twenty lines below, states
the absolute-path convention correctly.

So a user who sets this option gets no error, no warning, and no effect.  That is
worse than not having it: the package's stated principle everywhere else is that a
value that cannot be used is diagnosed rather than left to quietly do nothing.

## Steps to Reproduce

1. Set `org-db-cli-files-directory` to any directory other than `org-directory`.
2. Run a query that returns files (or call `org-db-cli-query-files` with a
   skeleton).
3. The returned paths are unchanged: they were already absolute, so
   `expand-file-name` ignores the base entirely.

## Evidence

- `org-db-cli.el` — the `org-db-cli-files-directory` defcustom and its docstring;
  `org-db-cli-query-files`'s `(base (or org-db-cli-files-directory
  org-directory))` and `(expand-file-name f base)`.
- `org-db-cli-query-files`'s own docstring: "The `file` field the CLI writes is
  already absolute and canonicalized … so what comes back names a file by its
  truename".
- Ledger Ruling 17 in
  `/Users/johnw/src/dot-emacs/.superpowers/sdd/2026-08-18-org-agents/progress.md`,
  which established the absolute-path fact and notes "org-db-cli already passes
  absolute through unchanged (expand-file-name no-op)".

## What to do

Prefer removing it.  It was written against a plan that expected relative paths;
the CLI does not emit them and there is no other consumer.  Keep
`expand-file-name` as the defensive no-op it is, or drop it too — but if the
option stays, its docstring must say it only applies to a hypothetical relative
answer, which is not a thing the CLI produces.

## Acceptance Criteria

- [ ] `org-db-cli-files-directory` is gone, or its docstring is true
- [ ] `org-db-cli-test.el` covers whatever the decision is (a relative-path row is
      the case worth pinning if the option survives)
- [ ] no other file references it (nothing does today)

## Context

`org-agents-test-gate-refuses-bare-call`'s docstring says "An unapproved arbitrary
call is never evaluated, even inside (and ...)" — but its only assertion is
`(should-not (org-agents--gate '(and (todo) (shell-command "touch /tmp/pwned"))))`.
That establishes the gate answered nil.  It does not establish that nothing was
evaluated.

The distinction matters here more than anywhere else in the suite: this is the
package's security boundary, and the spec's Verification section cites this test
by name for exactly the claim the assertions do not make.  A future refactor that
evaluated a form on the way to refusing it would leave this test green.

The precedent for fixing it is in the same project: the honesty audit found the
DST test asserting its expectation with the same function it was testing, and the
fix was to assert a literal instead.  A test whose docstring promises more than it
checks is the same failure in a different dress.

## Evidence

- `org-agents-test.el` — `org-agents-test-gate-refuses-bare-call`, docstring and
  its single `should-not`.
- Spec `docs/superpowers/specs/2026-08-18-org-agents-design.md`, Verification:
  "gate: `org-agents-test-gate-refuses-bare-call` — an unapproved `(and (todo)
  (shell-command "x"))` is never evaluated".
- The final review's own probing did establish the boundary empirically under
  fourteen attempts — so the property is true; it is this test that does not check
  it.

## What to do

- Assert the effect did not happen: bind `shell-command` (via `cl-letf`) to signal
  if called, and keep the `should-not`.  Then the test fails both if the gate
  approves and if anything evaluates the form.
- Do not use a real `/tmp` side effect; the suite writes nothing outside its own
  temporary directories.
- While there, check the neighbouring gate tests for the same gap.

## Acceptance Criteria

- [ ] the test fails if the refused form is evaluated, proven by mutation (make

- [ ] the docstring matches what the assertions establish
- [ ] no other test in the file promises "is never evaluated" without asserting it

machinery" that had been proposed alongside it.  The important part of that
ruling is the second half: the package already has a sound trust boundary in
`org-agents--gate`, and an action must go through it rather than growing a second
one.  The gate was attacked fourteen ways by the final review (quoted call
forms, dotted lists, lambda-headed cons cells, vectors, records, byte-code
objects in function position) and held, so there is a boundary to reuse.

## Evidence

- Spec `docs/superpowers/specs/2026-08-18-org-agents-design.md`, "Scope of
  Version 1": "Deferred … `AGENT_ACTION` (Tinderbox `$AgentAction`) behind the

- Design review `docs/superpowers/specs/2026-08-18-org-agents-design-review.md`,
  feature cuts item 10.
- `org-agents.el`, `org-agents--gate` — the existing choke point, and
  `org-agents--structurally-safe-p` beside it.

## What to do

- Read `:AGENT_ACTION:` with the same `org-agents--read-sexp` treatment every

## Problem

`org-agents--scope-files` (org-agents.el:966-995) consults the bridge whenever
the query has a pushable conjunct, with no test on the scope and no test on how
many files the scope names:

```elisp
(candidates (and skeleton (org-db-cli-available-p) (org-db-cli-query-files skeleton)))
```

`org-db-cli--run` (org-db-cli.el:67-101) is a synchronous `call-process` with no
timeout. So for an `agenda`-scope agent naming 8 files, org-agents pays a
subprocess spawn plus a round trip to a possibly-remote PostgreSQL in order to
narrow *8 files* — and if the host is unreachable, Emacs blocks until TCP gives
up, with no bound.

Measured 2026-08-19: a live agenda-scope update over those 8 files (2.4 MB,
`todo.org` alone 1.3 MB / 373 matches) costs **0.018s** when the dirtied buffer
is re-scanned and the rest are org-ql cache hits. Narrowing that is not worth a
network round trip on its best day.

`org-agents-mode` already binds the bridge away for the save path specifically,
because a save must never block on a network. That fixes the acute case and
leaves the general one.

## Proposal

Consult the prefilter only when it can plausibly pay for itself:

- always for a scope in `org-agents--corpus-scopes` or a directory (they have no
  bound, and this is the case the prefilter exists for);
- for a named-file scope, only when the file count exceeds a defcustom threshold
  (some tens of files — the crossover is where a spawn plus a round trip beats
  opening that many buffers; measure before fixing the default);
- never when the base file set is already in memory as up-to-date buffers, since
  org-ql will take cache hits on all of them.

Independently: give `org-db-cli--run` a timeout so no code path can block Emacs
without bound. `call-process` has no timeout argument, so this means either an
asynchronous process with a timer, or a `timeout(1)`-style wrapper. The former
is the honest fix and is a larger change; the latter is one prefix argument and
covers the realistic failure.

## Acceptance Criteria

- An agenda-scope agent with a pushable conjunct spawns no subprocess (a test

- A corpus-scope agent still uses the prefilter.
- No org-agents code path can block Emacs indefinitely on an unreachable
  database host; a test covers the timeout with a deliberately hanging stub.

Add a ripgrep prefilter backend so corpus scopes need no database.

Measured on 2026-08-19 against the real corpus (~/org, 3,634 non-archive .org
files, 33 MB). Full log: prefilter-alternatives.md in the SDD workspace.

## Why

The database is only a candidate-file narrower — evaluation is org-ql and always
was. But today it is the *only* narrower, so the three unbounded scopes
(`active`, `all`, a directory) hard-error without a reachable PostgreSQL. Live
evaluation is not a real fallback: no prefilter at all costs 45.98s, 885 MB peak
RSS, and 3,640 open buffers for one query.

ripgrep does the same narrowing from the live files:

| path | files opened | wall clock | result |
|---|---|---|---|
| no prefilter | 3,634 | 45.98s | 764 matches |
| rg prefilter + org-ql | 309 | 3.90s (rg 0.13s) | 764 matches |

Same 764 matches from 309 files as from 3,634 — an empirical superset check on
real data, which the database path has never had (its 20 differential tests
still cannot run for want of a reachable DB).

## Two correctness advantages over the DB, not just setup

1. No staleness window. README §"The database prefilter" concedes a file that
,   *newly* satisfies a pushed conjunct since the last `org db sync` is missed
   until the next sync — a false negative. rg reads live bytes.
2. No second parser to diverge. Honest-limitation #2 (`:PROP+:` continuation
   line makes org-jw discard the whole drawer) cannot arise when the prefilter
   matches the same bytes org-ql reads.

## Shape of the work

`org-agents--pushdown-fns` is already backend-agnostic — it emits abstract
superset-safe conjuncts, and only the closing `prin1-to-string` in
`org-agents--skeleton` is CLI-specific. So:

- Change `--skeleton` to return the conjunct sexp; let each backend serialize.
  The CLI bridge keeps its `prin1`.
- New backend emits one rg pattern per conjunct, intersecting per-conjunct file
  sets for `and` and unioning for `or`:
  `(property NAME)` → `^[ \t]*:NAME:`;
  `(property NAME VAL)` → same plus `regexp-quote`d value;
  `(scheduled/deadline/closed …)` → stamp existence only;
  `(heading "lit")` → `^\*+ .*lit`; `(path DIR)` → rg `--glob`.
- A defcustom choosing the backend, defaulting to rg when `rg` is on PATH.

rg cannot compare dates, so planning conjuncts push as bare stamp existence.
Measurement retires that worry: `SCHEDULED:` occurs in 186 of 3,633 files and
`DEADLINE:` in 46 — 95–99% narrowing from existence alone.
