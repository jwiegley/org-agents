#+title: A worked attribute registry
#+startup: showeverything

This is a whole =org-agents= attribute registry, written out so that the
format can be read rather than inferred. It is *documentation*: nothing
reads this file at runtime. Point =org-agents-attributes-file= at your own
copy — the default is =~/org/attributes.org= — which the package will never
create for you and never assumes exists.

Two rules before the entries, because both are easy to get wrong once and
then wonder about for an afternoon.

*The drawer goes immediately under the heading.* Org keeps a property
drawer there and =org-get-property-block= looks nowhere else, so a drawer
written after the body text is not a property drawer at all. The reader
diagnoses such an entry as declaring no =ATTR_TYPE=, which is exactly what
it looks like from Org's side.

*Members are separated by whitespace, not by semicolons.* Tinderbox
separates the members of a set or a list with semicolons; here the
separator is whitespace, because that is what Org's own =NAME_ALL=
convention uses and therefore what =org-property-get-allowed-values=
already reads.

* OPEN
:PROPERTIES:
:ATTR_TYPE:    boolean
:ATTR_DEFAULT: false
:END:
Whether this item is still open for comment.

A =boolean= admits =true= and =false=, unquoted and lower case, and nothing
else — not =t=, not =yes=, not =True=. Those two values are in no drawer here:
the reader synthesizes them onto every boolean declaration, which is why
completion needs no special case for the type and why the linter's
vocabulary check and its type check are one check.

* REVIEWS
:PROPERTIES:
:ATTR_TYPE:    number
:ATTR_DEFAULT: 0
:END:
How many times this entry has been through review.

A signed integer or decimal, with no exponent: =3=, =3.5=, =.5=, =-3=. The
whole value must be one number, which is what catches an accumulated
property — a =:REVIEWS: 3= beside a =:REVIEWS+: 4= reads back as the text
=3 4=, and that is not a number.

=number= is also the one type =org-agents-attribute-columns= gives a summary
operator, =+=.

* STATUS
:PROPERTIES:
:ATTR_TYPE:    set
:ATTR_VALUES:  open wip blocked done
:ATTR_DEFAULT: open
:ATTR_FACES:   blocked org-warning | done org-done
:END:
Where the item stands. A =set= rather than a =string=: an item may be
blocked and waiting on review at once, and a set is unordered and admits
no repeat.

=ATTR_FACES= is parsed and stored and read by nothing today. It is here
because the format is cheaper to fix now than to change later.

* OWNER
:PROPERTIES:
:ATTR_TYPE:    string
:ATTR_VALUES:  johnw alice bob :ETC
:END:
Who is carrying this.

The trailing =:ETC= is Org's own marker for "these are defaults, other
values should be allowed too". It does two things: =org-set-property=
offers the three names but accepts a fourth, and the linter stops
reporting a name outside the list — which is the honest reading, since
the declaration itself says the vocabulary is open.

* TOPICS
:PROPERTIES:
:ATTR_TYPE:   list
:ATTR_VALUES: emacs org lisp nix
:END:
What this is about.

A =list= is ordered and admits duplicates, where a =set= is neither.
Completion offers the members one at a time, which is what completing one
member of a whitespace-separated value needs.

* DUE
:PROPERTIES:
:ATTR_TYPE:    date
:ATTR_DEFAULT: [2026-12-31 Thu]
:END:
When this is wanted by.

A =date= must both parse and name a day that exists. =[2026-12-31 Thu]=,
=<2026-12-31 Thu 10:00>= and the plain =2026-12-31= are all accepted;
=[2026-13-45 Xyz]= and =[2026-02-30 Mon]= are not, and it takes a round trip
through =encode-time= to tell — =org-parse-time-string= reads both of them
without complaint.

* Prototypes
This heading is reserved and declares nothing. It is skipped silently,
where any other top-level entry with no =ATTR_TYPE= is named as malformed.
Every entry BELOW it, at any depth, is a prototype: an ordinary entry whose
drawer holds ordinary properties, which any entry in the corpus may read
through by naming it in =:PROTOTYPE:=.

Nothing is ever written into the entry that reads through one. Change a
master here and every follower changes with it — and grep does not see the
inherited value, while an agent through =property-resolved= does.

** Task
:PROPERTIES:
:STATUS:  open
:OWNER:   johnw
:REVIEWS: 0
:END:
The master every task follows. Its three properties are the three declared
above, so a follower's =STATUS= completes from =ATTR_VALUES= and lints
against =ATTR_TYPE= exactly as a local one does.

Note what is NOT here: no =AGENT_QUERY=, and it would do nothing if it
were. Behaviour does not travel — a master that lent its query would make
every follower an agent — so no =AGENT_= name resolves through a prototype,
and neither does =PROTOTYPE= itself.

** Urgent Task
:PROPERTIES:
:PROTOTYPE: Task
:STATUS:    wip
:END:
A master may itself carry =:PROTOTYPE:=, and the chain is walked
nearest-first. A follower of =Urgent Task= reads =STATUS= as =wip= from
here and =OWNER= as =johnw= from =Task=, one hop further out. A cycle is a
=user-error= naming the hops in order.

*The two followers, and the agent that finds them.* Those live in the corpus
rather than in this file, which is the point of prototypes: the relation is
between entries, not between places in an outline. This is prose in
=Urgent Task='s body and not a heading of its own, because every heading
below =* Prototypes= is a prototype and every top-level heading in this file
is an attribute declaration — there is no third thing a heading here can be.

#+begin_example
,* TODO Ship the widget
:PROPERTIES:
:PROTOTYPE: Urgent Task
:END:

,* TODO Ship the gadget
:PROPERTIES:
:PROTOTYPE: Urgent Task
:OWNER:     ada
:END:
#+end_example

Neither drawer holds a =STATUS= line. Both entries resolve =STATUS= to
=wip= through =Urgent Task=; =Ship the widget= resolves =OWNER= to =johnw=
through the chain, and =Ship the gadget= to =ada=, because a local value
outranks every prototype.

An agent that matches through that inheritance:

#+begin_example
,* Work in progress, wherever it says so
:PROPERTIES:
:AGENT_QUERY:  (and (todo) (property-resolved "STATUS" "wip"))
:AGENT_FORMAT: OWNER
:END:
#+end_example

=(and (todo) $STATUS^)= is NOT that query written short. =$STATUS^= expands
to =(property-resolved "STATUS")= — one argument, no value — which asks only
whether =STATUS= resolves *at all*; and because =STATUS= declares
=:ATTR_DEFAULT: open= above, every entry in the corpus resolves it. So the
short form matches every TODO there is, and it narrows nothing: a bare
existence test on a name with a declared default is exactly the case the
prefilter cannot push, so it is an unnarrowed scan of the whole scope. A
value has to be written out.

=(and (todo) (property "STATUS" "wip"))= is narrower than either, and wrong
for a different reason: it matches only entries that spell the value in
their own drawer, which is neither of the two above.

=$STATUS^= in boolean position is a known org-ql predicate and runs
unremarked. In value position — =(string-match "w" $STATUS^)= — it becomes
residual Lisp and the evaluation gate asks about it once, exactly as it does
for =$STATUS*=.

A master may also be named by id, which reaches an entry out in the corpus
and needs no heading in this file at all:

#+begin_example
,* TODO Ship the doohickey
:PROPERTIES:
:PROTOTYPE: id:1f2e3d4c-5b6a-7890-abcd-ef0123456789
:END:
#+end_example

That form resolves through =org-id='s location table, which is the one thing
prototypes need configured: =org-id= has to know which file holds the master
(=org-id-track-globally= on and a populated =org-id-locations-file=, or the
master in the same file as the follower). Where the table has no answer the
reference simply dangles, with the ordinary one-message diagnostic. Naming a
master by =name= out of the section above needs none of that.
