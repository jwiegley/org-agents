#+title: org-agents: init.org snippet
#+startup: showall

One =use-package= block, written in the style of the surrounding Org
extensions in =~/org/init.org=, plus a first agent to try it on.

*Where it goes.* Under =*** org-ql= (line 11513 today), immediately after
=**** org-ql-semantic= (which ends at line 11592), as one more level-four
sibling. That is the right neighbourhood: =org-agents= requires =org-ql= and
=org-ql-ext=, whose =property-ts= predicate is the one the examples below
lean on.

One thing about that neighbourhood is worth saying out loud: an agent query
may NOT use =(semantic "...")=. org-ql compiles that predicate by running
its normalizer, which spawns =org db search= past the evaluation gate, so
=org-agents-refused-heads= ships refusing it and the query signals instead
of running. Semantic search stays available as =M-s s=; see the option's
comment in the block below for how to accept the subprocess instead.

One thing is not turned on for you: completion of declared attribute
values. It is a function on Org's own
=org-property-allowed-value-functions=, and a library has no business
adding itself to a user's hook at load time, so the =:hook= entry in the
block below is what arms it. See *The attribute registry* further down for
the file it reads.

There is nothing else that must be configured. The candidate-file
prefilter is ripgrep, which needs no DSN, no config file and no
credential: it is found on =exec-path= or it is not, and where it is not
an unbounded scope is scanned live with one message saying so. Two options
govern it if you want them — see the block below.

* Paste-ready block

**** org-agents

Agents in the sense of Eastgate Tinderbox: an ordinary Org entry carrying an
org-ql query in =:AGENT_QUERY:=, which on update populates itself with links
to every entry that matches — as child alias headings, as a plain list, or
as a table. Queries are org-ql S-expressions with a =$PROP= layer on top, so
=$NEXT_REVIEW= reads as the property name, the value, or a number, according
to the position it appears in.

#+begin_src emacs-lisp
(use-package org-agents
  :after (org-ql-ext)
  :commands (org-agents-update
             org-agents-update-buffer
             org-agents-update-all
             org-agents-preview
             org-agents-list-approvals
             org-agents-mode
             global-org-agents-mode)
  ;; Org calls the dynamic-block writer by name, from C-c C-x C-u and from
  ;; `org-update-all-dblocks', so it has to be autoloaded as well.
  :autoload (org-dblock-write:org-agents
             org-agents-allowed-values)
  :init
  ;; What arms completion of declared attribute values.  The package does
  ;; not add itself to this hook -- it is Org's, and it is the user's.
  ;; Spelled as an `:init' `add-hook' and not as `:hook', because
  ;; use-package appends `-hook' to a `:hook' name that does not already
  ;; end in it, and this one ends in `-functions'.  The symbol is
  ;; autoloaded, so the package still loads on first use and not at
  ;; startup: nothing runs until Org asks for a property's allowed values.
  (add-hook 'org-property-allowed-value-functions
            #'org-agents-allowed-values)
  :bind
  (("M-s a" . org-agents-preview)
   :map
   org-mode-map
   ("C-c C-x Q" . org-agents-update)
   :map
   my-ctrl-c-n-map
   ("u" . org-agents-update-buffer)
   ("U" . org-agents-update-all))
  :custom
  ;; The other six options are best left at their defaults:
  ;; `org-agents-exclude' — (not (property "AGENT_MATCH")) — is what keeps
  ;; agents from consuming each other's aliases;
  ;; `org-agents-safe-queries' grows by answering "remember this approval
  ;; permanently?" at the prompt, which writes to `custom-file'
  ;; (settings.el) — only a query holding Lisp outside the org-ql
  ;; vocabulary ever prompts, and every example below is structurally safe
  ;; and runs unremarked;
  ;; `org-agents-prefilter' is `auto', which narrows an unbounded scope
  ;; with ripgrep where it can and scans live with one message where it
  ;; cannot — set it to `require' to be refused rather than kept waiting,
  ;; or to nil never to spawn anything;
  ;; `org-agents-refused-heads' is `(semantic)', which is what makes
  ;; `(semantic "...")' in an agent query SIGNAL rather than run: org-ql
  ;; compiles that predicate by calling its normalizer, and the normalizer
  ;; spawns `org db search' after the gate has finished and whatever the
  ;; user answered — remove `semantic' from the list to accept that
  ;; subprocess, since no approval overrides a refusal;
  ;; `org-agents-refused-queries' is the negative twin of
  ;; `org-agents-safe-queries', written by pressing `r' in
  ;; `org-agents-list-approvals', which is also where an approval is read
  ;; back and revoked;
  ;; and `org-agents-rg-executable' is "rg", resolved against
  ;; `exec-path' — name the binary here if ripgrep is installed under
  ;; another name, or somewhere a GUI Emacs's `exec-path' does not
  ;; reach.
  ;;
  ;; Where `org-agents-update-all' looks: files (each scanned for
  ;; `:AGENT_QUERY:') or directories, or the symbol `agenda'.
  (org-agents-files (list (org-file "agents.org")
                          org-constants-todo-path)))
#+end_src

* Updating on save

=org-agents-mode= updates a buffer's agents in =before-save-hook=, so an agent
is refreshed by the act of saving the file it lives in. A save whose render
changes nothing writes no bytes — old =AGENT_MATCHED= stamps and all — and a
save spawns no subprocess whatever =org-agents-prefilter= says. Agents whose
scope is =active=, =all= or a directory are named once and skipped: there is
no bound on what one of those would open, and a save is a keystroke. =C-c n
u= still refreshes them on demand.

*The lazy way, and the one to prefer here.* Arm just the files that hold
agents, with a file-local minor mode on the first line. Emacs appends the
=-mode= suffix itself, so the value is =org-agents= and not =org-agents-mode=;
being a =mode:= entry rather than an =eval:= one, it raises no risky-local
prompt, and visiting the file is what autoloads the package:

#+begin_example
# -*- mode: org; mode: org-agents; -*-
#+title: Agents
#+end_example

That suits the two files =org-agents-files= already names, and costs nothing
in any other Org buffer.

*The blanket way.* =global-org-agents-mode= arms every Org buffer whose text
mentions =:AGENT_QUERY:=, deciding that with a plain regexp so the check is
cheap enough to run on every Org buffer you visit. It has to be called to take
effect, which loads =org-agents= at startup rather than on first use — the
price of not having to mark each file:

#+begin_src emacs-lisp
(global-org-agents-mode 1)
#+end_src

=M-s a= sits deliberately beside =M-s s=: semantic search and agent preview are
the two ways of asking "what would match?" before committing anything to a
drawer. Preview is =org-ql-search= over the expanded query with the agent exclusion
appended, and it is the appended form that is gated, so what it shows is
what an agent would render.

No binding is needed for the dynamic block: Org's own =C-c C-x x= offers
=org-agents= as a block type once the package has loaded, and =C-c C-x C-u=
updates the block at point.

* First agent

Put this in =~/org/agents.org= (which the =:custom= above registers), then
update it with =C-c C-x Q=. It uses the default =children= view and the default
=agenda= scope, so it searches the nine files in =org-agenda-files= and needs
no prefilter at all:

#+begin_example
* Reviews that have come due
:PROPERTIES:
:AGENT_QUERY:  (and (todo) (property-ts $NEXT_REVIEW :to today))
:AGENT_FORMAT: NEXT_REVIEW
:AGENT_SORT:   date
:AGENT_LIMIT:  25
:END:
#+end_example

After the update the entry has grown one child per match, and a status line
of its own:

#+begin_example
* Reviews that have come due
:PROPERTIES:
:AGENT_QUERY:   (and (todo) (property-ts $NEXT_REVIEW :to today))
:AGENT_FORMAT:  NEXT_REVIEW
:AGENT_SORT:    date
:AGENT_LIMIT:   25
:AGENT_MATCHED: 3 [2026-08-19 Wed 09:14]
:END:
** [[id:1F2E3D4C-...][Review: Renew the domain]] [2026-08-14 Fri]
:PROPERTIES:
:AGENT_MATCH: t
:END:
#+end_example

Those aliases are ephemeral: every update reaps the ones that hold nothing
but their drawer. Write anything under an alias and it is yours — no update
deletes it, and if its match is gone it is retitled =(stale)= instead.

The whole property vocabulary implemented today: =AGENT_QUERY= (required),
=AGENT_VIEW= (=children= default, =list=, =table=), =AGENT_SCOPE= (=agenda= default,
=active=, =all=, a directory, or a list of files), =AGENT_SORT=, =AGENT_LIMIT=,
=AGENT_COLUMNS= (table), =AGENT_FORMAT= (=children= and =list=). =AGENT_MATCH= and
=AGENT_MATCHED= are written by the package, not by hand.

* A standalone dynamic block

A block with its own =:query= needs no agent entry around it at all, and can
go in any Org file. This one is a table; =C-c C-x C-u= on it renders it:

#+begin_example
#+BEGIN: org-agents :query (and (property "NEXT_REVIEW") (todo "TODO")) :view table :columns "ITEM_BY_ID NEXT_REVIEW LAST_REVIEW" :sort (ts-column 2) :limit 20
#+END:
#+end_example

=ITEM_BY_ID= is the link column, wherever in =:columns= it is named; every
other name is read as a property on the matched heading. =(ts-column 2)=
orders the rendered rows by the second column read as timestamps, and is
table-only — a =children= or =list= view says so rather than sorting nothing.
Written inside an agent entry instead, a block's parameters override that
entry's =AGENT_*= properties name by name, so one agent can carry several
views of itself.
