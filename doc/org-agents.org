** Summary
:PROPERTIES:
:DESCRIPTION: What this package is, in one screen.
:END:
#+cindex: summary
#+cindex: agent

org-agents provides /agents/: ordinary Org entries that carry a query in
an =:AGENT_QUERY:= property and, when you update them, populate
themselves with links back to every entry in your corpus that the query
matches.  An agent renders its matches as child headings, as a plain
list, or as a table.  Nothing else about the entry is special.  It is a
heading like any other, in a file like any other, and you fold it,
annotate it, link to it, export it and commit it exactly as you would
anything else you wrote.

The idea, and the word, come from Eastgate Systems' Tinderbox, where
agents have been in use since 2002.  So do prototypes, action code and the
typed attribute model that the rest of this package implements.  See
[[*Agents in the Tinderbox tradition]] for what those ideas are and what
became of each one here, and [[*History and Acknowledgments]] for the
attribution they are owed.

Beyond agents themselves, org-agents implements the remainder of that
model over Org outlines:

#+attr_texinfo: :table-type table :indic asis
- a corpus-wide attribute registry ::
  One optional file declares your own properties, giving each a type, a
  vocabulary, a default and documentation, and a command lints the corpus
  against those declarations.  See [[*The attribute registry]].
- prototypes ::
  Any entry may read its properties through a /master/ entry it names,
  resolved when a value is read rather than copied into the follower.
  Change the master and every follower changes with it.  See
  [[*Prototypes]].
- appearance from attribute values ::
  A declared attribute may map its values to Emacs faces, and a minor
  mode draws each headline in the face its resolved value names.  It
  writes nothing: no text, no property, no overlay.  See [[*Appearance]].
- action code ::
  An agent may carry not only a query but a small declarative sentence
  saying what to /do/ to the entries the query matched --- applied only by
  an explicit command, and only after a dry run you have read.  See
  [[*Action code]].

The whole package is one file, =org-agents.el=.  It establishes no key
bindings; every command below is reached with {{{kbd(M-x)}}} until you
bind it yourself.

** What an agent is
:PROPERTIES:
:DESCRIPTION: The before, the after, and the one evaluation engine.
:END:
#+cindex: agent, definition of
#+cindex: query
#+cindex: alias
#+cindex: @samp{AGENT_QUERY}, agent property

Suppose your corpus records, on the entries that need it, a =NEXT_REVIEW=
property saying when you next mean to look at something.  The entries
carrying it are scattered across projects, errands and reading lists, and
the set changes weekly.  You can already find them: Org's agenda will
match them, and =org-ql-search= will match them more precisely.  What you
cannot do is /keep/ the answer.  A search result lives in a transient
buffer.  You cannot annotate one of its rows, or link to it, or fold it
away beside the project it belongs to, or read it with =grep=, or commit
it and see in next month's diff what changed.

An agent keeps the answer.  Write a heading whose drawer holds a query:

#+begin_example
,* Up for review
  :PROPERTIES:
  :AGENT_QUERY: (and (todo "TODO") (property "NEXT_REVIEW"))
  :END:
#+end_example

#+findex: org-agents-update
Then, with point anywhere inside that entry, type
{{{kbd(M-x org-agents-update)}}}.  The echo area says
=org-agents: 3 matches=, and the entry now reads:

#+begin_example
,* Up for review
  :PROPERTIES:
  :AGENT_QUERY: (and (todo "TODO") (property "NEXT_REVIEW"))
  :AGENT_MATCHED: 3 [2026-08-20 Thu 17:47]
  :END:
,** [[id:rewrite-exporter][Rewrite the exporter]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
,** [[id:audit-prefilter][Audit the prefilter]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
,** [[id:renew-passport][Renew the passport]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
#+end_example

#+cindex: @samp{AGENT_MATCH}, agent property
#+cindex: @samp{AGENT_MATCHED}, agent property
Each match has become a child heading holding a link to it --- an /alias/,
in Tinderbox's word --- marked =:AGENT_MATCH: t= so that the next update
knows it wrote it.  The agent also records what it found and when, in
=:AGENT_MATCHED:=.  From here the answer is Org text: you can fold the
agent shut, follow a link, write a paragraph under one of the aliases
explaining why it matters, and export or commit the lot.  Writing under an
alias also changes what the next update may do to it, which is worth
knowing before you rely on it; see [[*The alias contract]].

The same three matches can be rendered as a list or as a table inside an
=org-agents= dynamic block instead.  See [[*Views]].

#+cindex: evaluation engine
#+cindex: org-ql, as the evaluation engine
#+cindex: prefilter
#+cindex: ripgrep
One more fact belongs here rather than four chapters later, because a
reader who misunderstands it will misunderstand everything downstream.

*Evaluation is always performed by org-ql, against live Org buffers.*
There is exactly one evaluation engine and therefore exactly one answer.
A query is an org-ql S-expression, extended with a compact =$PROP= reference
layer that this package expands before org-ql sees it (see
[[*The query language]]).  Whatever the scope, whatever the view, the
entries an agent reports are the entries org-ql matched in a real buffer.

#+vindex: org-agents-prefilter
ripgrep appears nowhere in that sentence.  It is an /optional
candidate-FILE prefilter/: for a scope that names a directory rather than
a list of files, org-agents may run ripgrep first to work out which files
are worth opening at all, and then org-ql opens only those.  A prefilter
can therefore only narrow the set of files org-ql reads.  It can never
change what matches, and it can never make something match that org-ql
would not have matched.  Narrowing too little is merely slow; narrowing
too much would be a wrong answer with no error, so only conditions whose
ripgrep answer is provably a superset of org-ql's are ever pushed into it.
Where ripgrep is absent, or where a query offers nothing to push, the
scope is read live instead --- slower, and identical in what it finds.
See [[*Scope and the ripgrep prefilter]].

Because =org-ql-ext= and =org-ext= are not on any package archive, they
cannot be declared in =Package-Requires=, and org-agents cannot be
installed as a self-contained package until that is resolved.  What has
to be true is only that both files are on =load-path= before org-agents
is required.

** Installation
:PROPERTIES:
:DESCRIPTION: Clone it, put three files on load-path, require it.
:END:
#+cindex: installation

There is no package-archive recipe.  Clone the repository and put its
directory, and the directory holding the two modules of the previous
section, on =load-path=:

#+begin_src emacs-lisp
(add-to-list 'load-path "~/src/org-agents")
(add-to-list 'load-path "~/src/dot-emacs/lisp")   ; org-ql-ext, org-ext
(require 'org-agents)
#+end_src

#+cindex: use-package, and org-agents
There is no generated autoloads file either, which matters for exactly
one line of the deferred configuration below.  In the style of the
surrounding Org extensions in the author's own init:

#+begin_src emacs-lisp
(use-package org-agents
  :after (org-ql-ext)
  :commands (org-agents-update
             org-agents-update-buffer
             org-agents-update-all
             org-agents-preview
             org-agents-insert-dblock
             org-agents-list-approvals
             org-agents-check-attributes
             org-agents-attribute-columns
             org-agents-apply-actions
             org-agents-mode
             global-org-agents-mode
             org-agents-faces-mode
             global-org-agents-faces-mode)
  ;; Org calls the dynamic-block writer by name, and Org calls
  ;; `org-agents-allowed-values' by name off one of its own hooks from any
  ;; Org buffer, so both have to be reachable before the package loads.
  :autoload (org-dblock-write:org-agents
             org-agents-allowed-values)
  :init
  ;; Completion of declared attribute values.  A library has no business
  ;; adding itself to a user's hook at load time, so this one is yours.
  (add-hook 'org-property-allowed-value-functions
            #'org-agents-allowed-values)
  :bind (("M-s a" . org-agents-preview)
         :map org-mode-map
         ("C-c C-x Q" . org-agents-update))
  :custom
  (org-agents-files '("~/org/agents.org")))
#+end_src

#+findex: org-agents-allowed-values
The =:autoload= line beside the =add-hook= is not decoration.  Because
the package has no autoloads file, a deferred =use-package= form that
puts =org-agents-allowed-values= on Org's hook without autoloading that
symbol breaks =org-set-property= in *every* Org buffer, with
=void-function org-agents-allowed-values=.  Adding the hook outside the
form, from an init that never loads org-agents eagerly, has the same
effect.  Keep the two together.

** Activation
:PROPERTIES:
:DESCRIPTION: The minimum configuration, which is very little.
:END:
#+cindex: activation
#+cindex: configuration, minimum

Nothing has to be configured for an agent to work.  Write an
=:AGENT_QUERY:= in a drawer and update it; the default scope is your
agenda files, and the default view writes child aliases into the entry
you are looking at.  The remaining settings buy the features you choose
to use.

#+attr_texinfo: :table-type table :indic asis
- =org-agents-files= ::
  #+vindex: org-agents-files
  Which files =org-agents-update-all= opens *and writes*.  Defaults to
  =("~/org/agents.org")=.  Set it if you keep agents in particular files
  and want one command to refresh them all; you do not need it to update
  the agent in front of you.  See [[*By hand]].
- =org-agents-attributes-file= ::
  #+vindex: org-agents-attributes-file
  The attribute registry.  Defaults to ="~/org/attributes.org"=.  Wholly
  optional: a missing or unreadable file declares nothing and says nothing
  about it.  Create it when you want typed attributes, prototypes or
  faces.  See [[*The registry file]].
- =org-agents-prefilter= ::
  #+vindex: org-agents-prefilter
  Defaults to =auto=, which uses ripgrep where the executable is found and
  reads the scope live where it is not.  Leave it alone until you have a
  corpus-scope agent that is too slow.  See [[*Bounding a run]].

#+findex: org-agents-allowed-values
#+vindex: org-property-allowed-value-functions
One hook is deliberately *not* added for you.  Putting
=org-agents-allowed-values= on =org-property-allowed-value-functions=, as
the =use-package= form of the previous section does, is what makes
=org-set-property= complete the values your registry declares --- in every
Org buffer, not only in the corpus.  A library has no business mutating a
user's hook, so the =add-hook= is yours to write.  See
[[*Completing declared values]].

#+findex: org-agents-mode
#+findex: org-agents-faces-mode
#+findex: global-org-agents-mode
#+findex: global-org-agents-faces-mode
Two minor modes are also off until you turn them on: =org-agents-mode=,
which refreshes a buffer's agents before each save (see
[[*org-agents-mode]]), and =org-agents-faces-mode=, which colours
headlines from attribute values (see [[*Faces from attribute values]]).
Each has a globalized counterpart, =global-org-agents-mode= and
=global-org-agents-faces-mode=; the two choose which buffers to act in by
different rules, and for good reason (see [[*global-org-agents-mode]]).

** Conventions used in this manual
:PROPERTIES:
:DESCRIPTION: How commands, options, properties and examples are shown.
:END:
#+cindex: conventions in this manual
#+cindex: typographic conventions

Commands, functions, user options, properties and action verbs are given
their own definitions in [[*Reference]] and are shown there like this:

#+begin_example
 -- Command: org-agents-update
 -- User Option: org-agents-prefilter
 -- Agent Property: AGENT_QUERY
 -- Action Verb: set-property! name value
#+end_example

In running prose, a Lisp symbol is set as ~org-agents-update~ and a
property name, a keyword or a literal value as =AGENT_QUERY=.  A property
is written with its surrounding colons, =:AGENT_QUERY:=, where the point
is the line you type into a drawer, and bare where the point is the name.

#+cindex: key bindings, and the absence of any
#+kindex: C-c C-c
#+kindex: C-c C-x C-u
#+kindex: C-c C-x x
#+findex: org-agents-list-approvals
#+findex: org-dblock-update
#+findex: org-dynamic-block-insert-dblock
#+findex: org-agents-insert-dblock
*This package binds no keys.*  It defines exactly one keymap, and that
one is local to the buffer =org-agents-list-approvals= pops up (see
[[*Reviewing what you approved]]).  Every command in this manual is
therefore shown as {{{kbd(M-x org-agents-update)}}} and the like.  Three
bindings that do appear are Org's own, and work on an =org-agents= dynamic
block because it is a dynamic block: {{{kbd(C-c C-c)}}} inside one
writes it, {{{kbd(C-c C-x C-u)}}} runs ~org-dblock-update~, and
{{{kbd(C-c C-x x)}}} offers =org-agents= among the block types it can
insert.

Examples are shown as Org source, and every one in this manual was run.
Where the output of a run is shown, it is the text the buffer actually
held afterwards, and where an echo-area message is quoted it is the
message the package actually printed.  An absolute path that would
otherwise be a page wide is elided to =…=.  Timestamps are whatever your
own run produces.

Two corpora are printed in full, and every example is run over one of
them, so you can reproduce any of them.  [[*Tutorial]] uses the two small
files of [[*A corpus to work with]] and nothing else.  Every other chapter
uses the corpus and registry of [[*The example corpus]], which is the
tutorial's corpus with more properties on it.  Both use short, readable
=:ID:= values so that the rendered links fit on a line; in your own corpus
they will be the UUIDs =org-id= generates.

The manual carries four indices.  [[*Concept Index]] is the subject-matter
route in and is the one to try first.  [[*Key Index]] lists key sequences.
[[*Command, Function and Name Index]] lists commands, functions, and the
property and verb names, all by name.  [[*Variable Index]] lists user
options and variables.

* Agents in the Tinderbox tradition
:PROPERTIES:
:DESCRIPTION: The five ideas this package borrows, and where each came from.
:END:
#+cindex: Tinderbox
#+cindex: Eastgate Systems
#+cindex: Bernstein, Mark

Nothing in the model this package implements is its own invention.
Agents, prototypes, action code, user-defined attributes and appearance
driven from an attribute's value are Tinderbox's: a Macintosh application
for notes, published by Eastgate Systems, Inc., and designed by Mark
Bernstein, whose copyright notice reads
"Tinderbox is © Copyright 2002-2021 by Eastgate Systems, Inc."
(=tbxman920:5626=).  org-agents is an independent Emacs implementation of
those five ideas over Org outlines.  It is not affiliated with, endorsed
by, or connected to Eastgate Systems in any way, and nothing in it derives
from Tinderbox's code.

This chapter is here rather than in an appendix because the ideas are
easier to learn in the order Tinderbox arrived at them than in the order
an Org property drawer presents them.  Each section says what Tinderbox
does, quoting its own manual, and then what org-agents made of it and
where the rest of this manual describes that.
[[*History and Acknowledgments]] states the attribution proper and
catalogues, with reasons, what was deliberately left out.

All quotations are from the Tinderbox v9.2 manual and are cited by its
line number in the plain-text edition, as =tbxman920:LINE=.  Later
versions of Tinderbox may differ.

** The five ideas
:PROPERTIES:
:DESCRIPTION: Attributes, prototypes, agents, action code, appearance.
:END:
#+cindex: five ideas, the

Tinderbox is built on five ideas that reinforce one another.  Stated as
briefly as they can be:

1. *Attributes.*  Every note has a large space of named, *typed* values.
   Some are the application's; the rest are yours to define, with a type,
   a default, a suggested vocabulary and a description.
2. *Prototypes.*  A note may be described as another note plus its
   differences.  Where it has no value of its own for an attribute, the
   value comes from its prototype --- and this has nothing to do with
   where either note sits in the outline.
3. *Agents.*  A query can itself be a note.  An agent searches the
   document for notes that satisfy its criteria and gathers an alias of
   each one inside itself.
4. *Action code.*  A document can act on itself: an action is a sentence
   that changes one or more notes, and an agent can carry one.
5. *Appearance follows from values.*  How a note looks is itself read out
   of its attributes, so making a set of notes conspicuous is a matter of
   what they mean rather than of what colour you painted them.

Put together, those five say something a search command does not: that
the answer to a question is a part of the document, that describing a
thing and describing where you filed it are different acts, and that a
corpus can be asked to maintain itself.  That is the part worth
borrowing, and it is what the rest of this manual is about.

The five ideas are not borrowed whole.  Tinderbox is one binary document
that one application owns while it is open; an Org corpus is thousands of
plain-text files under version control that other tools also write.  Two
of Tinderbox's mechanisms depend on the first arrangement and are
deliberately absent here: continuous, timer-driven evaluation, and
inheritable action code.  Both absences are argued in
[[*What was deliberately not ported, and why]].

** Attributes in Tinderbox
:PROPERTIES:
:DESCRIPTION: Typed values, declared once, with a vocabulary and a default.
:END:
#+cindex: attribute, Tinderbox
#+cindex: system attribute
#+cindex: user attribute
#+cindex: suggested values

Tinderbox divides the attribute space in two:

#+begin_quote
System attributes: information built into all Tinderbox documents such as
the color of the note, or its width and height.  Tinderbox keeps this
information about every note, and you may view, use, and change it.

User attributes: you may add your own attributes that every note will
have.  For instance, you could add the attribute "Priority," and assign
every note a priority level from one to five.  Or in a bibliography,
create the attribute "Type" and tag the note for each source as either
"primary" or "secondary."

--- /Attributes/, =tbxman920:1338--1342=
#+end_quote

A user attribute is *declared* before it is used, and the declaration
carries more than a name:

#+begin_quote
The inspector lets you choose to type of attribute --- some of the choice
included number, string, URL, or list --- and set the default value that
the attribute should use.  A text field labeled "Description" invites you
to write a brief explanation of the way you intend to use the new
attribute...

--- /User Attributes/, =tbxman920:1534--1536=
#+end_quote

and a vocabulary may be suggested for it:

#+begin_quote
Suggested values can be useful when an attribute's vocabulary should be
limited --- for example, the anticipated values of $Status might be
"planned;in progress;overdue;completed".  Suggested values are entered as
semi-colon delimited lists.

--- /Suggested Values/, =tbxman920:1472--1475=
#+end_quote

*What org-agents made of it.*  Org's own drawer properties are the system
attributes: they exist on every entry, Org gives several of them meaning,
and you may read and write any of them.  What Org has no notion of is the
other half.  A property drawer is untyped and undeclared:
=:REVIEWS: lots= is as valid to Org as =:REVIEWS: 5=, nothing records
that the property was ever meant to be a number, and nothing can tell
you where your corpus and your intentions have drifted apart.

#+cindex: attribute registry
#+vindex: org-agents-attributes-file
#+findex: org-agents-check-attributes
The registry file named by =org-agents-attributes-file= is the missing
half.  One top-level entry declares one attribute: the heading is its
name, =:ATTR_TYPE:= its type, =:ATTR_VALUES:= its suggested values,
=:ATTR_DEFAULT:= its default, and the entry's body is its description.
=org-agents-check-attributes= is then a lint that reports where the corpus
disagrees with the declarations --- a report Tinderbox has no need of,
because there its attributes cannot be used before they are declared.  See
[[*The attribute registry]].

org-agents implements six of Tinderbox's dozen-odd types, keeps
Tinderbox's =set= and =list= semantics exactly, changes their separator
from semicolons to whitespace so as not to fight Org, and declines to port
the type whose values are evaluated.  Each of those decisions is argued in
[[*What it changed]] and [[*What was deliberately not ported, and why]].

** Prototypes in Tinderbox
:PROPERTIES:
:DESCRIPTION: Inheritance that relates two notes, not two positions.
:END:
#+cindex: prototype, Tinderbox
#+cindex: inheritance, prototype
#+cindex: containment is not inheritance

#+begin_quote
Often, the easiest way to describe a note is to explain how it differs
from another note.  We say that the first note serves as the prototype of
the second: it shares all the properties of the prototype, except where
we specify otherwise.

--- /Prototypes/, =tbxman920:1682--1685=
#+end_quote

The plain-text edition of that passage has its clauses out of order, an
artifact of the extraction; the sentence above is those four lines put
back in the order the words require.

The lookup rule is a short checklist:

#+begin_quote
Whenever Tinderbox looks up the value of an attribute, it reviews the
following checklist: If the note has a value for that attribute, that's
the value.  Otherwise, If the note has a prototype, and if the prototype
has a value, then we inherit the prototype's value.  Otherwise, If the
prototype itself has a prototype, we inherit that value.  Otherwise, We
use the default value for that attribute.

--- /Inheritance/, =tbxman920:1739--1746=
#+end_quote

and the sentence that makes the idea worth having at all:

#+begin_quote
Note that inheritance has nothing to do with the document hierarchy; a
note's prototype is not necessarily its container.

--- /Inheritance/, =tbxman920:1751=
#+end_quote

#+cindex: @samp{PROTOTYPE}, entry property
#+findex: property-resolved
#+findex: org-agents-resolve-property
*What org-agents made of it.*  =:PROTOTYPE:= on any entry names a master,
either by name out of a reserved =Prototypes= section of the registry file
--- the same name Tinderbox gives the same container --- or as =id:UUID=
anywhere in the corpus.  The resolution order is Tinderbox's checklist,
with its two prototype steps written as one walk of the chain: the entry's
own drawer, then the chain nearest hop first, then the registry's
=:ATTR_DEFAULT:=, then nothing.  Reads are virtual, so
a master may be changed once and every follower changes with it.  See
[[*Prototypes]] and [[*The resolution order]].

#+cindex: outline inheritance, versus prototypes
#+vindex: org-use-property-inheritance
Org does have an inheritance of its own --- =org-use-property-inheritance=
makes a property visible to an entry's descendants --- and it is a
different relation.  Tinderbox's sentence above is exactly org-agents'
position, and it is why the query layer spells the two axes differently:
=$NAME*= asks the outline and =$NAME^= asks the prototype chain.
Containment is not inheritance; a task filed under a project is not a kind
of project, and a query has to say which it means.  See [[*The two axes]].

** Agents in Tinderbox
:PROPERTIES:
:DESCRIPTION: A query that is a note, gathering aliases of what it finds.
:END:
#+cindex: agent, Tinderbox
#+cindex: alias, Tinderbox

#+begin_quote
Agents are notes that search your Tinderbox document continuously for
notes that meet the agent's criteria.  If an agent finds a note that
satisfies its criteria, it automatically places an alias of that note
inside the agent.  The agent can also apply an action to notes it finds.
For example, one agent might find notes that represent overdue library
books and automatically set their color to red.

--- /Anatomy Of A Note/, =tbxman920:1015--1017=
#+end_quote

The property that makes a note an agent, and the one that gives it
something to do:

#+begin_quote
AgentQuery --- the criteria for which the agent is looking.  If a note
satisfies the query, the agent will contain an alias of that note.  If a
note no longer satisfies that query, the agent will remove the note's
alias from its children.

AgentAction --- an optional action to be performed on the newly-created
alias of any note that matches the agent's query.

--- /Agents/, =tbxman920:2538--2545=
#+end_quote

*What org-agents made of it.*  An ordinary Org entry carrying
=:AGENT_QUERY:=; the property is what makes the entry an agent, exactly as
=$AgentQuery= is what makes a Tinderbox note one.  =:AGENT_ACTION:= is
=$AgentAction=.  In the default view each match becomes a child alias
heading, and a match that no longer satisfies the query loses its alias
--- with one deliberate exception, for an alias you have written under,
which is marked stale rather than removed.  See [[*Views]] and
[[*The alias contract]].

Two differences are worth naming here, because a Tinderbox reader will
look for them.  Tinderbox agents run *continuously*, on a priority-driven
timer; org-agents' run when you say so.  And a Tinderbox alias is a live
proxy of its original, where an org-agents alias is a heading holding a
link and nothing more.  Both are argued in [[*What it changed]] and
[[*What was deliberately not ported, and why]].

** Action code in Tinderbox
:PROPERTIES:
:DESCRIPTION: A document that acts on itself, and when it does so.
:END:
#+cindex: action code, Tinderbox
#+cindex: rule, Tinderbox
#+cindex: edict, Tinderbox

#+begin_quote
An action describes a change made on one or more notes.  For example, the
action $Color(California)="red" sets the color of the note named
"California" to "red".

--- /Queries and Actions/, =tbxman920:2795--2796=
#+end_quote

Tinderbox runs an action at several different times, and the times are as
much a part of the idea as the syntax:

#+begin_quote
An OnAdd action is performed when a note is added to a container, is
discovered by an agent, or is placed atop an adornment, and affects the
note being added.  A Rule is performed at frequent intervals, and affects
the note that possesses the rule.  An Edict is performed after a document
is opened, and at infrequent intervals while the document remains open.

--- /Queries and Actions/, =tbxman920:2798--2801=
#+end_quote

It is a full language, and it reaches outside the document:

#+begin_quote
If an action is simply an expression, the expression is evaluated and the
result discarded.  For example, the action runCommand("open
/Applications/iTunes.app") will ask your computer to open iTunes.

--- /Side Effects/, =tbxman920:2880--2882=
#+end_quote

#+cindex: @samp{AGENT_ACTION}, agent property
#+findex: org-agents-apply-actions
*What org-agents made of it.*  =:AGENT_ACTION:= holds a declarative
sentence over a *fixed vocabulary of nine verbs* --- =set-property!=,
=delete-property!=, =tag!=, =todo!=, =priority!=, =scheduled!=,
=deadline!=, =effort!=, =archive!= --- applied to the entries the query
matched.  It is a vocabulary rather than a language: the parser is a
regexp lexer, a token becomes a function by name construction plus
=fboundp=, arguments reach a verb as strings, and *nothing in the property
is ever evaluated*.  The worst thing expressible is a bounded Org edit
that =grep= can find afterwards.  See [[*Action code]] and
[[*The nine verbs]].

The three times at which Tinderbox runs an action are all absent.
=:AGENT_ACTION:= is run by one command, ~org-agents-apply-actions~, typed,
and that command prints a dry run and writes nothing until you have agreed
to it.  Neither minor mode runs an action, no timer does, and saving a
file does not.  The reason is stated in
[[*What was deliberately not ported, and why]]; the mechanism, and why it
is structural rather than merely disciplined, is in
[[*The three refusals]].

** Appearance in Tinderbox
:PROPERTIES:
:DESCRIPTION: Colour read out of attribute values.
:END:
#+cindex: appearance, Tinderbox
#+cindex: colour from attribute values

#+begin_quote
The Inspector provides direct access to many of the most-commonly-used
attributes.  For example, the Appearance inspector lets you change $Color
--- the note's Color --- $BorderColor --- the color of the note's border
--- and many other attributes related to the note's appearance.

--- /Attributes/, =tbxman920:1353--1354=
#+end_quote

and, joining appearance to agents:

#+begin_quote
An agent that contains "urgent tasks" can automatically change their
color in order to draw your attention.

--- /Actions, Expressions, and Rules/, =tbxman920:2792=
#+end_quote

#+findex: org-agents-faces-mode
#+cindex: @samp{ATTR_FACES}, registry property
*What org-agents made of it.*  =:ATTR_FACES:= in the registry maps an
attribute's values to Emacs faces, and =org-agents-faces-mode= draws a
headline in the face its *resolved* value names.  Resolved is the whole
point: an entry that spells only =:PROTOTYPE:=, or nothing at all and so
takes =:ATTR_DEFAULT:=, is coloured exactly as one that spells the value
in its own drawer.  See [[*Appearance]].

The mechanism, though, is not Tinderbox's.  There, colour follows from
attribute values *by running action code*: a rule or an agent action
assigns =$Color=, which is a write to a note.  Here it is one font-lock
keyword --- no text inserted, no property written, no overlay created,
and turning the mode off puts the buffer back exactly as it was.  That
difference is what makes it safe to leave on in a file under version
control.

** What Org already had
:PROPERTIES:
:DESCRIPTION: The parts of the model Org supplies, so the new parts are visible.
:END:
#+cindex: Org, what it already provides

#+findex: org-agenda-columns
#+vindex: org-property-allowed-value-functions
Much of Tinderbox's model has an Org counterpart already, and org-agents
neither replaces nor reimplements any of it.  Knowing which parts are
Org's makes it clear how little of this package is actually new.

#+attr_texinfo: :table-type table :indic asis
- the property drawer ::
  The attribute space itself, minus the types.
- =:NAME_ALL:=, and =org-property-allowed-value-functions= ::
  A per-file vocabulary, and the mechanism that completes it.
- =org-use-property-inheritance= ::
  Inheritance along the outline --- a different axis.
- the agenda, and org-ql ::
  The query engine, and interactive searching.
- column view, and =org-agenda-columns= ::
  A table of attribute values, editable in place.
- dynamic blocks ::
  A region of a file that a function rewrites.
- tags, TODO keywords, priorities, planning lines ::
  Most of what an action needs to be able to set.

What org-agents adds on top is correspondingly narrow: a declaration for
the properties you invented, so they can have a type and a vocabulary and
be linted; a second inheritance axis that relates two entries instead of
two positions; a way for a query's answer to become part of the document
rather than a transient buffer; a way for appearance to follow from a
value without anything being written; a bounded action vocabulary with a
dry run in front of it; and a prefilter, so that asking a question of a
whole corpus is affordable.

#+findex: org-ql-search
#+findex: org-agents-preview
In particular, if what you want is to /look/ at the answer to a query
once, Org and org-ql already do that better than an agent does, and
=org-agents-preview= is the door into it (see
[[*Looking before you write]]).  An agent is for a question you want to
keep asking, whose answer you want to keep.

* Tutorial
:PROPERTIES:
:DESCRIPTION: One agent, built up a step at a time, with the real output.
:END:
#+cindex: tutorial
#+cindex: first agent

This chapter builds one agent from nothing, a property at a time.  Every
step was run, and the output shown after each is the text the buffer
actually held.  No registry and no configuration is needed, and the scope
stays on your agenda files until the last step, which changes it in order
to show you what a scope change costs.

** A corpus to work with
:PROPERTIES:
:DESCRIPTION: Two small files, given in full, so the steps are reproducible.
:END:
#+cindex: corpus, tutorial

#+vindex: org-agenda-files
#+vindex: org-directory
Make a directory, put these two files in it, add both to
=org-agenda-files=, and point =org-directory= at the directory --- the
last of those matters only for the scope step near the end.  The first
file is a corpus in miniature: two projects, two errands, and a
=NEXT_REVIEW= property on some of them but not all.

#+cindex: @samp{ID}, and readable link targets
The =:ID:= values are short and readable only so that the links this
tutorial writes fit on a printed line.  In your own corpus they will be
the UUIDs =org-id= generates, and everything below works the same.

=work.org=:

#+begin_example
,#+title: Work

,* Projects
  :PROPERTIES:
  :OWNER: me
  :END:
,** TODO Rewrite the exporter
   :PROPERTIES:
   :ID:          rewrite-exporter
   :NEXT_REVIEW: 2026-09-01
   :END:
,** TODO Audit the prefilter
   :PROPERTIES:
   :ID:          audit-prefilter
   :NEXT_REVIEW: 2026-08-25
   :END:
,** DONE Ship 0.1
   :PROPERTIES:
   :ID: ship-0-1
   :END:
,* Errands
,** TODO Renew the passport
   :PROPERTIES:
   :ID:          renew-passport
   :NEXT_REVIEW: 2026-08-21
   :END:
,** TODO Collect the print
   :PROPERTIES:
   :ID: collect-print
   :END:
#+end_example

=agents.org= is where the agent will live.  It starts empty apart from
its title:

#+begin_example
,#+title: Agents
#+end_example

Three of the five entries in =work.org= have both a =TODO= keyword and a
=NEXT_REVIEW= property.  Those three are the answer the agent should
find, and it is worth knowing it in advance: =Ship 0.1= is =DONE=, and
=Collect the print= has no review date.

** Your first agent
:PROPERTIES:
:DESCRIPTION: One property, one command, three child headings.
:END:
#+cindex: agent, writing one
#+findex: org-agents-update

In =agents.org=, write a heading and give it a query:

#+begin_example
,* Up for review
  :PROPERTIES:
  :AGENT_QUERY: (and (todo "TODO") (property "NEXT_REVIEW"))
  :END:
#+end_example

That is the whole of it.  =:AGENT_QUERY:= is what makes the entry an
agent; every other agent property has a default, and the defaults are the
ones you want here.  The query is a plain org-ql S-expression --- =and=,
=todo= and =property= are all org-ql's --- so nothing about it needs your
approval before it runs.  A query built out of anything else does; see
[[*What is evaluated, and what is refused]].

Now put point anywhere inside that entry --- on the heading, in the
drawer, or in the body --- and type {{{kbd(M-x org-agents-update)}}}.
The echo area says:

#+begin_example
org-agents: 3 matches
#+end_example

and the buffer now reads:

#+begin_example
,#+title: Agents

,* Up for review
  :PROPERTIES:
  :AGENT_QUERY: (and (todo "TODO") (property "NEXT_REVIEW"))
  :AGENT_MATCHED: 3 [2026-08-20 Thu 17:47]
  :END:
,** [[id:rewrite-exporter][Rewrite the exporter]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
,** [[id:audit-prefilter][Audit the prefilter]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
,** [[id:renew-passport][Renew the passport]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
#+end_example

#+kindex: C-c C-o
The three matches are the three you expected.  Follow one of the links
with {{{kbd(C-c C-o)}}} and you land on the entry in =work.org=.

#+vindex: org-agents-files
#+findex: org-agents-update-buffer
#+findex: org-agents-update-all
Two other commands do the same work over more ground:
=org-agents-update-buffer= updates every agent in the current buffer, and
=org-agents-update-all= updates every agent in the files
=org-agents-files= names.  See [[*By hand]].

** What the update wrote
:PROPERTIES:
:DESCRIPTION: Aliases, the match record, and the unsaved buffer.
:END:
#+cindex: alias
#+cindex: @samp{AGENT_MATCHED}, agent property

Read what the update put in the file, because each part of it is a
promise about the next update.

#+cindex: @samp{AGENT_MATCH}, agent property
Each match became a child heading whose title is a link to the match and
whose drawer holds =:AGENT_MATCH: t=.  That property is written by the
package and never by you: it is how the next update recognizes the
headings it wrote, so that it can replace them.  A child that has never
carried it is not the package's to touch at all.  A heading of this kind
is an /alias/, which is Tinderbox's word for it.

The agent itself gained =:AGENT_MATCHED:=, holding a count and an
inactive timestamp.  It records that the answer was computed, and when.
An agent whose stamp is three weeks old is telling you something an
agent that quietly re-answered on a timer could not.

#+cindex: buffer, left modified by an update
#+kindex: C-/
Notice what the update did *not* do: it did not save the file.  An update
leaves its buffers modified and unsaved on purpose, so that you can read
the result over --- and undo it with {{{kbd(C-/)}}} --- before you keep
it.  That is true of =org-agents-update-all= across many files as well.

Two consequences of the =:AGENT_MATCHED:= stamp are worth knowing now
rather than discovering later.  Its timestamp is inactive, and inactive
timestamps are visible to queries, so a =(ts-inactive :from ...)= query
over a corpus that holds agents will match the agents themselves.  And
because the stamp changes, a version-control diff of a saved update shows
movement even where the rendered aliases did not move.
[[*What writing AGENT_MATCHED costs]] sets out the whole cost of
recording the result on the agent.

#+cindex: alias, annotating one
Now write a line of your own under one of the aliases:

#+begin_example
,** [[id:audit-prefilter][Audit the prefilter]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
Why this one matters: it is the slow one.
#+end_example

You have just changed who owns that heading.  An alias holding nothing but
its drawer is /pristine/, and every update deletes it and writes it again.
The moment there is anything under it, no update will delete it; if its
match stops matching, the heading is marked =(stale)= and left where it
is, with your note.  This is the single most important thing to understand
about the =children= view, and [[*The alias contract]] sets out its four
sharp edges.

Delete that line again before going on: the steps below print the output
of an agent whose three aliases are all pristine, and an alias you have
adopted is one this package will no longer rewrite --- which is exactly
what the paragraph above promised.

** Showing properties beside the link
:PROPERTIES:
:DESCRIPTION: :AGENT_FORMAT:, so you need not open a match to read it.
:END:
#+cindex: @samp{AGENT_FORMAT}, agent property

A list of titles is often not enough: for a review queue you want the
date beside each one.  Add =:AGENT_FORMAT:=, naming properties to show
after the link, and update again:

#+begin_example
,* Up for review
  :PROPERTIES:
  :AGENT_QUERY:  (and (todo "TODO") (property "NEXT_REVIEW"))
  :AGENT_FORMAT: NEXT_REVIEW
  :AGENT_MATCHED: 3 [2026-08-20 Thu 17:47]
  :END:
,** [[id:rewrite-exporter][Rewrite the exporter]] 2026-09-01
:PROPERTIES:
:AGENT_MATCH: t
:END:
,** [[id:audit-prefilter][Audit the prefilter]] 2026-08-25
:PROPERTIES:
:AGENT_MATCH: t
:END:
,** [[id:renew-passport][Renew the passport]] 2026-08-21
:PROPERTIES:
:AGENT_MATCH: t
:END:
#+end_example

=:AGENT_FORMAT:= takes whitespace-separated property names, so
=NEXT_REVIEW OWNER= would show both.  Be aware of two things before you do
that.  The values are read from the match's own drawer with *no*
inheritance, so naming =OWNER= here shows nothing for the two matches
under =Projects=, even though =Projects= sets it --- the outline axis has
a spelling of its own, and it is =$OWNER*= (see [[*The two axes]]).  And a
named property that a match does not have contributes an empty string,
which leaves trailing whitespace on the heading.  See [[*Formats]].

** The same matches as a table
:PROPERTIES:
:DESCRIPTION: :AGENT_VIEW: table, :AGENT_COLUMNS:, and a sorted queue.
:END:
#+cindex: @samp{AGENT_VIEW}, agent property
#+cindex: @samp{AGENT_COLUMNS}, agent property
#+cindex: table view
#+cindex: dynamic block

Child headings are the right rendering for something you want to fold
into the outline and write under.  For a queue you mean to scan and sort,
a table is better.

First delete the three aliases the last update wrote, because a change of
view does not reclaim the outline the previous view built: only the
=children= renderer looks for aliases, so the table renderer will leave
them sitting under the agent for ever.  See
[[*Limitations of the views]].  Then set =:AGENT_VIEW: table= and name the
columns:

#+begin_example
,* Up for review
  :PROPERTIES:
  :AGENT_QUERY:   (and (todo "TODO") (property "NEXT_REVIEW"))
  :AGENT_VIEW:    table
  :AGENT_COLUMNS: ITEM_BY_ID NEXT_REVIEW
  :END:
#+end_example

Update it, and in place of the aliases there is an =org-agents= dynamic
block, which the update opened because the entry had none:

#+begin_example
,#+BEGIN: org-agents
| ITEM_BY_ID           | NEXT_REVIEW |
|----------------------+-------------|
| [[id:rewrite-exporter][Rewrite the exporter]] |  2026-09-01 |
| [[id:audit-prefilter][Audit the prefilter]]  |  2026-08-25 |
| [[id:renew-passport][Renew the passport]]   |  2026-08-21 |
,#+END:
#+end_example

#+cindex: @samp{ITEM_BY_ID}, agent column
=ITEM_BY_ID= is the link to the match, wherever in the column list you
put it.  Every other name is read as a property at the match, and a
property the match does not have makes an empty cell rather than an
error.  The renderer writes an unpadded table and then asks Org to align
it, so the table arrives aligned; the alignment is cosmetic, and a
failure there is reported and stepped over rather than allowed to take
the update down with it.

#+cindex: @samp{AGENT_SORT}, agent property
A review queue in file order is not much of a queue.  Add a sort:

#+begin_example
  :AGENT_SORT:    (ts-column 2)
#+end_example

and the rows come out in date order:

#+begin_example
,#+BEGIN: org-agents
| ITEM_BY_ID           | NEXT_REVIEW |
|----------------------+-------------|
| [[id:renew-passport][Renew the passport]]   |  2026-08-21 |
| [[id:audit-prefilter][Audit the prefilter]]  |  2026-08-25 |
| [[id:rewrite-exporter][Rewrite the exporter]] |  2026-09-01 |
,#+END:
#+end_example

=(ts-column 2)= sorts the table's rows by reading column 2 as a timestamp;
the count is one-based over =:AGENT_COLUMNS:=.  It is a row sort, so it
applies to a table and is refused in any other view.  A =list= view is
available too, and a block can be given parameters of its own so that one
agent carries two views at once.  See [[*Views]] and [[*Dynamic blocks]].

** Narrowing what the agent reads
:PROPERTIES:
:DESCRIPTION: :AGENT_SCOPE:, :AGENT_LIMIT:, and the first prefilter message.
:END:
#+cindex: @samp{AGENT_SCOPE}, agent property
#+cindex: @samp{AGENT_LIMIT}, agent property
#+cindex: scope

#+vindex: org-directory
Everything so far has used the default scope, =agenda=, which reads the
files =org-agenda-files= names.  =:AGENT_SCOPE:= changes that.  Its value
may be =agenda=, =active=, =all=, a directory relative to
=org-directory=, or a list of file names.  Adding a limit as well:

#+begin_example
,* The two nearest reviews
  :PROPERTIES:
  :AGENT_QUERY:   (and (todo "TODO") (property "NEXT_REVIEW"))
  :AGENT_SCOPE:   ("work.org")
  :AGENT_VIEW:    table
  :AGENT_COLUMNS: ITEM_BY_ID NEXT_REVIEW
  :AGENT_SORT:    (ts-column 2)
  :AGENT_LIMIT:   2
  :END:
,#+BEGIN: org-agents
| ITEM_BY_ID          | NEXT_REVIEW |
|---------------------+-------------|
| [[id:renew-passport][Renew the passport]]  |  2026-08-21 |
| [[id:audit-prefilter][Audit the prefilter]] |  2026-08-25 |
,#+END:
#+end_example

The echo area says =org-agents: 2 matches=, and =:AGENT_MATCHED:= records
2 --- the rows written, not the rows found.  The limit is applied *after*
the sort, so these really are the two nearest reviews and not the first
two org-ql happened to come across.

#+vindex: org-agents-prefilter
Now try a scope that names a directory instead of a file.  Go back to the
=Up for review= agent, set =:AGENT_SCOPE: .= on it --- the directory
holding these two files, since =org-directory= is where you put them ---
and update.  The echo area says =org-agents: 3 matches=, the same three as
before.

What is different is invisible, and it is your introduction to the
prefilter.  =agenda= and an explicit file list *name* the files they will
read, so there is nothing for a prefilter to work out and none is run.
=active=, =all= and a directory name nothing: naming a directory says
nothing about how much it holds, and reading one live means opening
however many files it turns out to contain.  Those three scopes are
therefore narrowed with ripgrep first, where the query gives it something
to look for --- and this query does, so with ripgrep installed the update
you have just run asked ripgrep which of the two files could hold a match
before org-ql opened either.

Where that cannot be done, the scope is read live and the run says so.
Set ~org-agents-prefilter~ to nil, update again, and the fallback message
is what you get:

#+begin_example
org-agents: scope ‘.’ not narrowed (prefiltering off); scanning 2 files live
org-agents: 3 matches
#+end_example

Without ripgrep installed the same line reads =(ripgrep not found)=
instead, and there are two further reasons it can give; see
[[*Which scopes get narrowed, and why]].  Set the option back to =auto=
when you have read the message.  Whichever path a run takes, the answer is
the same three matches, because a prefilter chooses files and never
matches.  See [[*Scope and the ripgrep prefilter]].

** Refreshing on save
:PROPERTIES:
:DESCRIPTION: org-agents-mode, and why a save can afford it.
:END:
#+cindex: updating on save
#+findex: org-agents-mode
#+findex: global-org-agents-mode

#+kindex: C-x C-s
Typing a command to refresh an agent gets old.  Put the buffer back to
the simple version:

#+begin_example
,* Up for review
  :PROPERTIES:
  :AGENT_QUERY: (and (todo "TODO") (property "NEXT_REVIEW"))
  :END:
#+end_example

turn on {{{kbd(M-x org-agents-mode)}}}, and save with {{{kbd(C-x C-s)}}}.
The echo area says =org-agents: updated 1 agent=, and the file that
reached disk is the fully rendered one --- the three aliases and the
=:AGENT_MATCHED:= stamp included.

#+cindex: byte-identical save
Save again with nothing changed and the file on disk is *byte-for-byte
identical*, old stamp and all.  That is not an accident: an update that
renders what was already there puts the buffer back exactly as it was, and
it is the one property that makes writing =:AGENT_MATCHED:= on every save
affordable.  Without it, every save of every file holding an agent would
show up in =git diff=.

Three deliberate refusals are what keep a save cheap, and the paragraph
above is the first of them.  The second is that a save never spawns a
prefilter, whatever =org-agents-prefilter= says.  The third follows from
it: an agent whose scope *needs* a prefilter is not updated on save at
all.  It is named once and left for =org-agents-update=.  Add
=:AGENT_SCOPE: all= to the agent above, save, and you get:

#+begin_example
org-agents: not updated on save, the scope needs a prefilter: Up for review (…/agents.org:3)
#+end_example

with the render left exactly as it was.  The reasoning behind all three
refusals is in [[*The three refusals on the save path]].

#+findex: global-org-agents-mode
=org-agents-mode= is buffer-local.  {{{kbd(M-x global-org-agents-mode)}}}

* The query language
:PROPERTIES:
:DESCRIPTION: org-ql, and the $PROP layer written on top of it.
:END:

#+cindex: query language
#+cindex: query, an agent's

An agent is an Org entry carrying a query, and the query is the whole of
what the agent knows about your corpus.  This chapter is about writing
one: the language it is written in, the shorthand this package adds to
that language, and the two axes along which a property may be read.

Nothing here says anything about what an agent /does/ with its matches.
For that see [[*Views]] and [[*Updating]].

Every query in this chapter was run over the corpus and registry of
[[*The example corpus]], which are printed there in full, and the output
shown after each is what the agent rendered.

** org-ql is the base language
:PROPERTIES:
:DESCRIPTION: What org-agents adds, and what it leaves alone.
:END:

#+cindex: org-ql, as the base language
#+cindex: predicate, org-ql
An agent's query is an org-ql sexp query.  This package defines no query
language of its own, and does not wrap or restrict org-ql's: anything you
can write in an org-ql sexp query you can write in =:AGENT_QUERY:=.  That
includes the predicates --- ~todo~, ~tags~, ~heading~, ~level~,
~priority~, ~category~, ~ts~, ~scheduled~, ~deadline~, ~closed~, ~src~
and the rest --- the combinators ~and~, ~or~, ~not~, ~when~ and ~unless~,
the relational predicates ~parent~, ~ancestors~, ~children~ and
~descendants~, and arbitrary Lisp.

The predicate catalogue is org-ql's own and is not reproduced here.  See
[[info:org-ql::Queries][Queries]] in the org-ql manual for the list, the
argument shapes, and the aliases.  Two of org-ql's conventions are worth
recalling because they surprise people who meet them through an agent: a
bare string is read as a ~regexp~ predicate over the entry's text, so
=:AGENT_QUERY: "Tinderbox"= is a full-text search rather than a heading
search; and the comparator symbols ~<~, ~<=~, ~>~, ~>=~ and ~=~ need no
quoting where a predicate accepts one.

What this package adds to that language is small and is the subject of
the rest of this chapter:

- the =$PROP= reference layer, which is rewritten into plain org-ql
  before anything else happens ([[*Property references]]);
- one predicate, ~property-resolved~, which org-ql has no equivalent of
  ([[*The property-resolved predicate]]);
- a gate, because a query read out of a file is code read out of a file
  ([[*What is evaluated, and what is refused]]);
- the conjunct in ~org-agents-exclude~, which is conjoined into every
  query so that an agent does not match the aliases it wrote
  ([[*The structural gate]]);
- an optional ripgrep prefilter, which chooses which files org-ql opens
  and can never change what matches
  ([[*Scope and the ripgrep prefilter]]).

#+vindex: org-agents-exclude
#+cindex: alias, excluded from an agent's matches
One habit is worth forming early.  Where org-ql has a predicate for what
you mean, write the predicate rather than the equivalent Lisp.  Both
answer the same question, but a predicate call stays inside what the gate
admits without asking, and it may be pushed into the prefilter; a piece
of Lisp does neither.  So prefer =(level < 3)= to =(< $LEVEL 3)=, and
=(todo "TODO")= to =(equal $TODO "TODO")=, and keep the Lisp for the
questions org-ql has no predicate for.

** Property references
:PROPERTIES:
:DESCRIPTION: The $PROP layer, and why it exists.
:END:

#+cindex: @samp{$PROP}, property reference
#+cindex: @samp{$NAME}, property reference
#+cindex: property reference
#+cindex: expansion, of a property reference
#+cindex: sugar, the property-reference
A property reference is a ~$~ followed by a property name, optionally
followed by one suffix:

#+begin_example
$URL        the entry's own :URL: value
$URL*       the outline axis:   an ancestor's value counts
$URL^       the prototype axis: a master's value counts
#+end_example

The layer exists for two reasons.  The first is brevity: over a corpus
with a dozen user attributes ~property~ appears in almost every query,
and ~$NEXT_REVIEW~ says what =(property "NEXT_REVIEW")= says in a third
of the space.  The second reason matters more.  "The
entry's =:OWNER:=" is ambiguous in an outline, and dangerously so ---
it may mean the value in this entry's own drawer, or the one an ancestor
wrote, or the one a prototype lends.  Writing ~$OWNER~, ~$OWNER*~ and
~$OWNER^~ forces the question to be answered in the query, where a reader
can see it, rather than in the reader's head.  See [[*The two axes]].

Expansion is a source-to-source rewrite of the form, performed before the
gate is consulted and before org-ql sees anything.  The expander reads no
buffer and evaluates nothing, so what a reference means never depends on
where point happens to be.  That also means you can work out what a query
will do by expanding it in your head, and that the form the gate shows you
is the expanded one --- so a prompt about =(> $REVIEWS 3)= names
~string-to-number~ and ~org-entry-get~, which is what will actually run.

Write the name as the drawer spells it.  Org compares property keys
case-insensitively, so a drawer key =:next_review:= answers a query for
=NEXT_REVIEW=, but a reader of your query has only what you wrote.

** The four positions
:PROPERTIES:
:DESCRIPTION: Boolean, value, numeric and name position, with an example of each.
:END:

#+cindex: position, of a property reference
#+cindex: boolean position
#+cindex: value position
#+cindex: numeric position
#+cindex: name position
A reference expands according to the position it appears in.  There are
four positions, and the whole of the layer is in this list --- what you
write, and what org-ql is handed:

#+attr_texinfo: :table-type table :indic asis
- ~$URL~ ::
  ~(property "URL")~
- ~$URL*~ ::
  ~(org-entry-get nil "URL" t)~
- ~$URL^~ ::
  ~(property-resolved "URL")~
- ~(and (todo) $URL)~ ::
  ~(and (todo) (property "URL"))~
- ~(string-match "gh" $URL)~ ::
  ~(string-match "gh" (or (org-entry-get nil "URL") ""))~
- ~(equal $OWNER* "johnw")~ ::
  ~(equal (or (org-entry-get nil "OWNER" t) "") "johnw")~
- ~(equal $OWNER^ "johnw")~ ::
  ~(equal (or (org-agents-resolve-property-quietly "OWNER") "") "johnw")~
- ~(> $REVIEWS 3)~ ::
  ~(> (string-to-number (or (org-entry-get nil "REVIEWS") "0")) 3)~
- ~(> $REVIEWS* 3)~ ::
  ~(> (string-to-number (or (org-entry-get nil "REVIEWS" t) "0")) 3)~
- ~(> $REVIEWS^ 3)~ ::
  ~(> (string-to-number (or (org-agents-resolve-property-quietly "REVIEWS") "0")) 3)~
- ~(property $OWNER "johnw")~ ::
  ~(property "OWNER" "johnw")~
- ~(property-ts $NEXT_REVIEW :from -7)~ ::
  ~(property-ts "NEXT_REVIEW" :from -7)~
- ~(property-resolved $STATUS "blocked")~ ::
  ~(property-resolved "STATUS" "blocked")~
- ~(children $URL)~ ::
  ~(children (property "URL"))~
- ~$ITEM~ ::
  ~(org-get-heading t t t t)~

The four rules behind it are these.

#+texinfo: @subheading Boolean position

A reference stands where a query is expected: as the whole query, as an
argument of ~and~, ~or~, ~not~, ~when~ or ~unless~, or as the query
argument of ~parent~, ~ancestors~, ~children~ or ~descendants~.  There it
becomes a predicate: ~(property NAME)~ for a bare reference,
~(property-resolved NAME)~ for the prototype axis, and the inheriting
~org-entry-get~ call for the outline axis.

Motivation: anything actionable that has a link.

#+begin_src org
,* Anything with a link
  :PROPERTIES:
  :AGENT_QUERY:  (and (todo) $URL)
  :AGENT_VIEW:   list
  :END:
#+end_src

renders

#+begin_example
- [[id:rewrite-exporter][Rewrite the exporter]]
- [[id:renew-passport][Renew the passport]]
#+end_example

=Tinderbox notes= has a =:URL:= but no TODO keyword, so it does not
match.  Nothing was asked about this query: ~$URL~ became a plain org-ql
predicate, and the gate admits it unremarked.

#+texinfo: @subheading Value position

A reference in residual Lisp --- Lisp that is not a predicate call ---
becomes ~(or ACCESSOR "")~.  It is never nil, so ~string-match~ and its
neighbours cannot signal at an entry that has no such property.

Motivation: which of these live on GitHub?

#+begin_src org
,* Hosted on GitHub
  :PROPERTIES:
  :AGENT_QUERY:  (string-match "github" $URL)
  :AGENT_VIEW:   list
  :AGENT_FORMAT: URL
  :END:
#+end_src

renders

#+begin_example
- [[id:rewrite-exporter][Rewrite the exporter]] https://github.com/example/exporter
#+end_example

This one is residual Lisp, so it reaches the gate: the first update asks
once, and remembers the answer.  See [[*Remembered approvals]].

#+texinfo: @subheading Numeric position

Any argument of ~<~, ~>~, ~<=~, ~>=~, ~=~, ~+~, ~-~, ~*~ or ~/~ is
numeric, and the property is coerced with
~(string-to-number (or ACCESSOR "0"))~.  The coercion propagates down, so
a reference nested inside an arithmetic expression is coerced too.  A
property nothing set therefore reads as zero rather than as an error.

Motivation: what have I been over more than three times?

#+begin_src org
,* Reviewed more than three times
  :PROPERTIES:
  :AGENT_QUERY:  (> $REVIEWS 3)
  :AGENT_VIEW:   list
  :AGENT_FORMAT: REVIEWS
  :END:
#+end_src

renders

#+begin_example
- [[id:rewrite-exporter][Rewrite the exporter]] 5
- [[id:ship-0-1][Ship 0.1]] 9
#+end_example

#+texinfo: @subheading Name position

The first argument of ~property~, ~property-ts~ and ~property-resolved~
is a property /name/, not a value, and a reference there denotes the name
string.  This is what lets you write the name once, in the same spelling
you use everywhere else, and still reach a predicate's keyword arguments.

Motivation: everything whose next review falls in the next month.

#+begin_src org
,* Reviews due within the month
  :PROPERTIES:
  :AGENT_QUERY:  (property-ts $NEXT_REVIEW :from -7 :to 30)
  :AGENT_VIEW:   list
  :AGENT_FORMAT: NEXT_REVIEW
  :END:
#+end_src

renders

#+begin_example
- [[id:rewrite-exporter][Rewrite the exporter]] 2026-09-01
- [[id:audit-prefilter][Audit the prefilter]] 2026-08-25
- [[id:renew-passport][Renew the passport]] 2026-08-21
#+end_example

Only the /first/ argument of those three predicates is a name position.
=(property $OWNER "johnw")= is =(property "OWNER" "johnw")=, but
=(property "STATUS" $STATUS)= is refused: the value argument is not a
position the expander has a reading for.  See
[[*Limitations of the query layer]].

A known org-ql predicate holding no reference in one of these positions is
passed through untouched, whatever its arguments are.  That is what keeps
this layer from being able to break a query that does not use it.

** The two axes
:PROPERTIES:
:DESCRIPTION: $NAME* is the outline, $NAME^ is the prototype chain.
:END:

#+cindex: axis, outline
#+cindex: axis, prototype
#+cindex: @samp{$NAME*}, outline axis
#+cindex: @samp{$NAME^}, prototype axis
#+cindex: inheritance, outline versus prototype
There are two ways a value can reach an entry that does not spell it, and
this package gives each a spelling of its own:

#+attr_texinfo: :table-type table :indic asis
- (no suffix) ::
  The entry's own drawer, and nothing else.  ~$URL~ is
  ~(property "URL")~, which is org-ql reading the drawer.

- ~*~ --- the outline axis ::
  ~org-entry-get~ with its INHERIT argument, so an ancestor's value
  answers, and so do a =#+PROPERTY:= keyword and ~org-global-properties~.
  This is Org's own property inheritance, unchanged.

- ~^~ --- the prototype axis ::
  The entry, then its =:PROTOTYPE:= chain nearest hop first, then the
  registry's =:ATTR_DEFAULT:=, then nothing.  See
  [[*The resolution order]] for the order in full.

They are two axes and not two settings of one, because containment is not
inheritance.  A task filed under a project is not a kind of project.  A
query has to say which relation it means, and the difference is not
academic --- asked along the two axes over the same corpus, the same
question gives two answers with no entry in common.

Motivation, along the outline: everything actionable inside a project I
own, where ownership is written once on the project.

#+begin_src org
,* Anything johnw owns, by containment
  :PROPERTIES:
  :AGENT_QUERY:  (and (todo "TODO") $OWNER*)
  :AGENT_VIEW:   list
  :END:
#+end_src

#+begin_example
- [[id:rewrite-exporter][Rewrite the exporter]]
- [[id:audit-prefilter][Audit the prefilter]]
#+end_example

The two entries under =Projects=, which is where =:OWNER:= is written.

Now the same question along the other axis, over the same corpus:

#+begin_src org
,* Owner resolved through the prototype
  :PROPERTIES:
  :AGENT_QUERY:  (equal $OWNER^ "johnw")
  :AGENT_VIEW:   list
  :END:
#+end_src

#+begin_example
- [[file:…/corpus.org::*Projects][Projects]]
- [[id:audit-prefilter][Audit the prefilter]]
- [[id:collect-print][Collect the print]]
#+end_example

Three matches, and not one of them is in the first answer's set of two.
=Projects= spells =:OWNER:= in its own drawer.  The other two reach it
through a chain of masters.  =Rewrite the exporter=, which the outline
query found, does not match here, because the prototype axis does not walk
the outline.  Reversing that --- one entry answering both --- would take an
entry that is both filed under an owning project and given an owning
master.

#+cindex: suffix, on a property reference
At most one suffix is read.  ~$~, ~$*~, ~$N*^~ and ~$N^*~ name no property
or no axis, and rather than being read as something almost right they are
refused by name:

#+begin_example
org-agents: no expansion for ‘$N*^’ in ‘$N*^’
#+end_example

The reason for refusing rather than guessing is worth knowing, because it
is the shape of every refusal in this package.  Reading ~$*~ as a
reference would hand ~org-entry-get~ the empty name, which answers nil at
every entry; reading ~$N*^~ as one would name a property whose key holds a
~^~, which no drawer spells.  Either way you would have an agent that
matches nothing with nothing said about why.

One asymmetry between the axes will meet you, and it is real rather than
an oversight.  In boolean position the prototype axis expands to
~(property-resolved NAME)~, which is a predicate, so the gate admits it
without a word.  The outline axis expands to ~(org-entry-get nil NAME t)~,
which is a function call, so it is residual Lisp and you are asked about
it once.  See [[*The structural gate]].  The two axes also behave
differently in the prefilter; see [[*Inheritance and pushability]].

** Entry specials
:PROPERTIES:
:DESCRIPTION: The seven references that name the entry rather than a property.
:END:

#+cindex: special, entry
#+cindex: @samp{$ITEM}, entry special
#+cindex: @samp{$TODO}, entry special
#+cindex: @samp{$PRIORITY}, entry special
#+cindex: @samp{$TAGS}, entry special
#+cindex: @samp{$CATEGORY}, entry special
#+cindex: @samp{$LEVEL}, entry special
#+cindex: @samp{$FILE}, entry special
Seven names refer to the entry itself rather than to a row of its property
drawer.  They exist because the obvious spelling does not work:
=(property "TODO")= is a perfectly valid query that never matches
anything, since no drawer holds a =:TODO:= line.  A special is expanded to
an accessor instead:

#+attr_texinfo: :table-type table :indic code
- $ITEM ::
  ~(org-get-heading t t t t)~ --- the heading text, without TODO keyword,
  priority cookie, tags or comment marker.
- $TODO ::
  ~(org-get-todo-state)~.
- $PRIORITY ::
  ~(org-entry-get nil "PRIORITY")~.
- $TAGS ::
  ~(org-get-tags)~ --- a list of strings, not a string.
- $CATEGORY ::
  ~(org-get-category)~.
- $LEVEL ::
  ~(org-current-level)~ --- a number.
- $FILE ::
  ~(buffer-file-name)~.

Three things follow from that table.

A special manages its own type.  In numeric position it is /not/ wrapped
in ~string-to-number~, because ~org-current-level~ already answers with a
number: =(< $LEVEL 3)= expands to =(< (org-current-level) 3)=.  In value
position it is not wrapped in ~(or … "")~ either, so ~$TAGS~ reaches
~member~ as the list it is and ~$TODO~ can be compared against nil.

A suffix on a special is /ignored/, not refused: ~$ITEM~, ~$ITEM*~ and
~$ITEM^~ all expand to ~(org-get-heading t t t t)~.  There is nothing to
inherit and nothing for a prototype to carry, so there is no reading for a
suffix to have; it is dropped silently rather than diagnosed, which is the
one place in this layer where a spelling that means nothing is not named.

The seven accessors are a closed set of read-only readers of the entry at
point, so a query is no less safe for holding one, and a bare special
passes the structural gate unremarked.

Motivation: headings that mention Tinderbox, wherever they are.

#+begin_src org
,* Headings that mention Tinderbox
  :PROPERTIES:
  :AGENT_QUERY:  (string-match "Tinderbox" $ITEM)
  :AGENT_VIEW:   list
  :END:
#+end_src

#+begin_example
- [[id:tinderbox-notes][Tinderbox notes]]
#+end_example

Here too, prefer org-ql where org-ql has an answer.  ~heading~, ~todo~,
~tags~, ~level~, ~priority~ and ~category~ are all predicates, and a
predicate is admitted without a prompt and may narrow the file set; a
special is for when you need the value inside an expression, as
~$ITEM~ is needed above and ~$TAGS~ is needed in
=(member "emacs" $TAGS)=.

** The property-resolved predicate
:PROPERTIES:
:DESCRIPTION: The prototype-aware property, and when to reach for it.
:END:

#+cindex: @samp{property-resolved}, query predicate
#+findex: org-agents-resolve-property
This package defines one org-ql predicate:

#+begin_example
(property-resolved NAME &optional VALUE)
#+end_example

It answers non-nil when the entry /resolves/ NAME --- or resolves it to
VALUE --- along the prototype axis: the entry's own drawer, then its
=:PROTOTYPE:= chain, then the registry's =:ATTR_DEFAULT:=.  VALUE is
compared with ~string-equal~, case-sensitively, and the argument order is
org-ql's own ~property~.

It exists because org-ql's ~property~ cannot see such a value, and no
amount of configuration makes it.  The plain ~(property NAME)~ and
~(property NAME VALUE)~ forms read the entry's own drawer, which is
exactly what a =:NAME:= line in the file is; a value that arrives through
a master is written in another file entirely, and the inheriting entry
spells nothing at all.

Motivation: everything blocked, however it came to say so.

#+begin_src org
,* Blocked, however it says so
  :PROPERTIES:
  :AGENT_QUERY:  (property-resolved "STATUS" "blocked")
  :AGENT_VIEW:   list
  :END:
#+end_src

#+begin_example
- [[id:audit-prefilter][Audit the prefilter]]
#+end_example

=Audit the prefilter= spells no =:STATUS:= at all.  Its
=:PROTOTYPE: Blocked Task= resolves to =blocked= through the chain.
=(property "STATUS" "blocked")= matches nothing here, and ~grep~ over the
corpus for =blocked= finds only the registry.  Those are the two cases to
reach for this predicate for --- a value that arrives through a chain, and
one that comes from a registry default.  Where the value is in the entry's
own drawer, ~property~ answers and is cheaper.

The sugar covers only half of this predicate.  In boolean position
~$STATUS^~ expands to =(property-resolved "STATUS")=, the existence form;
there is no reference spelling for the value form.  So write the predicate
--- and prefer writing it to the equivalent Lisp even where the sugar
would serve.  =(property-resolved "OWNER" "johnw")= is a predicate call,
so it is admitted without a prompt and it can narrow the file set, while
=(equal $OWNER^ "johnw")= is residual Lisp and does neither.  The sugar is
a convenience; the predicate is the interface.

Two diagnostics you may meet.  The predicate's arity is checked before any
entry is examined, because it carries no normalizer and therefore has
nothing to swallow a stray keyword argument with:

#+begin_example
org-agents: ‘property-resolved’ takes a property name and an optional
value, both strings: ‘(property-resolved "STATUS" :inherit t)’
#+end_example

And a prototype chain that loops is reported rather than signalled from
inside a predicate body, once per update, naming the hops --- a
~user-error~ raised inside org-ql's generated matcher would abort the
whole update.  For a caller in Lisp,
~org-agents-resolve-property~ signals on a cycle and
~org-agents-resolve-property-quietly~ reports one; see
[[*Functions for Lisp callers]].

For what "resolves" means, hop by hop, see [[*The resolution order]]; for
what it costs, see [[*Reads are virtual]].

** Putting a query in a property drawer
:PROPERTIES:
:DESCRIPTION: One line, and what Org does to it on the way in.
:END:

#+cindex: @samp{AGENT_QUERY}, agent property
#+cindex: property drawer, a query in a
#+findex: org-ql-defpred
An Org property value is a single line, and =:AGENT_QUERY:= is an Org
property value.  Keep the query on one line.

#+begin_src org
,* Up for review
  :PROPERTIES:
  :AGENT_QUERY: (and (todo "TODO") (property "NEXT_REVIEW"))
  :END:
#+end_src

Four things about that one line are worth knowing, because each of them
can turn a query you wrote into something you did not.

A property line written with nothing after it reads as absent, not as
empty.  =:AGENT_QUERY:= alone is an entry with no query, and you get
=No :AGENT_QUERY: at point= rather than a diagnosis about unreadable
text.  The same rule applies to every agent property: written-but-empty
and not-written mean the same thing.

Org reads the literal value =nil= as no value at all.  So
=:AGENT_VIEW: nil= is an agent with no view, which takes the default,
rather than an agent whose view is refused.

Text that will not read as a Lisp form is diagnosed as itself, naming
what was read and what ~read-from-string~ said about it:

#+begin_example
org-agents: unreadable :AGENT_QUERY: ‘(and (todo)’: End of file during parsing
#+end_example

#+cindex: continuation, of a property value
A =:AGENT_QUERY+:= continuation line /is/ read.  ~org-entry-get~ joins
the pieces with ~org--property-get-separator~ --- a space, unless
~org-property-separators~ says otherwise --- so a query split at a
whitespace boundary does read back as the query you meant.  It is still a
bad idea.  Split anywhere else and the pieces join into a different sexp,
or into one that will not read at all, and nothing about the drawer says
which happened.

Where a query genuinely will not fit on a line, the answer is not to
continue it but to name it.  Define a predicate of your own with
~org-ql-defpred~ in your init file and call it from the drawer: the
drawer then holds =(and (todo "TODO") (my-stalled-p))=, the definition
lives in a file you wrote, and the query stays a predicate call, which is
what the gate admits without asking.  Note the other half of that
bargain: a predicate you define is a predicate the gate now admits by
name, and org-ql runs its normalizer when it compiles a query.  See
[[*Refused heads]].

** Limitations of the query layer
:PROPERTIES:
:DESCRIPTION: What the sugar cannot express.
:END:

The =$PROP= layer is a rewrite over four positions, and it is worth
knowing where it stops.

A property name in a reference is a literal.  Nothing computes one, and
there is no spelling for "the property this other property names".

The two axes cannot be composed.  At most one suffix is read, so there is
no way to ask for "an ancestor's resolved value" or "a master's inherited
value" in the sugar.  Where you want a combination, write the Lisp
yourself, and write it with ~org-agents-resolve-property-quietly~ rather
than the signalling resolver: residual Lisp runs at every candidate entry,
and a ~user-error~ from inside org-ql's generated matcher aborts the whole
update.

A reference is expanded only in the four positions.  Inside any other
known predicate's argument list it is refused by name rather than read as
a value:

#+begin_example
org-agents: no expansion for ‘$TOPICS’ in ‘(tags $TOPICS)’
org-agents: no expansion for ‘$STATUS’ in ‘(property "STATUS" $STATUS)’
#+end_example

That is deliberate, and it is the safe direction: an argument silently
read the wrong way is an agent that matches the wrong thing.  Where you
want a property's value as an argument, put the predicate's job into Lisp
--- =(member "emacs" (split-string $TOPICS))= rather than
=(tags $TOPICS)=.

A suffix on an entry special is ignored rather than diagnosed.  See
[[*Entry specials]].

The layer covers the query and nothing else.  =:AGENT_FORMAT:= and
=:AGENT_COLUMNS:= take bare property names, and both read with
~org-entry-get~ at the match with no inheritance and no resolution --- so
a format naming =OWNER= is empty for a match that inherits it from an
ancestor or a master, even where the query that found the match read it
along one of those axes.  See [[*Formats]] and [[*The table view]].

* What is evaluated, and what is refused
:PROPERTIES:
:DESCRIPTION: The gate: what runs unremarked, what asks, what is refused.
:END:

#+cindex: gate, the evaluation
#+cindex: safety
#+cindex: trust
#+cindex: arbitrary Lisp in a query
#+cindex: residual Lisp
An org-ql query is Lisp, and org-ql evaluates the Lisp in it at every
candidate entry.  A query you type at a prompt is your own Lisp and needs
no ceremony.  A query read out of a property drawer is code read out of a
file, and a file may have arrived from anywhere --- a colleague, a
mailing-list attachment, a repository you cloned to read.

This chapter says exactly what runs without a word, what you are asked
about, what is refused whatever you answer, and how a decision you made
once is remembered.  A reader who finishes it should be able to look at a
file someone sent them and decide whether to update its agents.

** Why a gate exists
:PROPERTIES:
:DESCRIPTION: A query out of a drawer is code out of a file.
:END:

org-ql compiles a query into a predicate function and tests it with point
at each candidate heading.  Any part of the query that is not a predicate
call is compiled in as it stands, so it runs once per candidate entry with
whatever privileges Emacs has.  Over a corpus scope that is thousands of
files and hundreds of thousands of entries.

A query built only out of org-ql's predicates is a different kind of
thing.  What it can do is bounded by what those predicates do, which is
read Org buffers and answer yes or no --- with one exception, which has a
node of its own in [[*Refused heads]].  The gate's whole job is to tell
those two kinds apart: to let the first run without interrupting you, and
to put the second to you before it runs.

It is not a sandbox, and it does not try to be.  Nothing here analyses
what a piece of Lisp would do if it ran; the distinction drawn is
structural, and everything that falls on the wrong side of it is handed to
you to decide.  What the gate buys is that you are asked, once, with the
form printed in front of you --- and that a decision you make is
remembered and reviewable.

** The structural gate
:PROPERTIES:
:DESCRIPTION: What passes without a word, and what the gate is shown.
:END:

#+cindex: structurally safe query
A form passes the structural gate when it is built only out of:

- known org-ql predicates --- built-in, their aliases, and any defined
  with ~org-ql-defpred~, including this package's ~property-resolved~;
- the combinators ~and~, ~or~, ~not~, ~when~ and ~unless~, and the
  relational predicates ~parent~, ~ancestors~, ~children~ and
  ~descendants~;
- literals in argument position;
- quoted data, which is returned rather than evaluated, whatever it
  holds;
- the seven accessor forms a bare entry special expands to.

Every argument must answer for itself, because org-ql evaluates a
predicate's arguments as Lisp too.  =(tags (shell-command "x"))= is a
predicate call with a predicate's name on it and does not pass.  A dotted
list fails closed.  A list whose first element is not a symbol is the data
it looks like --- which is how org-ql's own =(src :regexps ("defun"))= is
written --- unless that first element is itself callable, since a
byte-code object reads in from a property drawer like any other text.

#+vindex: org-agents-exclude
What the gate is shown is the /form/, not the query.  ~org-agents-exclude~
is conjoined in first, so a query written

#+begin_example
(> $REVIEWS 3)
#+end_example

reaches the gate --- and org-ql --- as

#+begin_example
(and (> (string-to-number (or (org-entry-get nil "REVIEWS") "0")) 3)
     (not (property "AGENT_MATCH")))
#+end_example

One function says what that form is, so the form that is gated, the form
that is hashed and the form that is evaluated cannot come to mean
different things.  A gate that judged the query alone would have you
approving a form nobody had been shown.

Here is how a handful of real forms are classified.  The expanded form is
what is judged, so the reference layer's position rules decide this as
much as anything you wrote:

#+begin_example
passes  (and (todo "TODO") (property "NEXT_REVIEW"))
passes  (property-resolved "STATUS" "blocked")
passes  (org-get-heading t t t t)                          <- $ITEM
passes  (and (todo) (org-get-todo-state))                  <- $TODO
asks    (org-entry-get nil "OWNER" t)                      <- $OWNER*
asks    (string-match "github" (or (org-entry-get nil "URL") ""))
asks    (> (string-to-number (or (org-entry-get nil "REVIEWS") "0")) 3)
#+end_example

#+vindex: org-ql-ask-unsafe-queries
What "asks" means depends on where you are.  Interactively you get one
~yes-or-no-p~ with the whole form printed in the prompt.  In batch, or
under ~inhibit-interaction~, there is nobody to ask, so the query is
skipped with a message naming it and the update reports
=query not approved=:

#+begin_example
org-agents: skipping unapproved query (and (string-match "github" (or
(org-entry-get nil "URL") "")) (not (property "AGENT_MATCH")))
#+end_example

And if org-ql's own ~org-ql-ask-unsafe-queries~ is nil, nothing is asked
and the form runs.  That variable is org-ql's and it governs whether you
are asked; setting it to nil turns off the prompting in this package as
well.  A refusal is not affected by it (see [[*Refused heads]]).

The text you are shown is a function of the form and of nothing else.
Every printer variable that could change it is bound while it is printed
--- ~print-length~ and ~print-level~ to nil so nothing is elided,
~print-escape-newlines~ so a string in the query cannot break the prompt
into lines and push the interesting conjunct off the top of the window,
~print-gensym~ so an uninterned symbol cannot share text with the
interned symbol of the same name.  What you read is what is hashed.

** Remembered approvals
:PROPERTIES:
:DESCRIPTION: The hash, where it is kept, and what invalidates it.
:END:

#+cindex: approval, of a query
#+cindex: hash, of a query
#+cindex: SHA-1
#+cindex: session approval
#+vindex: org-agents-safe-queries
#+vindex: custom-file
Say yes to a prompt and the decision is remembered, keyed on the SHA-1 of
the printed form.  There are two records.  The session table holds it
until Emacs is restarted.  ~org-agents-safe-queries~ holds it across
sessions, as a list of =(HASH . TEXT)= conses where TEXT is the very text
the hash was taken of --- so a stored approval can afterwards be read for
what it is rather than taken on trust.

You are offered the permanent record only where customize has a file to
write.  ~customize-save-variable~ writes to the file =(custom-file t)=
names, which answers nil, and writes nothing, unless ~user-init-file~ is
set.  Where your real init is an Org file that you tangle,
~user-init-file~ is the tangled output and a saved approval is overwritten
the next time it is generated.  Set ~custom-file~ to a file of its own, or
every approval you make is a session approval.  Emacs says so when it
happens:

#+begin_example
org-agents: ‘org-agents-safe-queries’ changed for this session only;
customize has no file to save it in
#+end_example

#+vindex: org-agents-exclude
Editing ~org-agents-exclude~ invalidates every approval you hold.  That
follows from the gate being shown the form: the exclusion is part of the
form, so changing it changes the text, and therefore the hash.  Measured
over the same query with the default exclusion and with a different one:

#+begin_example
(and (> (string-to-number (or (org-entry-get nil "REVIEWS") "0")) 3)
     (not (property "AGENT_MATCH")))
    8c7df326f437dfec6f233c25527319074d1a9fe1

(and (> (string-to-number (or (org-entry-get nil "REVIEWS") "0")) 3)
     (not (tags "alias")))
    0fc9c317d66ac204ff69d4b677b44d9df985c7ef
#+end_example

(A form is printed as one line, and hashed as one line; the forms above
are wrapped only to fit the page.)

This is the behaviour you want.  An approval names a form, and you were
shown a form; being asked again after the form changed is the fail-safe
direction.  A /refusal/ is deliberately not invalidated by it; see
[[*Refused queries]].

A hash identifies one printed form and not a query up to meaning.
=(and (todo) (property "URL"))= and =(and (property "URL") (todo))= ask
the same question and hash differently:

#+begin_example
(and (todo) (property "URL"))    79a5340c2ae90ab017c6cb55cc2db16adadd6526
(and (property "URL") (todo))    a5282dd174fe90eeae4ddd8e0f5297cceaae2029
#+end_example

So an approval is narrow, which is the right way for an approval to be
wrong: reordering a query costs you one more prompt.  Where what you want
to allow or forbid is a /predicate/ rather than a particular query, the
instrument is ~org-agents-refused-heads~ and not a hash.

#+vindex: org-agents-safe-queries
#+vindex: org-agents-refused-queries
Both records are marked risky, and so is the session table.  That is not
hygiene.  Either record /is/ what the gate consults, the default exclusion
is published, and the hash of a form is computable offline --- so a file
able to set one of them could pre-approve its own arbitrary Lisp and never
be asked about it.  Marked risky, Emacs asks you before a file-local value
is applied.

** Refused heads
:PROPERTIES:
:DESCRIPTION: A predicate whose name is not a question.
:END:

#+cindex: refused head
#+cindex: normalizer, org-ql
#+vindex: org-agents-refused-heads
~org-agents-refused-heads~ is a list of predicate heads this package will
not hand org-ql, whatever else says.  It is consulted /first/: before
structural safety, before the safe list, before any remembered approval,
and ~org-ql-ask-unsafe-queries~ does not override it.  The switch governs
whether you are asked, and a head on this list is not a question.

The reason such a list is needed is that a head with no dangerous
argument of its own can still be dangerous.  What a predicate head vouches
for is its own name.  org-ql runs each predicate's /normalizer/ when it
compiles a query --- after the gate has admitted the head, and before any
entry is examined --- and a normalizer is arbitrary code from wherever
that predicate was defined.

The default value lists one head, ~semantic~, and it is a shipped example
rather than a placeholder.  =org-ql-semantic.el= defines it with a normalizer
that calls ~org-ql-semantic--ensure-cache~, which ~call-process~-es
=org db search=.  Structurally =(semantic "x")= is a predicate call like
any other, so the structural gate admits it without a prompt and the
subprocess runs.  A refused head is where such a predicate goes.

#+begin_example
org-agents: ‘semantic’ is refused by ‘org-agents-refused-heads’
#+end_example

Three properties of the matching are worth stating.  It is by literal
symbol, so an alias of an IO-bearing predicate has to be listed as well as
the predicate.  It descends every cons cell, so a refused head is reported
wherever it appears --- in argument position, under a nested query, not
only as the head of the whole form.  And unlike the structural check it
does not exempt quoted data: =(quote (semantic "x"))= is refused too.
That fails closed, and the shape it costs is one nobody writes on purpose,
while what failing open costs is a subprocess.

A refused head outranks an approval.  A query you approved last week whose
head you add to this list today is refused today, with no need to hunt
down the approval.

** Refused queries
:PROPERTIES:
:DESCRIPTION: Saying no to one form, permanently.
:END:

#+cindex: refusal, of a query
#+vindex: org-agents-refused-queries
~org-agents-refused-queries~ is the negative twin of the approval record,
with the same =(HASH . TEXT)= shape, so one listing can show an approval
and a refusal side by side.  A form whose hash is there is refused before
the safe list is consulted and before ~org-ql-ask-unsafe-queries~ is
looked at, and the refusal outlives the session that made it:

#+begin_example
org-agents: this query is refused; see ‘org-agents-refused-queries’
#+end_example

Manage it through the listing rather than by hand; see
[[*Reviewing what you approved]].

Approval and refusal are keyed on the same hash and looked up differently,
because their fail-safe directions are opposite.  An approval that stops
matching asks again.  A refusal that stops matching /runs/.  So an
approval names the whole form and nothing else, while a refusal is looked
up for the form /and/ for the query inside it --- and refusing through the
listing records both entries where the form was built by appending the
exclusion.  The consequence is the one you want: editing
~org-agents-exclude~ invalidates every approval and lifts no refusal.
Verified both ways round: a form refused through the listing under the
default exclusion is still refused after the exclusion has been edited,
while an approval of the same form is not honoured after the same edit.

A hand-written entry covers only the exact form it names, and a hash
covers one printed form.  A refusal of =(and (todo) (evil))= does not
cover =(and (evil) (todo))= or =(and (and (todo) (evil)))=, which print
differently and hash differently.  Where what you object to is a
predicate, use ~org-agents-refused-heads~, which refuses it however the
query around it is spelled.

** Reviewing what you approved
:PROPERTIES:
:DESCRIPTION: The approvals listing, its keys, and how to read a file you were sent.
:END:

#+findex: org-agents-list-approvals
#+findex: org-agents-approvals-mode
#+cindex: approvals listing
The records the gate keeps are hashes, and a hash says nothing about what
it stands for.  ~org-agents-list-approvals~ pops
=*org-agents approvals*=, one row per remembered decision, with three
columns: the State, the first twelve characters of the Hash, and the Query
text that hash covers.

All three records are listed, the session table included.  A row reading
=approved (session)= was approved at a prompt and not saved; it is listed
and revocable exactly like a saved one, which matters because on a setup
where customize has no file to write /every/ approval is a session
approval.  A row written by an older version that recorded no text says
=(query text not recorded)= rather than showing an empty cell, and its
state is marked =(legacy)= --- nothing can recover the query such a hash
stood for.

The buffer is in ~org-agents-approvals-mode~, derived from
~tabulated-list-mode~, and its keys are:

- Key: d (org-agents-approvals-revoke) ::
  Forget the approval on this line, in this session and on disk.  On a
  refusal row this says
  =org-agents: this line is a refusal; ‘u’ lifts one=.

- Key: r (org-agents-approvals-refuse) ::
  Forget the approval and record the form as a refusal, which the gate
  consults before anything else and which no later approval undoes.
  Where the form carries the current exclusion, the query inside it is
  recorded too, so that editing the exclusion afterwards cannot lift the
  refusal.

- Key: u (org-agents-approvals-unrefuse) ::
  Lift a refusal.  The query goes back to needing approval, not to having
  it: lifting a refusal is not the same as saying yes.  On an approval row
  this says =org-agents: this line is an approval; ‘d’ forgets one=.

- Key: g (revert-buffer) ::
  Reread all three records.  The binding is ~special-mode~'s, and the
  buffer's ~revert-buffer-function~ is what does the rereading.

#+texinfo: @subheading Deciding whether to trust a file

Put together, that is enough to work through a file someone sent you.

Read the drawer first.  A query is one line and you can read it.  If it is
built only out of org-ql predicates and combinators, what it can do is
what those predicates do, and it will run without asking you --- so the
reading is the whole of your review.  Check the heads: a name you do not
recognise may be a predicate someone defined, and admitting a head admits
its normalizer.  Where you do not know a head, do not update the agent.

#+findex: org-agents-mode
If the query holds Lisp, you will be asked, once, with the form printed
whole.  Nothing is approved by opening the file, and nothing is approved
by turning on a minor mode.  ~org-agents-mode~ updates on save, which
means the prompt arrives when you save, not silently; and no save ever
spawns a prefilter.  Say no and the agent renders nothing and reports
=query not approved=.

#+cindex: Local Variables block
#+cindex: risky variable
Look at the rest of the file too.  A query is not the only thing an Org
file can carry.  A =Local Variables= block could try to set
~org-agents-safe-queries~ to pre-approve its own Lisp, or empty
~org-agents-refused-heads~ to remove the protection for every file read
afterwards in the session.  Every option this package defines is marked
risky for exactly that reason, so Emacs asks before applying one from a
file --- that protection is Emacs's rather than this package's, and it
depends on your answering those prompts as carefully as this one.

#+findex: org-agents-apply-actions
An =:AGENT_ACTION:= property is a separate question with a separate answer:
nothing runs it but ~org-agents-apply-actions~, typed, and that command
shows you every intended edit before it writes one.  See
[[*The dry run]].

Finally, {{{kbd(M-x org-agents-list-approvals)}}} after the fact.  If you approved
something you would rather not have, =d= forgets it and =r= makes sure you
are not asked again.

* Scope and the ripgrep prefilter
:PROPERTIES:
:DESCRIPTION: Where an agent looks, and what makes looking everywhere affordable.
:END:

#+cindex: scope
#+cindex: prefilter, ripgrep
An agent's scope says which files it reads.  Two of the five forms name
their files; the other three describe a set, and nothing about describing
a set bounds how much it holds.  This chapter is about the difference, and
about the optional ripgrep prefilter that makes the second kind
affordable.

One sentence to hold on to throughout: the prefilter chooses which files
org-ql opens, and can never change what matches.

** Scopes
:PROPERTIES:
:DESCRIPTION: The five forms of :AGENT_SCOPE:.
:END:

#+cindex: @samp{AGENT_SCOPE}, agent property
#+vindex: org-directory
#+vindex: org-agenda-files
=:AGENT_SCOPE:= takes one of five forms:

#+attr_texinfo: :table-type table :indic asis
- ~agenda~ ::
  #+cindex: @samp{agenda}, agent scope
  ~(org-agenda-files)~.  The default, and the one most agents want: it
  names its files, and it is the set you already keep curated.
- ~active~ ::
  #+cindex: @samp{active}, agent scope
  Every =.org= file below ~org-directory~, recursively, skipping any
  directory named =archive= and everything below it.
- ~all~ ::
  #+cindex: @samp{all}, agent scope
  Every =.org= file below ~org-directory~, recursively, archives
  included.
- a directory name ::
  #+cindex: directory, as an agent scope
  Any other bare value is read as a directory, expanded against
  ~org-directory~, and read recursively.  =.= is the corpus root itself.
- a list of file names ::
  #+cindex: file list, as an agent scope
  A value beginning with =(= is read as a Lisp list of file names ---
  =("corpus.org" "notes.org")= --- each expanded against
  ~default-directory~, which for an agent is the directory of the file it
  lives in.

The distinction that matters is between a scope that /enumerates/ its
files and one that /describes/ a set.  =agenda= and an explicit list
enumerate: the file names exist as a list before anything is read.
=active=, =all= and a directory describe: the only way to know what they
hold is to walk the tree.  That difference decides which scopes are
prefiltered ([[*Which scopes get narrowed, and why]]) and how an
unreadable file is reported
([[*A file the scope names but cannot open]]).  It also decides whether the
file set is stable between two updates: a described scope's walk can
intermittently drop a symlink to a file on this platform, and an
enumerating scope cannot.  See [[*Limitations of the prefilter]].

A scope that names no directory is refused, before anything is spawned, so
that a mistyped scope is diagnosed as one rather than as a prefilter
failure:

#+begin_example
org-agents: scope ‘nowhere’ names no directory (/Users/you/org/nowhere)
#+end_example

and a value that is neither a known name, a directory nor a list of
strings is named as the bad scope it is --- =:AGENT_SCOPE: (1 2)= gets
=org-agents: bad scope (1 2)= rather than a type error from further
along.  A scope that resolves to no files selects nothing; it does not
fall back to searching the buffer the agent lives in.

#+vindex: org-agents-files
#+findex: org-agents-update-all
~org-agents-files~ is a different thing and the two are easy to confuse.
A scope says which files one agent /reads/.  ~org-agents-files~ says which
files ~org-agents-update-all~ opens and /writes/.  See [[*By hand]].

** Which scopes get narrowed, and why
:PROPERTIES:
:DESCRIPTION: The measured cost of each kind of scope.
:END:

#+cindex: ripgrep
#+cindex: measurement, of a prefiltered scope
#+vindex: org-agents-prefilter
#+vindex: gc-cons-threshold
Only =active=, =all= and a directory scope are ever prefiltered.  =agenda=
and an explicit file list are always read live.  Both halves of that were
measured on the author's corpus rather than assumed.

For an enumerated scope, a prefilter is pure overhead.  Measured over the
eight largest files of that corpus, 8.9 MB and 373 matches: an
=agenda=-scope update costs 0.03 to 0.05 seconds once the buffers are
visited, and spawns no subprocess at all.  One ripgrep run over the whole
corpus costs 0.10 to 0.45 seconds.  Prefiltering a set that is already
small and already named makes the common case 5 to 25 times slower to
reach the same answer.

For a described scope the numbers are of a different kind.  Measured with
=(and (todo) (property "NEXT_REVIEW"))= over an =active= scope: one
ripgrep run narrows 3,634 files to 309 in half a second, and org-ql over
those 309 finishes in ten seconds with 764 matches over 316 buffers.  With
no prefilter at all, the same query had not finished after nine minutes.
The same experiment on a 3,669-file corpus narrowed to 314 files in 0.09
seconds of ripgrep and finished in 12 seconds.

Do not budget the unprefiltered path in seconds.  It is not a slower way
to the same place within one attention span; it is the thing the option
exists to avoid.  (Longer still at a low ~gc-cons-threshold~ --- past nine
minutes at the batch default --- since opening that many Org buffers makes
garbage faster than the default budget expects.)

Read those figures as an order of magnitude and not as a benchmark.
Machine load moves them: the package's own measurement of one ripgrep
census over one scope came out at 3.5 seconds on an idle machine and 12.8
on one busy with other work.  A figure outside a stated range is load
rather than a regression.

One sharpening that is /not/ implemented, so that you do not look for it:
there is no file-count ceiling above which a live walk is refused and
below which it is allowed.  The choice is per-scope-kind, not per-size.

** What the prefilter can and cannot do
:PROPERTIES:
:DESCRIPTION: One evaluation engine, and a candidate-file filter in front of it.
:END:

#+cindex: evaluation engine, the one
Evaluation is always org-ql's, against live buffers.  There is exactly one
evaluation engine and therefore exactly one answer.  ripgrep is a
candidate-/file/ prefilter: it chooses which files org-ql opens, and
nothing else.

That asymmetry sets the whole design.  Narrowing too little is merely
slow.  Narrowing too much is a wrong answer with no error at all --- an
agent that renders fewer matches than it has, and says nothing about it.
So a conjunct is pushed into ripgrep only where the files ripgrep answers
with are provably a /superset/ of the files org-ql's own matches could
come from, and whatever cannot be proven a superset stays residual.  See
[[*The push-down rules]].

ripgrep distinguishes "no file matches" from "I could not answer" by exit
status, and this package keeps the two apart.  An empty answer is an
answer: an agent over a corpus scope whose query genuinely matches nothing
renders zero matches, rather than reporting a broken prefilter.  Only a
real failure --- no executable, any exit status but 0 or 1, a death by
signal, an expired deadline --- means "no answer", and then the scope is
scanned live.  A failing run says so on its own account first, naming the
status and quoting whatever the program wrote to standard error:

#+begin_example
org-agents: /usr/local/bin/rg exited 2: …
#+end_example

Four conditions send a described scope down the live path, and each says
which it was:

#+begin_example
org-agents: scope ‘.’ not narrowed (prefiltering off); scanning 9 files live
org-agents: scope ‘.’ not narrowed (no pushable conjunct); scanning 9 files live
org-agents: scope ‘.’ not narrowed (ripgrep not found); scanning 9 files live
org-agents: scope ‘.’ not narrowed (ripgrep failed); scanning 9 files live
#+end_example

The file count is in the message because the slowness should be explained
rather than mysterious: on the author's corpus that walk is 3,634 files
and a query of 172 seconds, which is a shocking thing to happen without a
reason attached.

So: ~org-agents-prefilter~ changes what an agent costs and never what it
answers.  If you suspect it of changing an answer, set it to nil and
compare --- the two runs should agree, and a disagreement is a bug in this
package rather than a setting to be tuned.

** The push-down rules
:PROPERTIES:
:DESCRIPTION: Which conjuncts can narrow a file set, and what they compile to.
:END:

#+cindex: push-down, of a conjunct
#+cindex: superset argument
The analysis is in two layers on purpose.  The splitter decides /which/
conjuncts are superset-safe, in an abstract vocabulary; the emitter
decides /how/ ripgrep expresses one, or declines to.  A pattern that
cannot be written soundly is not written, and the conjunct then contributes
no narrowing --- slow and correct rather than fast and wrong.

Seven predicate heads can push:

#+begin_example
property   property-resolved   property-ts
scheduled  deadline   closed   heading
#+end_example

and only the top-level conjuncts of an ~and~ are considered --- or the
whole query, where it is a single pushable predicate.  A conjunct under
~or~ or ~not~, and every nested query, is residual by omission, which
widens the candidate set and is therefore safe.

Here is the splitter and the emitter over real queries, with the patterns
ripgrep is actually handed:

#+begin_example
(and (todo "TODO") (property "NEXT_REVIEW"))
    (property "NEXT_REVIEW")        ^[ \t]*:NEXT_REVIEW\+?:
(property "URL" "https://x")
    (property "URL" "https://x")    ^[ \t]*:URL\+?:[ \t]+https://x[ \t]*$
(and (scheduled :to "+7d") (property "OWNER"))
    (scheduled)                     SCHEDULED:[ \t]*<
    (property "OWNER")              ^[ \t]*:OWNER\+?:
(deadline :from -7 :to 7)
    (deadline)                      DEADLINE:[ \t]*<
(closed :on "2026-08-20")
    (closed)                        CLOSED:[ \t]*\[
(heading "Tinderbox")
    (heading "Tinderbox")           ^\*+(?-u:.)*Tinderbox
(heading "Ship it (finally)")
    (heading "Ship it (finally)")   ^\*+(?-u:.)*Ship it \(finally\)
(property-ts "NEXT_REVIEW" :from -7)
    (property "NEXT_REVIEW")        ^[ \t]*:NEXT_REVIEW\+?:
(and (property "OWNER" "a b") (todo))
    (property "OWNER")              ^[ \t]*:OWNER\+?:
(property "CATEGORY" "work")        nothing pushed
(or (property "URL") (property "LOCATION"))
                                    nothing pushed
(string-match "gh" (or (org-entry-get nil "URL") ""))
                                    nothing pushed
(heading "Café")                    conjunct pushed, no pattern emitted
#+end_example

Read that table with these rules in mind.

A property /name/ pushes as the existence of a drawer line, and the
=\+?= is exact rather than generous: Org looks up =:NAME:= and =:NAME+:=
and nothing else, and an entry whose drawer holds only
=:NEXT_REVIEW+: plusvalue= does match =(property "NEXT_REVIEW")=.

A property /value/ pushes only where one drawer line spells it.
~org-entry-get~ builds a value by joining the =:NAME:= line with every
=:NAME+:= line, separated by ~org--property-get-separator~, so a value
assembled from more than one line is spelled on no line of the file and a
line-oriented matcher cannot find it.  Where that cannot be argued ---
=(property "OWNER" "a b")= above --- the name arm is pushed instead, which
is wider and always sound.  Note what the rule is /not/: it is not a test
for whitespace.  With a separator of =/=, =:P: al= plus =:P+: pha= answers
=al/pha=, a value holding no whitespace that no single line spells.

A special property never pushes.  ~org-entry-get~ answers =CATEGORY=,
=TODO=, =DEADLINE= and the rest out of entry structure, and no drawer
holds a line for one, so pushing it would return no files at all for a
query that matches thousands.

A planning bound is never pushed, only the presence of the stamp: ripgrep
cannot compare dates.  So =(deadline)=, =(deadline :from -7 :to 7)=,
=(deadline 7)= and =(deadline auto)= all push the same thing, all soundly,
and org-ql applies the bound afterwards.  The opening bracket in the
pattern is not decoration --- an active timestamp begins with =<= and an
inactive one with =[=, and demanding it narrowed 216, 91 and 18 candidate
files down to 203, 76 and 3 over a 3,669-file corpus.

A ~heading~ argument is always a literal, never a regexp: org-ql
normalizes ~heading~ to ~heading-regexp~ with every argument
~regexp-quote~-d.  The emitter therefore quotes for ripgrep's Rust dialect
instead --- note =\(finally\)= above, where an Emacs-style quoting would
have left the parentheses as grouping and demanded the text
=Ship it finally=.  The splitter refuses one character in a heading
literal and only one: =]=.  ~org-get-heading~ does not return a slice of
the line --- it reassembles it from the groups of a regexp --- and the only
substring org-ql can match that the raw line need not spell is one
crossing the junction between a priority cookie and the title.  Every such
substring holds the cookie's closing =]=.  (The emitter has refusals of its
own, over any literal; see [[*Limitations of the prefilter]].)  Several
literals of one ~heading~ are emitted as several patterns and
/intersected/, because org-ql requires all of them in one heading.

The authority for all of this is ~org-agents--pushdown-fns~ in the source,
whose every row states its own superset argument.  One warning for anyone
reading the repository's design notes: =docs/design.md= carries a
push-down table describing a PostgreSQL prefilter this package no longer
has, and its per-row justifications are facts about SQL operators that no
longer run.  Extending the rules on those arguments can push something
ripgrep cannot see, which drops files with no error.

** Inheritance and pushability
:PROPERTIES:
:DESCRIPTION: What a broad inheritance setting costs, and the one exception.
:END:

#+vindex: org-use-property-inheritance
A broad ~org-use-property-inheritance~ --- ~t~ most of all --- makes no
~property~ or ~property-ts~ conjunct pushable at all.  An agent built only
out of those then falls back to its scope's whole file set: still correct,
and much slower.  Measured, with the option at ~t~:

#+begin_example
(and (todo "TODO") (property "NEXT_REVIEW"))    nothing pushed
#+end_example

So the prefilter's value depends on keeping inheritance narrow.  If you
have an agent over a corpus scope that is unaccountably slow, that option
is the first thing to look at.

Two honest notes about that guard.  It is conservative rather than
required: org-ql applies the ~org-use-property-inheritance~ default only
to a ~property~ form that carries an extra plist, and the plain
=(property NAME)= and =(property NAME VALUE)= forms --- the only two that
are ever pushed --- read the entry's own drawer, which is exactly what a
=:NAME:= line is.  The guard is kept anyway, because org-ql's own
~property~ docstring reads the other way, and if a future org-ql made that
true of the plain forms this guard is the only thing between that change
and a silent wrong answer.

#+cindex: @samp{property-resolved}, and the prefilter
~property-resolved~ is the deliberate exception, and it stays pushable at
every setting:

#+begin_example
(property-resolved "OWNER")   (?:^[ \t]*:OWNER\+?:|^[ \t]*:PROTOTYPE\+?:)
#+end_example

Two things there.  The resolver never reads
~org-use-property-inheritance~ and never passes an INHERIT argument, so
that option cannot change what the predicate answers --- keeping the guard
would be a pure loss of narrowing.  And the pattern is /widened/: the
local =:NAME:= line OR a =:PROTOTYPE:= line, as one alternation.  It has
to be.  An entry that resolves a name through a master never spells the
value, so the ordinary pattern would drop its file with no error, which is
the one failure mode this package must not have.  (The alternation is one
pattern rather than two on purpose: several patterns of one conjunct are
intersected, so two would mean "spells =:NAME:= AND carries
=:PROTOTYPE:=" --- catastrophically narrow, and silent.)

#+cindex: @samp{ATTR_DEFAULT}, and the prefilter
That widening has an exception of its own, and it is where a declared
default meets a query.  With an =:ATTR_DEFAULT:= declared that the query
could match, an entry spelling /neither/ line resolves the name too --- so
nothing can narrow, and the conjunct stays residual.  Measured against a
registry declaring =STATUS= with =:ATTR_DEFAULT: active=:

#+begin_example
(property-resolved "STATUS" "blocked")
    (?:^[ \t]*:STATUS\+?:[ \t]+blocked[ \t]*$|^[ \t]*:PROTOTYPE\+?:)
(property-resolved "STATUS" "active")     nothing pushed
(property-resolved "OWNER")               pushed  (OWNER declares no default)
#+end_example

=blocked= is not the declared default, so only an entry that spells a
line can answer it and the alternation is sound.  =active= is the
declared default, so every entry in the corpus resolves =STATUS= to
something the query matches, and no file can be excluded.  The exception
costs narrowing and never an answer.  For the resolution order this rests
on, see [[*The resolution order]]; for the wider price of virtual
resolution, [[*Reads are virtual]].

** Bounding a run
:PROPERTIES:
:DESCRIPTION: org-agents-prefilter, org-agents-rg-executable, org-agents-rg-timeout.
:END:

#+vindex: org-agents-prefilter
Three options govern the prefilter.

~org-agents-prefilter~ takes one of three values.  ~auto~, the default,
uses ripgrep where the executable is found and the query offers a conjunct
to push, and otherwise scans live with the message naming the reason and
the file count.  nil never runs ripgrep.  ~require~ refuses an unbounded
scope that cannot be narrowed, rather than scanning it live:

#+begin_example
org-agents: scope ‘.’ cannot be narrowed (no pushable conjunct) and
‘org-agents-prefilter’ is ‘require’; for live evaluation set it to
‘auto’, or use ‘agenda’ or an explicit file list
#+end_example

#+findex: org-agents-check-attributes
That is for someone who would rather be told an agent cannot be answered
affordably than wait for a live walk of the corpus.  ~require~ refuses a
/query/, and one caller is deliberately outside it:
~org-agents-check-attributes~ scans live rather than refusing, with the
same message naming the file count, because a lint that declined to run
would be failing its own contract rather than declining an expense on your
behalf.  See [[*Checking a corpus]].

#+vindex: org-agents-rg-executable
~org-agents-rg-executable~ names the program, resolved with
~executable-find~, so a bare name is looked up on ~exec-path~.  ripgrep 13
or later is wanted: the prefilter passes =--crlf=, without which a value
pattern cannot match in a file with CRLF line endings.  Every flag was
verified against 15.2.0 and against no other version; 13 is named as a
round, safely old floor.

One thing that program will /not/ see: =RIPGREP_CONFIG_PATH= is unset for
the child, and that is a soundness requirement rather than tidiness.
ripgrep prepends every argument in that file to its command line, and the
vector this package builds overrides only the flags it repeats.  Measured,
with a config file holding one line: under =--max-depth=1= a matching file
one directory down is not reported, and under =--max-filesize=10= nothing
is reported at all and ripgrep exits 1 --- which is correctly read as "an
answer, and no file matches", so every agent renders nothing with no error
and no message.  A personal ripgrep default is the mechanism ripgrep's own
documentation recommends, and it would silently empty every unbounded
agent.

#+vindex: org-agents-rg-timeout
#+kindex: C-g
~org-agents-rg-timeout~ is the number of seconds to wait for one run, or
nil for no bound.  A bound is needed because nothing else provides one: on
an unresponsive filesystem --- NFS, sshfs, a sleeping disk --- or under
=--follow= over a pathological symlink arrangement, a run can take
arbitrarily long.

A timer cannot rescue one, and that is why this is a deadline over an
asynchronous process rather than a timer over a synchronous call.
Measured: a ~run-at-time~ set before a ~call-process~ to a hanging child
never fires, because Emacs runs no timers while blocked there; one set
before a loop over ~accept-process-output~ fires at +0.57 s.
=timeout(1)= was the other candidate and was rejected twice over ---
=/usr/bin/timeout= does not exist on stock macOS, and it bounds the /child/
rather than Emacs, so against a process in an uninterruptible disk wait,
which is the very case this is for, Emacs would stay blocked waiting for
=timeout= to reap something that will not die.

The default of 30 seconds is roughly fifty times the slowest run measured
for any pattern this package builds over a 3,649-file corpus: 0.564 s cold
and 0.068 to 0.083 s warm.  On expiry the run answers "unavailable", which
is what a missing ripgrep answers, so the scope is scanned live.  A
spurious expiry therefore costs a slow correct answer and never a wrong
one, which is what makes having a bound safe at all.  With the bound off,
{{{kbd(C-g)}}} is the only escape.

#+cindex: reentrancy, during a prefilter
#+cindex: timer, an idle
The new cost of an asynchronous wait is reentrancy, and it is worth stating
plainly rather than leaving to be met.  Waiting on a subprocess runs timers
and process filters, where ~call-process~ ran nothing, so an update may
execute an idle timer while its prefilter is in flight.  Two mitigations
cover most of it: an update of a =children= agent collects /outside/ its
~atomic-change-group~, so no timer's edits can land in this package's
change group, and no save spawns a prefilter at all.

What that does not cover: a =list= or =table= agent renders from Org's
dynamic-block writer, which Org calls after the block's body has already
been deleted.  The wait therefore happens with the block emptied, and an
idle timer that edits the buffer at that spot during the wait either has
its text glued into the freshly rendered body or loses it when the writer's
failure path puts the old body back.  Demonstrated with a one-second stub
and a 0.4 second timer: the timer ran, found the body already gone, and its
line came back inside the rendered item.  Hoisting that collect too would
mean parsing the block's parameters ahead of Org and matching its parser
exactly, which trades a narrow exposure for a silent divergence, so it is
not done.  {{{kbd(C-g)}}} escapes, and a corpus-scope agent updated by hand
is the only way to reach the wait at all.

All three options are marked risky, and the last two for concrete reasons:
~org-agents-rg-executable~ names a program that will be run as a
subprocess, and a file-local ~org-agents-rg-timeout~ of nil takes off the
bound this exists to provide while a file-local 0 expires every run and
sends every corpus-scope agent down the live whole-corpus walk.

** A file the scope names but cannot open
:PROPERTIES:
:DESCRIPTION: Refused for an enumerated scope, skipped for a described one, never silently.
:END:

#+cindex: unreadable file
A file that nothing can open is reported by this package rather than by
org-ql, and the two kinds of scope get different answers.

An explicit =:AGENT_SCOPE:= file list is a hard refusal, naming the files:

#+begin_example
org-agents: :AGENT_SCOPE: names 1 file(s) that cannot be read, so this
agent is not answered: …/notes.org
#+end_example

You named this file in this agent.  Rendering a smaller answer with
nothing to say it was smaller is the failure mode this package refuses
everywhere else.

=agenda=, a directory, =active= and =all= skip, with one message naming
the scope and the files:

#+begin_example
org-agents: scope ‘.’ names 1 file(s) that cannot be read; they are
skipped: …/.#agents.org
#+end_example

These describe a set rather than enumerating it --- ~org-agenda-files~ is
a list Org maintains and filters --- so one stale entry, or one
root-owned stray in the corpus, must not break every agent in the buffer.
At most five names are spelled out and the rest are counted, because the
usual case is one stale path and naming it is the whole point, while a
root-owned corpus could put thousands in one message.

Neither way is silent.  The message is the whole difference between a skip
and a drop.

What this replaced is worth knowing, because you may still meet it in an
older report.  Handed a file it cannot open, ~org-ql-select~ calls
~display-warning~, which /returns/ the warning text as a string; that
string is left in the list org-ql then maps ~buffer-name~ over, so the
diagnostic used to arrive as the payload of a type error ---
=Wrong type argument: bufferp, "Error (org-ql-select): Can not open file:
…"= --- and one bad path made every agent in the buffer fail with what
read like a bug in this package.

The test is =(or (file-readable-p f) (find-buffer-visiting f))= and both
halves are needed: measured, a file visited while readable and then
=chmod 000= has ~file-readable-p~ nil, ~find-buffer-visiting~ non-nil, and
org-ql over it works and returns its match.  This mirrors org-ql's own
rule rather than inventing a stricter one.  Its cost, measured over a
3,639-file =active= scope, is 0.465 seconds, against 0.265 for the
directory walk that produced the list and the ten-odd seconds org-ql then
spends opening those files --- so it is roughly twice the walk and
negligible against the read it precedes, which is the comparison that
matters.

This is a fallback-path diagnostic only.  ripgrep cannot read an
unreadable file either, so a narrowed scope never reports one; what it does
instead is the subject of the next node.

** Limitations of the prefilter
:PROPERTIES:
:DESCRIPTION: What is never pushed, and what one bad file costs.
:END:

Each of these costs candidate files or a whole run, and none of them can
cost a match.

#+cindex: encoding, and a pushed literal
#+cindex: latin-1
A literal is pushed only where every character in it is printable ASCII.
ripgrep decodes as UTF-8 while Emacs may decode an Org file as latin-1
through a coding cookie or ~file-coding-system-alist~: measured, a latin-1
file holding =* Cafe Review= with an accented =e= matches the ASCII
pattern =Caf= and does not match the UTF-8 pattern for the accented
spelling.  No flag fixes it, since =--encoding= is one global setting and a
corpus is mixed.  Such a conjunct emits no pattern, which costs breadth and
never an answer.

A planning bound is never pushed, only the presence of the stamp; org-ql
applies the bound.  See [[*The push-down rules]].

A broad ~org-use-property-inheritance~ removes narrowing from every
~property~ and ~property-ts~ conjunct.  See
[[*Inheritance and pushability]].

Only the top-level conjuncts of an ~and~ are considered.  A query whose
whole shape is a disjunction --- =(or (property "URL") (property
"LOCATION"))= --- pushes nothing, even though each arm would push on its
own.

#+cindex: symlink loop
One unreadable file under the root costs the entire run.  Measured: with
one unreadable file among two, ripgrep prints the readable match, writes
=Permission denied= to stderr, /and/ exits 2 --- and a partial answer is
exactly the unsound direction, so the whole answer is discarded and the
scope is scanned live.  A symlink loop does the same by the same route,
since =--follow= over one makes ripgrep exit 2.  Under =auto= every agent
over that root then falls back to a live scan until the file or the loop
is dealt with: slow, correct, and reported as =ripgrep failed=.  Under
=require= they *refuse to update at all*, which is that setting keeping
its word --- one stray root-owned file anywhere under the root is enough
to stop every corpus-scope agent, and the refusal names the reason.

Finally, the intersection of ripgrep's answer with the scope's own file
list depends on ripgrep's traversal not being narrower than
~directory-files-recursively~'s.  That is what =--hidden=, =--no-ignore=,
=--follow= and an inclusive =--iglob '*.org'= are in the argument vector
for: ripgrep honours =.gitignore= by default and a corpus is commonly a
git repository, ripgrep skips dot-directories by default and the Emacs
walk descends into them, and the Emacs walk matches its regexp with
~case-fold-search~ so =NOTES.ORG= is in the base set.  A file ripgrep
failed to visit would be a match lost with no error, and those flags are
what keeps ripgrep's traversal from being the narrower of the two rather
than something the intersection makes safe.

#+cindex: symlink, to a file, and an unstable base set
#+findex: directory-files-recursively
The Emacs walk has the last word, though, and on this platform it is
itself not quite stable.  ~directory-files-recursively~ can
intermittently drop a *symlink to a file* from an =active= or =all=
scope's base set: ~file-name-all-completions~ sometimes reports such a
link with a trailing slash, which makes the walk take it for a directory
it must not follow.  So a corpus assembled out of per-file symlinks may
see matches in the linked files appear and disappear between updates of
the same agent, with *nothing said either time*.  A symlink to a
/directory/ is unaffected, and so is the prefilter --- ripgrep reports
the file either way.  This is the one place in this chapter where a
match can go missing quietly, and it is not the prefilter's doing: name
the files in an explicit =:AGENT_SCOPE:= list where that matters.

* Views
:PROPERTIES:
:DESCRIPTION: The three ways an agent shows what it found.
:END:
#+cindex: view
#+cindex: rendering an agent

An agent's query says which entries it is interested in.  Its /view/ says
what to write down about them.  There are three, and they differ less in
what they can express than in where they put it: the =children= view
writes into the outline, as headings under the agent, while the =list=
and =table= views write inside a dynamic block and never touch the
outline around it.

That difference is the one to choose on.  A =children= view puts the
matches where Org's own outline machinery can reach them, so you can fold
them, refile beside them, annotate one, or let a second agent match them;
the price is that the agent owns a region of your outline and rewrites it
on every update.  A =list= or =table= view owns nothing but the inside of
its block, and can be dropped into the middle of prose.

Evaluation does not change with the view.  All three ask the same
question of the same engine and get the same matches; only the writing
down differs.

The examples in this chapter, and in [[*Dynamic blocks]] after it, were
run over the corpus and registry of [[*The example corpus]].

** Choosing a view
:PROPERTIES:
:DESCRIPTION: :AGENT_VIEW:, and the three values it takes.
:END:
#+cindex: @samp{AGENT_VIEW}, agent property
#+cindex: choosing a view

Name the view in =:AGENT_VIEW:=.  With the property absent you get
=children=, which is why the shortest possible agent---one bare
=:AGENT_QUERY:= line---renders as headings.

#+attr_texinfo: :table-type table :indic code
- children ::
  #+cindex: @samp{children}, agent view
  One child heading per match, written under the agent.  The default, and
  the only view that writes outside a dynamic block.  See [[*The children view]].

- list ::
  #+cindex: @samp{list}, agent view
  An Org plain list, one item per match, written inside an =org-agents=
  dynamic block.  See [[*The list view]].

- table ::
  #+cindex: @samp{table}, agent view
  An Org table: a header row, a rule, and one row per match, written
  inside an =org-agents= dynamic block.  See [[*The table view]].

Any other value is refused rather than rendered, and the diagnosis names
what you wrote and what the three names are:

#+begin_example
org-agents: Broken view (~/org/agents.org:1): :AGENT_VIEW: ‘tabel’ is not
one of children, list, table
#+end_example

The refusal is deliberate, and the reason is worth knowing because it
explains a whole class of this package's diagnostics.  Every view but
=table= renders as a list, so an unrecognized name would come out as a
list rather than as nothing: =tabel= would quietly render, and would
render the wrong view.  A view that silently does the wrong thing is
worse than a view that refuses.

The value is compared as text before it is interned, so a misspelling
leaves no stray symbol behind in your Emacs.

One Org rule catches people here.  Org reads the property value =nil= as
no value at all, so =:AGENT_VIEW: nil= is an agent with no view, and it
takes the default rather than complaining.

** The children view
:PROPERTIES:
:DESCRIPTION: The default: one child heading per match.
:END:
#+cindex: children view
#+cindex: alias
#+cindex: @samp{AGENT_MATCH}, agent property

This is Tinderbox's arrangement: the agent is a container, and what it
finds appears inside it.  Each match becomes a child heading holding a
link to the match, one level below the agent, carrying =:AGENT_MATCH: t=
in its own drawer.  Following the tradition, such a heading is called an
/alias/.

[[*Your first agent]] builds one of these from nothing; what follows is
the rendering itself, in full.  An agent and an update produce this:

#+begin_example
,* Up for review
  :PROPERTIES:
  :AGENT_QUERY: (and (todo "TODO") (property "NEXT_REVIEW"))
  :AGENT_MATCHED: 3 [2026-08-20 Thu 17:46]
  :END:
,** [[id:rewrite-exporter][Rewrite the exporter]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
,** [[id:audit-prefilter][Audit the prefilter]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
,** [[id:renew-passport][Renew the passport]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
#+end_example

Three things in that output are worth naming.

The link is an =id:= link where the match carries an =:ID:=, and building
it registers that id in =org-id-locations= so the link resolves later.  A
match with no =:ID:= is linked as =file:PATH::*Heading= instead, using
Org's own headline-search syntax.  A match with neither an id nor a file
to link to cannot be linked at all: it is rendered as its heading text
with =(?)= after it, because a link that goes nowhere is worse than text
saying there is none.

The alias's description is the match's heading /as it read when the alias
was written/.  It is text, not a live proxy; see [[*The alias contract]].

=:AGENT_MATCHED:= is the agent's own note of what it last found and when.
See [[*What writing AGENT_MATCHED costs]].

Because this is the only view that writes outside a dynamic block, it is
the only one that has to answer for what it deletes.  That answer is the
alias contract, and it is the next node.

** The alias contract
:PROPERTIES:
:DESCRIPTION: Which aliases the package owns, and which are yours.
:END:
#+cindex: alias contract
#+cindex: pristine alias
#+cindex: stale alias
#+cindex: @samp{(stale)}

An update rewrites the agent's children.  For that to be safe, there has
to be a rule saying which children it may delete, and the rule has to be
one you can predict without reading the code.  It is this:

- An alias carrying =:AGENT_MATCH: t= and holding /nothing but that
  drawer/ is *pristine*.  It belongs to the package.  Every update
  deletes it and writes it again.

- The moment you write anything under it, it is *yours*.  No update
  deletes it.  When its match is gone, the alias gets =(stale)= appended
  to its title instead.

- A child that never carried =:AGENT_MATCH: t= is not the package's to
  touch at all.

- An alias is recognized by the target it links to, never by its
  description.  The description is the match's old heading text, and
  headings drift.

Here is the whole contract in two updates.  After one update, annotate
the second alias:

#+begin_example
,* Up for review
  :PROPERTIES:
  :AGENT_QUERY: (and (todo "TODO") (property "NEXT_REVIEW"))
  :AGENT_MATCHED: 3 [2026-08-20 Thu 17:52]
  :END:
,** [[id:rewrite-exporter][Rewrite the exporter]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
,** [[id:audit-prefilter][Audit the prefilter]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
Why this one matters: it is the slow one.
,** [[id:renew-passport][Renew the passport]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
#+end_example

Now narrow the query to =(and (todo "TODO") (property "URL"))=.  Over this
corpus that drops =Audit the prefilter=, which has no =:URL:=, and keeps
the other two, which have one.  Update again:

#+begin_example
,* Up for review
  :PROPERTIES:
  :AGENT_QUERY: (and (todo "TODO") (property "URL"))
  :AGENT_MATCHED: 2 [2026-08-20 Thu 17:52]
  :END:
,** [[id:audit-prefilter][Audit the prefilter]] (stale)
:PROPERTIES:
:AGENT_MATCH: t
:END:
Why this one matters: it is the slow one.
,** [[id:rewrite-exporter][Rewrite the exporter]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
,** [[id:renew-passport][Renew the passport]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
#+end_example

Your note survived, and the alias it was written under is marked rather
than removed.  Notice also that the annotated alias is now /first/: the
two pristine ones were deleted and written again at the end of the
subtree, while the one you adopted stayed exactly where it was.
Annotating an alias moves it to the top of the list, in effect, and
keeps it there.

A match that comes back unmarks the alias its absence marked, so the
stale mark answers for this update and not for an older one.

Four consequences follow from the contract, and each is worth knowing
before you rely on it.

1.  Because a pristine alias is deleted rather than edited, extra drawer
   properties or tags you add to a body-less alias are *discarded* by the
   next update.  Write a line of text under the alias and they are kept
   along with it.

2.  A preserved alias keeps the description and the format suffix it was
   written with.  Only the stale mark changes.  So an alias whose match
   has since been renamed goes on showing the old title.

3.  An alias is recognized by its target.  A match that *gains an =:ID:=*
   between two updates is therefore a different target: the old alias is
   marked stale and a new one is written beside it.

4.  Two matches with no =:ID:= and identical headings in one file share
   one =file:...::*Heading= target, so a single alias may stand for both
   while =:AGENT_MATCHED:= counts two.  Give them ids to tell them apart.

An alias whose link you have edited past reading is left alone, and a
fresh alias is written beside it.  That is a duplicate, and it is
accepted: the alternative is guessing which match a mangled link stood
for.

** The list view
:PROPERTIES:
:DESCRIPTION: An Org plain list inside a dynamic block.
:END:
#+cindex: list view

A list beats children when you want the matches to read as part of a
document rather than as part of an outline: a bibliography in the middle
of a chapter, an index at the top of a project file, a set of links in a
meeting note.  Nothing is folded, nothing is refilable, and the agent's
subtree keeps whatever structure you gave it.

Set =:AGENT_VIEW: list= and update.  The renderer needs an =org-agents=
dynamic block to write into; if the entry has none, the update opens one:

#+begin_example
,* Everything with a URL
  :PROPERTIES:
  :AGENT_QUERY:  (property "URL")
  :AGENT_VIEW:   list
  :AGENT_FORMAT: URL
  :AGENT_MATCHED: 3 [2026-08-20 Thu 17:50]
  :END:
,#+BEGIN: org-agents
- [[id:rewrite-exporter][Rewrite the exporter]] https://github.com/example/exporter
- [[id:renew-passport][Renew the passport]] https://travel.state.gov/passport
- [[id:tinderbox-notes][Tinderbox notes]] https://www.eastgate.com/Tinderbox/
,#+END:
#+end_example

The block delimiters are the boundary of everything this view writes.
Text above the block, below it, or in another block is not touched.  For
what you can say in the =#+BEGIN:= line itself, see [[*Dynamic blocks]].

** The table view
:PROPERTIES:
:DESCRIPTION: :AGENT_COLUMNS:, ITEM_BY_ID, and one row per match.
:END:
#+cindex: table view
#+cindex: @samp{AGENT_COLUMNS}, agent property
#+cindex: @samp{ITEM_BY_ID}

A table is what you want when the answer is not "which entries" but
"which entries, and what do they say".  Name the columns in
=:AGENT_COLUMNS:=, whitespace separated:

#+begin_example
,* Review queue
  :PROPERTIES:
  :AGENT_QUERY:   (and (todo "TODO") (property "NEXT_REVIEW"))
  :AGENT_VIEW:    table
  :AGENT_COLUMNS: ITEM_BY_ID NEXT_REVIEW REVIEWS
  :AGENT_SORT:    (ts-column 2)
  :AGENT_MATCHED: 3 [2026-08-20 Thu 17:50]
  :END:
,#+BEGIN: org-agents
| ITEM_BY_ID           | NEXT_REVIEW | REVIEWS |
|----------------------+-------------+---------|
| [[id:renew-passport][Renew the passport]]   |  2026-08-21 |         |
| [[id:audit-prefilter][Audit the prefilter]]  |  2026-08-25 |       2 |
| [[id:rewrite-exporter][Rewrite the exporter]] |  2026-09-01 |       5 |
,#+END:
#+end_example

One column name is special.  =ITEM_BY_ID= is the link to the match, and
it may appear anywhere in the list, not only first.  Every other name is
read as a property at the match's own heading.  With =:AGENT_COLUMNS:=
absent you get =ITEM_BY_ID= alone, which is the one column no property
could have supplied:

#+begin_example
,* Everything with a location
  :PROPERTIES:
  :AGENT_QUERY: (property "LOCATION")
  :AGENT_VIEW:  table
  :AGENT_MATCHED: 2 [2026-08-20 Thu 17:50]
  :END:
,#+BEGIN: org-agents
| ITEM_BY_ID         |
|--------------------|
| [[id:renew-passport][Renew the passport]] |
| [[id:collect-print][Collect the print]]  |
,#+END:
#+end_example

A name nothing at the match has set gives an empty cell, silently:
=REVIEWS= is empty for =Renew the passport= in the first table above
because that entry has no such property.  That is a property nothing set,
not an error, and it is the same answer a column view would give.  A
match this package cannot locate has no entry to read properties at, so
all of its cells but the link are empty.

Two mechanical details, so the output is not surprising.  A =|= in a cell
value is escaped to =\vert{}=, because a bar would read as the boundary
of a cell that is not there and would make the row one column wider than
the table.  And the rule is written literally as =|-|= with no cell
padded: the renderer writes the table and then asks Org to align it,
which is the only place a column width can be measured.  If alignment
fails, the table is left unaligned rather than the whole update being
taken down with it.

The table view has no format suffix; =:AGENT_COLUMNS:= is the table's
version of that idea.  See [[*Formats]].

** Formats
:PROPERTIES:
:DESCRIPTION: :AGENT_FORMAT:, and where its suffix appears.
:END:
#+cindex: @samp{AGENT_FORMAT}, agent property
#+cindex: format suffix

=:AGENT_FORMAT:= names properties to show /after the link/, so you can
read a value without opening the entry it belongs to.  It is a
whitespace-separated list of property names, and it applies to the
=children= and =list= views only.

#+begin_example
,* Up for review
  :PROPERTIES:
  :AGENT_QUERY:  (and (todo "TODO") (property "NEXT_REVIEW"))
  :AGENT_FORMAT: NEXT_REVIEW
  :AGENT_MATCHED: 3 [2026-08-20 Thu 19:32]
  :END:
,** [[id:rewrite-exporter][Rewrite the exporter]] 2026-09-01
:PROPERTIES:
:AGENT_MATCH: t
:END:
,** [[id:audit-prefilter][Audit the prefilter]] 2026-08-25
:PROPERTIES:
:AGENT_MATCH: t
:END:
,** [[id:renew-passport][Renew the passport]] 2026-08-21
:PROPERTIES:
:AGENT_MATCH: t
:END:
#+end_example

The suffix goes on the alias heading in the =children= view and after the
link in a =list= item.  It has no place in a =table= view, where columns
do the same work with a header to name them.

Two properties of the reading are easy to trip over.

The values are read with *no inheritance*.  A format naming =OWNER= shows
nothing for a match whose =:OWNER:= is written on an ancestor, even
though that ancestor's value is what a query written =$OWNER*= would see.
See [[*The two axes]] for the two axes and what each of them reaches.

Values are joined with two spaces, and a property the match does not have
contributes the empty string.  A format naming two properties where the
match has only the first therefore leaves *two trailing spaces* on the
line.  Either keep a format to the properties your matches actually
carry, or expect the whitespace.  A suffix that is entirely empty
contributes nothing at all, not even the space that would have separated
it from the link.

** Sorting and limiting
:PROPERTIES:
:DESCRIPTION: :AGENT_SORT: and :AGENT_LIMIT:, and which sorts a table owns.
:END:
#+cindex: @samp{AGENT_SORT}, agent property
#+cindex: @samp{AGENT_LIMIT}, agent property
#+cindex: sorting an agent's matches
#+cindex: limiting an agent's matches

There are two kinds of sort, and the distinction is not decoration: one
orders /matches/ and is org-ql's, the other orders /rendered rows/ and is
this package's.

=:AGENT_SORT:= takes one of =date=, =todo=, =priority=, =reverse=, or a
list of those.  Those are org-ql's own sorting methods, applied to the
matched entries before anything is rendered, and they work in every view.

One thing about =date= is worth saying plainly, because the name invites
the wrong reading: it sorts on *Org's own planning timestamps* --- a
=SCHEDULED:=, a =DEADLINE:=, a plain timestamp in the entry --- and knows
nothing about a date you keep in a property.  Over a corpus whose review
dates live in =:NEXT_REVIEW:= it is therefore inert, and the matches come
out in the order org-ql found them, which is file order.  To order by a
property date, use the =table= view and =(ts-column N)= on the column that
renders it, as the example below does.

=:AGENT_SORT:= also takes =(column N)= and =(ts-column N)=, which order
the rows of a table: =(column N)= compares the rendered cells as strings,
=(ts-column N)= reads them as timestamps.  =N= is 1-indexed over
=:AGENT_COLUMNS:=.  A cell naming no time sorts after every cell that
does, because an entry with no date is not an entry dated the epoch.
These two are *table-only*, and asking for one in another view is
refused:

#+begin_example
(column 1) sorts table rows, but the view is ‘children’
#+end_example

as is a column number naming no column:

#+begin_example
:AGENT_SORT: no column 4 among 3 columns
#+end_example

A value that is neither kind is refused by name, with the whole
vocabulary in the message:

#+begin_example
cannot sort by ‘dtae’; expected date, todo, priority, reverse, a list of
those, or (column N)/(ts-column N)
#+end_example

=:AGENT_LIMIT:= is a count, and it is applied *after* the sort.  That
ordering is what makes "the two nearest reviews" expressible:

#+begin_example
,* The two nearest reviews
  :PROPERTIES:
  :AGENT_QUERY:   (property "NEXT_REVIEW")
  :AGENT_VIEW:    table
  :AGENT_COLUMNS: ITEM_BY_ID NEXT_REVIEW
  :AGENT_SORT:    (ts-column 2)
  :AGENT_LIMIT:   2
  :AGENT_MATCHED: 2 [2026-08-20 Thu 17:50]
  :END:
,#+BEGIN: org-agents
| ITEM_BY_ID          | NEXT_REVIEW |
|---------------------+-------------|
| [[id:renew-passport][Renew the passport]]  |  2026-08-21 |
| [[id:audit-prefilter][Audit the prefilter]] |  2026-08-25 |
,#+END:
#+end_example

Those really are the two nearest, and not the first two org-ql happened
to find.  With a row sort the limit is applied by the table renderer,
after the rows exist to be ordered; without one it is applied by the
collector.  Either way the limit comes last.

A limit that is not a count is refused rather than read charitably:

#+begin_example
:AGENT_LIMIT: must be a count, not ‘many’
#+end_example

=string-to-number= would read =many= as 0, and an agent rendering nothing
looks exactly like an agent that matched nothing.

** Limitations of the views
:PROPERTIES:
:DESCRIPTION: What the renderers do not preserve.
:END:
#+cindex: limitations, of the views

*Drawer edits to a pristine alias are discarded.*  This is the sharp
edge of the alias contract and it is worth restating on its own, because
it is the one that looks like data loss.  An alias holding nothing but
=:AGENT_MATCH: t= is deleted and written again by every update, so a
property or a tag you add to it is gone at the next update, with nothing
said about it.  Write one line of text under the alias first and the
whole heading, drawer and tags included, is preserved from then on.

*A hand-edited block body does not round-trip byte-exactly.*  The
renderer keeps a copy of the previous body so that a failed render can
put it back (see [[*Limitations of dynamic blocks]]).  That copy is exact
for a body a successful render wrote.  For a body you edited by hand it
is not quite: a trailing blank line is lost, and a hand-indented line
comes back at the block's own indentation column.

*A table's alignment is cosmetic and is not guaranteed.*  Alignment
happens after the table is in the buffer, and a failure there is reported
and stepped over rather than allowed to abort the update.  An unaligned
table is a correct table.

*Changing =:AGENT_VIEW:= away from =children= orphans the aliases already
written.*  A view change does not reclaim the outline the previous view
built: only the =children= renderer looks for aliases, so an agent
switched to =list= or =table= renders its block and leaves every alias
sitting under it, pristine ones included, with nothing said about them.
Delete them by hand.  The reverse case is the same in shape and easier to
see: an agent switched back to =children= renders aliases and leaves its
block where it was, holding the last answer it was given.

* Dynamic blocks
:PROPERTIES:
:DESCRIPTION: The org-agents block type, and what you can say in one.
:END:
#+cindex: dynamic block
#+cindex: @samp{org-agents} dynamic block

The =list= and =table= views write into an Org dynamic block whose type
is =org-agents=.  Using Org's own mechanism rather than a new one buys
three things: the block delimits exactly what the render owns, Org's
existing commands update it, and a block can carry parameters, which a
property drawer cannot.

The parameters matter more than they first appear.  A block's parameters
override the enclosing agent's properties name by name, so one agent can
carry several views of itself; and a block with its own =:query=
parameter needs no agent at all, which is how you drop a query into a
prose document that has no properties to hang one on.

** Inserting a block
:PROPERTIES:
:DESCRIPTION: org-agents-insert-dblock and C-c C-x x.
:END:
#+cindex: inserting a dynamic block
#+kindex: C-c C-x x

{{{kbd(C-c C-x x)}}} is Org's command for inserting a dynamic block, and
=org-agents= is among the types it offers, beside =columnview= and
=clocktable=.  {{{kbd(M-x)}}} =org-agents-insert-dblock= does the same
thing directly.

What is inserted is empty, and deliberately so:

#+begin_example
,#+BEGIN: org-agents
,#+END:
#+end_example

That is what =columnview= and =clocktable= do at {{{kbd(C-c C-x x)}}},
and it keeps insertion separate from evaluation.  Writing the block is a
separate step: {{{kbd(C-c C-c)}}} inside it, {{{kbd(C-c C-x C-u)}}}, or
=org-agents-update=.  See [[*By hand]].

If point is not at the beginning of a line, a fresh line is opened first.
If the enclosing entry is an agent whose view needs a block and has none,
an update opens one for you, so inserting the block by hand is a
convenience rather than a requirement.

** Block parameters
:PROPERTIES:
:DESCRIPTION: The seven parameters, and how a block overrides an agent.
:END:
#+cindex: block parameters
#+cindex: overriding an agent property

Org reads a block's parameters as Lisp.  That is what lets a block say
things a property drawer never could, and it is also what makes a block
get things wrong that a drawer cannot.

Each parameter overrides the corresponding =AGENT_*= property of the
entry the block sits under.  The test is presence, not truth, so a
parameter written =nil= *clears* the property: =:limit nil= asks for no
limit, which is not the same as a block that says nothing about limits.

#+attr_texinfo: :table-type table :indic code
- :query ::
  Overrides =:AGENT_QUERY:=.  A string, or the form itself, since Org has
  already read the parameters as Lisp.  Unreadable text is refused, as
  =unreadable :query ‘...’=.  A block with a =:query= belongs to no
  agent; see [[*Several blocks under one agent]].

- :view ::
  Overrides =:AGENT_VIEW:=.  A *symbol*, one of =children=, =list=,
  =table=.  A string is not the symbol, and is refused: =a block’s
  ‘:view’ must be one of children, list, table, not "table"=.  May not be
  nil, because there is no such thing as no view.  =children= is accepted
  and read as =list=: a block cannot write headings, so there is nothing
  else for it to mean.  Measured: a block written =:view children=
  renders a plain list, and says nothing.  See [[*The children view]].

- :scope ::
  Overrides =:AGENT_SCOPE:=.  Resolved exactly as the property is; see
  [[*Scopes]].  May not be nil: no scope resolves to no files, and the
  block would then read as a query that matched nothing.

- :sort ::
  Overrides =:AGENT_SORT:=.  Checked against the same vocabulary, with
  the same table-only rule for =(column N)= and =(ts-column N)=.

- :limit ::
  Overrides =:AGENT_LIMIT:=.  A non-negative integer, or nil to clear.
  Refused otherwise: =a block’s ‘:limit’ must be a count, not "5"=.

- :columns ::
  Overrides =:AGENT_COLUMNS:=.  A *string*, or nil.

- :format ::
  Overrides =:AGENT_FORMAT:=.  A *string*, or nil.

The one thing that surprises everybody: =:columns= and =:format= need
quoted strings, because a block's parameters are Lisp.

#+begin_example
,#+BEGIN: org-agents :format NEXT_REVIEW
,#+END:
#+end_example

is refused, and the message says exactly what happened:

#+begin_example
org-agents: a block’s ‘:format’ must be a string, not NEXT_REVIEW
#+end_example

Write =:format "NEXT_REVIEW"=.  In a property drawer,
=:AGENT_FORMAT: NEXT_REVIEW= needs no quotes, because a property value is
already a string.  The two spellings look alike and are read by different
readers.

A block that has neither a =:query= of its own nor an enclosing agent has
nothing to render, and says so:

#+begin_example
org-agents: block has no :query and no enclosing agent
#+end_example

#+findex: org-dblock-write:org-agents
Those four messages are quoted here as the writer raises them.  Reached
through Org's own dblock machinery --- {{{kbd(C-c C-c)}}},
~org-dblock-update~, ~org-update-all-dblocks~ --- each arrives in the echo
area behind a prefix from ~org-dblock-write:org-agents~, so what you
actually read is =org-agents: dblock update failed: org-agents: a block’s
‘:format’ must be a string, not NEXT_REVIEW=.  Reached through
~org-agents-update~ on an enclosing agent it is prefixed differently
again, with the agent's heading and its =FILE:LINE=.

** Several blocks under one agent
:PROPERTIES:
:DESCRIPTION: Two views of one agent, or two different questions.
:END:
#+cindex: multi-block agent
#+cindex: standalone dynamic block

One agent may carry as many =org-agents= blocks as you like.  An update
with point *outside* every block writes all of them, in buffer order; an
update with point *inside* one writes that block alone, which is how you
refresh one expensive view without the others.

There is a precondition, and it is not obvious: *the entry's own
=:AGENT_VIEW:= must be =list= or =table=, never =children=.*  The entry's
view decides which renderer runs, and =children= renders aliases without
ever looking for a block.  An agent with no =:AGENT_VIEW:= and two blocks
under it writes three child aliases, reports itself updated, and leaves
both blocks empty, saying nothing about them:

#+begin_example
,* No view named
  :PROPERTIES:
  :AGENT_QUERY: (property "NEXT_REVIEW")
  :AGENT_MATCHED: 3 [2026-08-20 Thu 17:52]
  :END:
,#+BEGIN: org-agents
,#+END:
,** [[id:rewrite-exporter][Rewrite the exporter]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
,** [[id:audit-prefilter][Audit the prefilter]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
,** [[id:renew-passport][Renew the passport]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
#+end_example

With =:AGENT_VIEW: list= on the entry, both blocks are written by one
=org-agents-update-buffer=, each according to its own parameters:

#+begin_example
,* Review desk
  :PROPERTIES:
  :AGENT_QUERY: (and (todo "TODO") (property "NEXT_REVIEW"))
  :AGENT_VIEW:  list
  :AGENT_MATCHED: 3 [2026-08-20 Thu 17:50]
  :END:
,#+BEGIN: org-agents :format "NEXT_REVIEW"
- [[id:rewrite-exporter][Rewrite the exporter]] 2026-09-01
- [[id:audit-prefilter][Audit the prefilter]] 2026-08-25
- [[id:renew-passport][Renew the passport]] 2026-08-21
,#+END:

,#+BEGIN: org-agents :view table :columns "ITEM_BY_ID NEXT_REVIEW" :sort (ts-column 2)
| ITEM_BY_ID           | NEXT_REVIEW |
|----------------------+-------------|
| [[id:renew-passport][Renew the passport]]   |  2026-08-21 |
| [[id:audit-prefilter][Audit the prefilter]]  |  2026-08-25 |
| [[id:rewrite-exporter][Rewrite the exporter]] |  2026-09-01 |
,#+END:
#+end_example

Because =:query= is among the parameters, two blocks of one agent need
not even be asking the same question:

#+begin_example
,* Two questions
  :PROPERTIES:
  :AGENT_QUERY: (property "NEXT_REVIEW")
  :AGENT_VIEW:  list
  :AGENT_MATCHED: 3 [2026-08-20 Thu 17:52]
  :END:
,#+BEGIN: org-agents
- [[id:rewrite-exporter][Rewrite the exporter]]
- [[id:audit-prefilter][Audit the prefilter]]
- [[id:renew-passport][Renew the passport]]
,#+END:

,#+BEGIN: org-agents :query (property "LOCATION")
- [[id:renew-passport][Renew the passport]]
- [[id:collect-print][Collect the print]]
,#+END:
#+end_example

A block that supplies its own =:query= and sits under no agent renders
standalone, over =org-agenda-files= as a =list= until its own parameters
say otherwise:

#+begin_example
,* Notes
,#+BEGIN: org-agents :query (property "LOCATION") :format "LOCATION"
- [[id:renew-passport][Renew the passport]] Pasadena
- [[id:collect-print][Collect the print]] Altadena
,#+END:
#+end_example

Write it with point inside the block, or with Org's own
{{{kbd(C-c C-c)}}}.  =org-agents-update-buffer= leaves such a block
alone: it belongs to no agent, there is nothing to record a count on, and
refreshing every dynamic block in a buffer is already
=org-update-all-dblocks='s job.

** Limitations of dynamic blocks
:PROPERTIES:
:DESCRIPTION: What one :AGENT_MATCHED: line cannot say.
:END:
#+cindex: limitations, of dynamic blocks

*=:AGENT_MATCHED:= records the first block's count, in buffer order.*
For a multi-block agent there is no single right number to record.  A
block's parameters override the entry's, =:query= included, so two blocks
of one agent may answer different questions, and "the agent's count" is
not one number.  The first block's count is what is written, and it is
what it says it is rather than a total.  In the =Two questions= example
above, =:AGENT_MATCHED:= is =3=, which is the first block's three
matches, and the second block's two are recorded nowhere.  Likewise an
agent whose =:AGENT_LIMIT:= is 1 and whose second block clears it with
=:limit nil= records =1=, while the second block holds three items.

*A =children= agent that owns blocks ignores them silently.*  Shown
above.  If you find an =org-agents= block that stays empty however often
you update, check the enclosing entry's =:AGENT_VIEW:=.

*A block cannot render =children=, and does not say so.*  =:view
children= is accepted --- it is one of the three views, and the parameter
is checked against all three --- and then read as =list=, because a block
has no way to write a heading.  Measured: the block renders a plain list
and no diagnostic is issued.  A view that quietly does something else is
worse than one that refuses, and this is the one place the package does
it.  What a refusal would cost is the reason: the writer reads the
entry's view as well as the block's, and Org reaches it for every
=org-agents= block whether this package sent it or not --- measured,
~org-update-all-dblocks~ in a buffer whose agent names no view renders
that agent's block as a list --- so a refusal on =children= would fire
there too.

*An interrupted or failed render restores the previous body, not the
buffer.*  =org-prepare-dblock= deletes the old body before the writer
runs, so everything a render needs is computed before anything is
written, and a failure puts the old body back.  {{{kbd(C-g)}}} is treated
the same way: the body goes back and the quit is then signalled again, so
the interrupt still interrupts.

*An edit landing in the block during a prefilter wait is not protected.*
A =list= or =table= agent over a corpus scope may wait on a ripgrep
subprocess from inside Org's dblock writer, with the block body already
deleted, and waiting on a subprocess runs timers.  The =children= view
does not have this exposure because it collects before it edits.  See
[[*Bounding a run]] for what this costs and why it is not closed.

* Updating
:PROPERTIES:
:DESCRIPTION: Every way to refresh an agent, and when to choose each.
:END:
#+cindex: updating
#+cindex: refreshing an agent

Nothing in this package updates an agent by itself.  There is no timer,
no idle hook, and no background process; a render happens because you
asked for one, either by running a command or by saving a file you have
armed for it.  That is a design position rather than an omission, and it
is argued in [[*What was deliberately not ported, and why]].

So there are exactly four ways in, and this chapter is about choosing
between them.

- A command, over one agent, one buffer, or a named file set.  See
  [[*By hand]].
- Org's own dynamic-block commands, over one block or every block in a
  buffer.  See [[*Inserting a block]] and [[*By hand]].
- A save, with =org-agents-mode= on in that buffer.  See
  [[*org-agents-mode]].
- A save in any buffer that looks like it holds an agent, with
  =global-org-agents-mode= on.  See [[*global-org-agents-mode]].

The package binds no keys of its own.  {{{kbd(C-c C-c)}}},
{{{kbd(C-c C-x x)}}} and {{{kbd(C-c C-x C-u)}}} are Org's, and reach this
package because an =org-agents= block is an ordinary Org dynamic block.
Everything else you bind yourself, or run with {{{kbd(M-x)}}}.

** By hand
:PROPERTIES:
:DESCRIPTION: org-agents-update, -update-buffer and -update-all.
:END:
#+cindex: updating by hand
#+findex: org-agents-update
#+findex: org-agents-update-buffer
#+findex: org-agents-update-all

Three commands, in order of how much they touch.

*=org-agents-update=* updates the agent point is in, or the =org-agents=
block point sits in.  Point may sit anywhere in the entry: on the
heading, in the drawer, in the body, or inside a block.  With point
inside a block, that block alone is written; otherwise the whole agent
is, which for a =children= agent means its aliases and for a block-view
agent means every one of its blocks.  The echo area reports
=org-agents: N match(es)=, or =org-agents: the block wrote N item(s)= for
a standalone block.  With neither an agent nor a block at point it
refuses:

#+begin_example
org-agents: no agent and no ‘org-agents’ block at point
#+end_example

#+kindex: C-c C-x Q
This is the command to bind.  The package does not bind it, so pick a key
in the Org map; {{{kbd(C-c C-x Q)}}} is free there, where the lower-case
{{{kbd(C-c C-x q)}}} and {{{kbd(C-c C-x a)}}} are both Org's own:

#+begin_src emacs-lisp
(with-eval-after-load 'org
  (define-key org-mode-map (kbd "C-c C-x Q") #'org-agents-update))
#+end_src

The =use-package= form in [[*Installation]] binds the same key.

*=org-agents-update-buffer=* updates every agent in the current buffer,
continuing past failures.  Headings are what it scans, and an agent is a
heading whose *own drawer* supplies a query; searching the buffer text
for the property name would find it in a note you wrote under an alias,
or in an agent's own prose, and would call one heading two agents.  A
dynamic block supplying its own =:query= belongs to no agent and is left
alone.

Each agent answers for itself.  One with a malformed property is named in
the summary and the rest are updated regardless, because an update that
stopped at the first bad query would leave every agent after it stale:

#+begin_example
org-agents: updated 2 agents, 1 failed:
org-agents: Broken limit (~/org/agents.org:31): :AGENT_LIMIT: must be a
count, not ‘many’
#+end_example

The failure names the agent's heading and its =FILE:LINE=, because the
same summary is read over a whole corpus where several agents may share a
heading.

*=org-agents-update-all=* updates every agent in the files
=org-agents-files= names.  That option is a list of files and
directories, or the symbol =agenda= for =org-agenda-files=; a directory
contributes the Org files below it, recursively.  Names are winnowed to
the readable ones and compared as truenames, so a file named twice
over---by itself and by a directory that holds it---is updated once, and
one summary does not report the agents in it twice.  A file that is
readable but that Emacs cannot visit (one grown past
=large-file-warning-threshold=, one that changed on disk since it was
last visited, one whose coding system cannot decode it) is recorded as a
single failure named by its file, and does not take with it the count of
the files already updated.

Note what =org-agents-files= is and is not.  It says which files
=org-agents-update-all= opens *and writes*.  It has nothing to do with
=:AGENT_SCOPE:=, which says which files an agent /reads/.  See [[*Scopes]].

*An update leaves its buffers modified and unsaved.*  All three commands
do, and it is deliberate: the result can be read over---and undone with
{{{kbd(C-/)}}}---before it is kept.  =org-agents-update-all= over a
hundred files leaves a hundred modified buffers and writes nothing to
disk.  Save them yourself, or do not.

** Looking before you write
:PROPERTIES:
:DESCRIPTION: org-agents-preview, which writes nothing.
:END:
#+cindex: previewing a query
#+findex: org-agents-preview

=org-agents-preview= reads a query from the minibuffer and shows what an
agent with that query would match, without writing anything anywhere.
It is the right way to develop a query, and the right way to find out
whether one will be approved before you commit it to a drawer.

The query is read, expanded and gated exactly as an agent's is, and
=org-agents-exclude= is conjoined in before =org-ql-search= sees the
form, so what is approved here is what runs.  See
[[*The structural gate]].

The scope is always =org-agenda-files=: a scope belongs to an agent, and
a preview has no agent.  Agenda files that cannot be read are skipped
with a message rather than refused.  With no agenda files at all, the
command says so instead of quietly searching the current buffer:

#+begin_example
org-agents: ‘org-agenda-files’ is empty, so there is nothing to preview
#+end_example

Results appear in an =org-ql-search= buffer, which is org-ql's own view
and behaves as org-ql documents it.  A query the gate does not admit is
refused with =org-agents: query not approved=.

** org-agents-mode
:PROPERTIES:
:DESCRIPTION: Updating a buffer's agents before each save.
:END:
#+cindex: updating on save
#+cindex: minor mode, org-agents-mode
#+findex: org-agents-mode
#+kindex: C-x C-s

An agent is worth more refreshed than remembered, and the cheapest moment
to refresh one is when you are already writing the file it lives in.
=org-agents-mode= is a buffer-local minor mode that updates that buffer's
agents before each save, and shows =Agents= in the mode line while it is
on.  It adds one function to
=before-save-hook= buffer-locally---on the global value the hook would
scan every save in the session, Org buffer or not, for agents it will not
find.

Turn it on with {{{kbd(M-x)}}} =org-agents-mode=, and the next
{{{kbd(C-x C-s)}}} renders before writing:

#+begin_example
,* Up for review
  :PROPERTIES:
  :AGENT_QUERY: (and (todo "TODO") (property "NEXT_REVIEW"))
  :AGENT_MATCHED: 3 [2026-08-20 Thu 17:51]
  :END:
,** [[id:rewrite-exporter][Rewrite the exporter]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
,** [[id:audit-prefilter][Audit the prefilter]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
,** [[id:renew-passport][Renew the passport]]
:PROPERTIES:
:AGENT_MATCH: t
:END:
#+end_example

Two properties are what make this usable rather than a nuisance, and both
are described in [[*The three refusals on the save path]].  A save whose
render changes nothing *writes no bytes at all*, old timestamps included,
and an agent whose scope has no bound is *named once and skipped*.  Read
that node before leaving the mode on.

The mode refuses a buffer that is not an Org buffer, and turns itself
back off before refusing, so there is never a mode reporting itself on
with no hook under it:

#+begin_example
org-agents: ‘org-agents-mode’ needs an Org buffer
#+end_example

*Arming one file.*  The targeted way to turn the mode on for a particular
file is a file-local mode line on its first line:

#+begin_example
# -*- mode: org; mode: org-agents; -*-
#+end_example

Two =mode:= specifications: the first names the major mode, the second a
minor mode to enable.  The value is =org-agents=, *not*
=org-agents-mode=, because Emacs appends =-mode= to whatever you write
there.  Write =mode: org-agents-mode= and Emacs looks for a mode called
=org-agents-mode-mode=, does not find one, and says so in a message you
will probably miss:

#+begin_example
Ignoring unknown mode ‘org-agents-mode-mode’
#+end_example

leaving the mode off in a file you believed you had armed.

*One Emacs behaviour that surprises people.*  =save-buffer= runs
=before-save-hook= only when the buffer is actually modified.  So
visiting a file and typing {{{kbd(C-x C-s)}}} without having changed
anything does not render: there was no save.  This is Emacs rather than
this package, but it looks like the mode failing.

** global-org-agents-mode
:PROPERTIES:
:DESCRIPTION: Arming every Org buffer that looks like it holds an agent.
:END:
#+cindex: minor mode, global-org-agents-mode
#+findex: global-org-agents-mode

=global-org-agents-mode= turns =org-agents-mode= on in every Org buffer
whose text matches =^[ \t]*:AGENT_QUERY:=.  A buffer that is not an Org
buffer is passed over silently; the mode's own refusal is for someone who
asked for it by name.

The test is a single whole-buffer regexp scan, and it is deliberately not
the authoritative per-heading scan an update uses.  All it decides is
whether to arm a hook.  A buffer wrongly armed pays for the real scan on
each of its saves, and a real scan that finds no agent does nothing and
says nothing.  Asking every heading's drawer instead would cost that in
every Org buffer you visit, agent or not, to decide something a text
search decides well enough.

In practice:

#+begin_example
agents.org       org-agents-mode=t     (holds an agent)
corpus.org       org-agents-mode=nil   (an Org file with no agent)
attributes.org   org-agents-mode=nil   (the registry)
#+end_example

Choosing between the global mode and the file-local line is a question
about where you keep your agents.  If they live in one or two files, the
file-local line is better: it is visible in the file, it travels with the
file, and it arms nothing else.  If agents are scattered through a corpus
you edit constantly, the global mode is better, because you will forget
to add the line.  The cost of the global mode is that the detector is a
text scan: a buffer that merely /mentions/ =:AGENT_QUERY:= in prose, this
manual's own sources among them, gets the mode and the scan on every
save.

The generated option =global-org-agents-mode= is marked risky, because
turning the mode on is what makes every save of an Org file run its
agents' queries.  A risky variable is not set from a file-local variables
block without your explicit confirmation.

** The three refusals on the save path
:PROPERTIES:
:DESCRIPTION: What a save deliberately will not do.
:END:
#+cindex: refusals on the save path
#+cindex: byte-identical save

A save is a keystroke, and a keystroke has a budget.  Three refusals keep
the update inside it.

*No save ever spawns a prefilter,* whatever =org-agents-prefilter= is set
to; the option is bound to nil for the whole extent of the update.  This
is safe because a prefilter can only narrow which files org-ql opens and
can never change what matches, so an agent updated without one matches
exactly what it would have matched, having merely opened more files to
find out.  It is also worth doing: for a scope that already names its
files, a prefilter is pure overhead, and measurably so---see
[[*Which scopes get narrowed, and why]].  Narrowing such a scope makes a
keystroke slower to reach the same answer.

*An agent whose scope needs a prefilter is not updated on save.*  Those
are the scopes with no bound on what they hold: =active=, =all=, and any
directory.  There is no telling how many files one of those would open,
so it is left for a command you asked for.  Such agents are named once,
in one message however many there are, and left exactly as they were:

#+begin_example
org-agents: not updated on save, the scope needs a prefilter: Up for
review (~/org/onsave.org:1)
#+end_example

Use =org-agents-update= on one of those.  Note the two rules answer
different questions and both are wanted: this one is about what an update
would /cost/, the first is about a save doing no work that cannot pay for
itself.

*A render that changes nothing puts the buffer back as it was.*  This is
the property that makes writing =:AGENT_MATCHED:= on every save
affordable at all.  The stamp says when an update ran, so it differs on
every run whatever the query found; without this rule every save would
rewrite the file and move the dates you rely on, for nothing.  So the
render is compared with the =:AGENT_MATCHED:= lines masked out, and where
nothing else moved the *old stamps stay* and the file reaches disk
byte-identical.  Measured: a second save with nothing new to find is
byte-for-byte identical to the first.

The buffer is restored with =replace-buffer-contents=, so point, the
mark, and every marker and overlay survive.

Two further behaviours belong here.

Any failure is reported and the save then goes on regardless:

#+begin_example
org-agents: the update on save failed: ...
#+end_example

A file must not become unsavable because a query written in it is wrong;
fixing the query is exactly what the next save is for.

A quit is deliberately *not* caught, so *{{{kbd(C-g)}}} during an update
on save aborts the save along with the update*.  A half-written render is
not what you asked to keep.

** What writing AGENT_MATCHED costs
:PROPERTIES:
:DESCRIPTION: :AGENT_MATCHED:, and the three consequences of it.
:END:
#+cindex: @samp{AGENT_MATCHED}, agent property
#+cindex: recording what an agent found

After a render, the update writes =:AGENT_MATCHED:= on the agent: how
many entries matched, and when.

#+begin_example
:AGENT_MATCHED: 3 [2026-08-20 Thu 17:46]
#+end_example

It is written only once the view has been rendered, never during one:
adding a line to a drawer moves every position below it, among them the
bounds of the very dynamic block a render was called for.  The time is
written as an inactive timestamp, so Org reads it back as one.

The point of the property is that an agent says what it last found
without being run again, which matters more here than in a system whose
agents update continuously.  It has three consequences, accepted rather
than avoided.

1. *It modifies the buffer.*  Which is to say an update always leaves its
   files modified and unsaved, even where the render itself found nothing
   new.  That is the feature [[*By hand]] describes, and the result can
   be read over and undone before it is kept.  On the save path the buffer
   is put back where the render changed nothing, so the stamp does not
   make every save rewrite the file.

2. *Its timestamp is inactive, and therefore visible to a query.*  A
   query written =(ts-inactive :from ...)= over a corpus holding agents
   will match the agents themselves.  This is not a bug in the query; it
   is a real inactive timestamp in a real drawer.

3. *It leaves a timestamp in the file,* so a version-control diff of a
   saved update shows the stamp even where the render itself did not
   move.

For what the count means when an agent carries several blocks, see
[[*Limitations of dynamic blocks]].

** Limitations of updating
:PROPERTIES:
:DESCRIPTION: What no update will ever do for you.
:END:
#+cindex: limitations, of updating

*There is no timer-driven update, and there will not be one.*  Nothing
in this package renders an agent while you are not looking at it.  The
reason is the medium: an Org corpus is thousands of text files under
version control that other tools also write, and a timer that rewrote
them would put edits into files you are not looking at and stamps into
commits you did not make.  This is the largest divergence from the system
these ideas come from, and it is argued at length, with the alternatives
named, in [[*What was deliberately not ported, and why]].

*The first save of a stale multi-block agent writes the file, and only
that save.*  A save refreshes every block of a multi-block agent, so a
buffer whose second block was stale reaches disk changed.  Every save
after it is byte-identical again.  This is worth saying because the
byte-identical save is the property you come to rely on, and the one save
that breaks it looks like the property failing.

*An update over a corpus scope leaves the files it read visited.*  org-ql
opens a file it has to evaluate against with =find-file-noselect=, and
nothing here reaps it, so an unnarrowed walk of =all= can leave thousands
of Org buffers behind.  The prefilter is what keeps that number down.  A
file-count ceiling, above which a live walk would be refused and below
which it would be allowed, is the obvious way to sharpen this and is not
implemented.  See [[*Limitations of the prefilter]].


* The attribute registry
:PROPERTIES:
:DESCRIPTION: Declaring the corpus's own user attributes.
:END:
#+cindex: attribute registry
#+cindex: user attributes
#+cindex: registry file

An agent asks a question about your corpus.  The rest of this manual is
about the corpus itself: what its properties mean, where their values come
from, how they look on the screen, and what may be done to them in bulk.
Tinderbox calls that model *dynamic properties*, and it is the half of
Tinderbox that org-agents borrows beyond the agent.  See [[*The five ideas]].

The registry is where the model starts.  It is one optional Org file,
named by ~org-agents-attributes-file~, in which you write down what your
corpus's own properties are.

** Why declare attributes
:PROPERTIES:
:DESCRIPTION: What typing an untyped drawer buys you.
:END:
#+cindex: declaring an attribute
#+cindex: property drawer, untyped

Org's property drawer is untyped and open.  Any entry may carry any
property, spelled any way, holding anything; nothing anywhere says which
names your corpus actually uses, what values each of them admits, or which
of them you meant.  That openness is why the drawer is useful, and it is
also why a corpus that has grown for years contains =STATUS=, =Status=,
=STATE= and =PHASE=, three of which were the same idea once.

Tinderbox has no such problem, because a Tinderbox attribute must be
declared before a note can hold it: you name it, choose its type, give it
a default, and optionally list the values it should suggest.  See
[[*Attributes in Tinderbox]] for what that pane looks like and what it is
for.

A registry is that declaration, written as Org.  Declaring an attribute
buys four things, and each of them is a separate feature of this package:

- *completion*, corpus wide. ~org-agents-allowed-values~ offers a declared
  vocabulary to ~org-set-property~ in every Org buffer, where Org's own
  =NAME_ALL= convention offers it only in the file or subtree that spells
  it.  See [[*Completing declared values]].
- *a lint*. ~org-agents-check-attributes~ compares a scope against the
  registry and reports where they disagree: a name nothing declares, a
  value outside its vocabulary, a value that is not of its type.  See
  [[*Checking a corpus]].
- *column formats*. ~org-agents-attribute-columns~ builds a =COLUMNS=
  format out of chosen declarations, with a summary operator on the
  numbers.  See [[*A corpus-wide column view]].
- *defaults, for prototype resolution*. An attribute's =:ATTR_DEFAULT:= is
  the last step of the resolution order, so a declared default is a value
  every entry in the corpus has without any entry spelling it.  See
  [[*The resolution order]].

Nothing else in the package requires a registry.  Agents, queries, views
and updating all work with no registry at all, and a missing or unreadable
registry declares nothing and says nothing about it.

** The registry file
:PROPERTIES:
:DESCRIPTION: One file, one top-level entry per attribute.
:END:
#+vindex: org-agents-attributes-file
#+cindex: registry file, where it lives

Set ~org-agents-attributes-file~ to the file you want to keep the
declarations in.  The default is =~/org/attributes.org=, which this package
will never create for you and never assumes exists.

Each *top-level* entry of that file declares one attribute:

- the *heading* is the attribute's name, spelled exactly as the property
  is spelled in a drawer;
- the *drawer* carries the declaration;
- the *body* is the attribute's documentation, for you and for anyone else
  reading the file.

#+begin_src org
,* STATUS
  :PROPERTIES:
  :ATTR_TYPE:    string
  :ATTR_VALUES:  active paused blocked done
  :ATTR_DEFAULT: active
  :ATTR_FACES:   blocked error | paused shadow | done success
  :END:
  The state of a piece of work, independent of its TODO keyword.

,* NEXT_REVIEW
  :PROPERTIES:
  :ATTR_TYPE: date
  :END:
  The day this entry should next be looked at.

,* REVIEWS
  :PROPERTIES:
  :ATTR_TYPE:    number
  :ATTR_DEFAULT: 0
  :END:
  How many times this entry has been reviewed.
#+end_src

#+cindex: registry file, drawer placement

*The drawer must sit immediately under the heading.* Org keeps a property
drawer there and looks nowhere else, so a drawer written after the body
text is not a property drawer at all.  The entry is then reported as
declaring no type, which is a true statement about a file whose real
mistake is one blank line higher up.  This is the single easiest way to
write a registry that reports itself empty, so put the drawer first in
every entry you write.

One heading in the file is reserved: a top-level =Prototypes= section,
whose entries are not declarations but masters.  See [[*Declaring masters]].

** The declaration
:PROPERTIES:
:DESCRIPTION: The four ATTR_ properties.
:END:
#+cindex: @samp{ATTR_TYPE}, registry property
#+cindex: @samp{ATTR_VALUES}, registry property
#+cindex: @samp{ATTR_DEFAULT}, registry property
#+cindex: @samp{ATTR_FACES}, registry property

Four properties make up a declaration.  Only the first is required, and it
is what makes an entry a declaration at all.  Their exact contracts are in
[[*Registry properties]]; what follows is what they are for.

=:ATTR_TYPE:= is one of =string=, =number=, =date=, =boolean=, =set= or
=list=. See [[*The six types]].

=:ATTR_VALUES:= is the values the attribute admits, separated by
whitespace.  Tinderbox calls these *suggested values*, and separates them
with semicolons; here the separator is whitespace, because whitespace is
what Org's own =NAME_ALL= convention uses and therefore what
~org-property-get-allowed-values~ already reads.  A trailing =:ETC= leaves
the vocabulary open, which is Org's own spelling of that: the values are
offered for completion, and a value not among them is still admitted.
=:ETC= reaches Org unfiltered, because Org is what reads it.

=:ATTR_DEFAULT:= is the default, written as text.  It is the last step of
the prototype resolution order, and it stays the trimmed string the file
holds: never a parsed number, never a decoded time.

=:ATTR_FACES:= maps values to Emacs faces, for ~org-agents-faces-mode~.
See [[*The ATTR_FACES syntax]].

#+findex: org-agents-attribute

A declaration is available to Lisp as a plist, which is the most direct
way to see what the reader made of your file:

#+begin_example
(org-agents-attribute "STATUS")
  => (:name "STATUS" :type string
      :values ("active" "paused" "blocked" "done")
      :default "active"
      :faces (("blocked" . error) ("paused" . shadow) ("done" . success))
      :doc "The state of a piece of work, independent of its TODO keyword."
      :file "…/attributes.org" :line 1)
#+end_example

** The six types
:PROPERTIES:
:DESCRIPTION: What each type admits, and what it refuses.
:END:
#+cindex: attribute types
#+cindex: @samp{set}, attribute type
#+cindex: @samp{list}, attribute type

#+attr_texinfo: :table-type table :indic code
- string ::
  #+cindex: @samp{string}, attribute type
  Any text.  With a declared vocabulary the whole trimmed value must be a
  member of it, compared case sensitively: a declared vocabulary is one
  you wrote down.

- number ::
  #+cindex: @samp{number}, attribute type
  A signed integer or decimal, with *no exponent*: =3=, =3.5=, =.5=, =-3=.
  Anchored at both ends, so the whole value must be one number.  That is
  what catches an accumulated property: a =:REVIEWS: 3= beside a
  =:REVIEWS+: 4= reads back as the text =3 4=, and that is not a number.
  =1e3= is refused, on the grounds that in an Org drawer it is far more
  likely to be a product code than a thousand.

- date ::
  #+cindex: @samp{date}, attribute type
  A value that parses *and names a real day*. Both halves are needed:
  Org's own parser reads =[2026-02-30 Fri]= as day 30 of February without
  complaint, so the round trip through ~encode-time~ and ~decode-time~ is
  what catches it.

- boolean ::
  #+cindex: @samp{boolean}, attribute type
  =true= or =false=, unquoted, lower case, and nothing else.  Not =t=, not
  =yes=, not =True=. The reader synthesizes the two values onto every
  boolean declaration, so a =:ATTR_VALUES:= on a boolean has no meaning
  and is ignored with a warning.

- set ::
  Whitespace-separated members, every one of them admitted by the
  vocabulary, *and no member repeated*. The empty set is valid.

- list ::
  Whitespace-separated members, every one admitted by the vocabulary.
  Duplicates are fine and order is significant.

=set= and =list= are Tinderbox's distinction --- a set's members are
unique, a list's may repeat and are ordered --- but the correspondence
stops at the distinction.  Tinderbox *coerces*: "passing a List with
duplicate values to a Set will remove duplicates" (=tbxman920:1439--1440=).
This package *validates*: a repeated member makes the value invalid and the
lint says so, and nothing here canonicalises order or compares two sets
order-insensitively.  The separator is whitespace rather than semicolons.
See [[*Attributes in Tinderbox]] for the correspondence, and
[[*What it changed]] for why.

#+findex: org-agents-attribute-valid-p

The predicate behind all six is available to Lisp as
~org-agents-attribute-valid-p~. Some measured answers:

#+begin_example
(org-agents-attribute-valid-p 'boolean "true")            => t
(org-agents-attribute-valid-p 'boolean "t")               => nil
(org-agents-attribute-valid-p 'boolean "True")            => nil
(org-agents-attribute-valid-p 'number  "3.5")             => t
(org-agents-attribute-valid-p 'number  "1e3")             => nil
(org-agents-attribute-valid-p 'number  "3 4")             => nil
(org-agents-attribute-valid-p 'date    "2026-09-01")      => t
(org-agents-attribute-valid-p 'date    "2026-02-30")      => nil
(org-agents-attribute-valid-p 'set  "emacs org"   '("emacs" "org")) => t
(org-agents-attribute-valid-p 'set  "emacs emacs" '("emacs" "org")) => nil
(org-agents-attribute-valid-p 'list "emacs emacs" '("emacs" "org")) => t
#+end_example

** It is pure data
:PROPERTIES:
:DESCRIPTION: Nothing a registry holds is ever evaluated.
:END:
#+cindex: registry, pure data
#+cindex: evaluation, and the registry

A registry file is *data*, and that is a guarantee rather than a
description of the present implementation.  Every field is read with
~org-entry-get~ and then used as a string, as one of six symbols out of a
fixed table, or as a face name interned from text.  There is nothing a
registry file can hold that this package will ~read~, ~eval~, or run.

This is a deliberate divergence from Tinderbox, which has an =Action=
attribute type whose values are strings of action code *evaluated when
used*. A type like that is precisely what could not be ported without
giving up the guarantee above.  See [[*What was deliberately not ported, and why]].

Two further properties of the reader are worth knowing:

- *Malformation is contained.* A bad =:ATTR_TYPE:= costs its entry: the
  entry is named once and skipped.  A bad anything else costs only that
  field, warned once, with the rest of the declaration intact.  A missing
  or unreadable registry declares nothing and says nothing about it.
- *The file is read lazily, and at most once per edit,* including an edit
  you have not saved.  So a correction to a declaration takes effect at the
  next thing that reads it, without a reload and without a cache to clear.

A name that is one of Org's special properties may be declared, and the
reader warns once that no completion is possible for it, because Org
answers for those names out of clauses of its own.  The declaration is
still worth having: the lint reads it.

** Checking a corpus
:PROPERTIES:
:DESCRIPTION: org-agents-check-attributes, which reports and never edits.
:END:
#+findex: org-agents-check-attributes
#+cindex: lint, attribute
#+cindex: seeding a registry

A registry is easiest to write against a corpus that already exists, and
{{{kbd(M-x)}}} ~org-agents-check-attributes~ is how you find out what is
in yours.  It takes a scope, with exactly the vocabulary =:AGENT_SCOPE:=
takes, and it *reports*. Nothing is edited, ever.

It asks three questions:

1. is a property name in use that the registry does not declare?
2. is a value one that does not parse as its =:ATTR_TYPE:=?
3. is a value one that is outside its =:ATTR_VALUES:=?

Given the registry of [[*The example corpus]] with a =TOPICS= declaration
added --- so four declarations, =STATUS=, =NEXT_REVIEW=, =REVIEWS= and
=TOPICS=, the last of them a =set= admitting =emacs org tinderbox= --- and
this file in scope:

#+begin_src org
,* One
  :PROPERTIES:
  :STATUS:      wedged
  :NEXT_REVIEW: 2026-02-30
  :REVIEWS:     lots
  :WIDGET:      3
  :TOPICS:      emacs emacs
  :END:
#+end_src

the echo area says =org-agents: 5 findings over 1 file= and
=*org-agents attributes*=, in ~compilation-mode~, holds --- every path
absolute, and elided here:

#+begin_example
…/lint.org:3: STATUS: `wedged' is not one of active paused blocked done
…/lint.org:4: NEXT_REVIEW: `2026-02-30' is not a date
…/lint.org:5: REVIEWS: `lots' is not a number
…/lint.org:6: WIDGET is not declared in …/attributes.org (1 use)
…/lint.org:7: TOPICS: `emacs emacs' is not a set
#+end_example

All five kinds in one report: a value outside its vocabulary; a date that
parses but names no day; a value not of its type; an undeclared name, with
a *site count*; and a =set= with a repeated member.  Each line begins
=FILE:LINE:=, so {{{kbd(RET)}}} and ~next-error~ walk them.  A clean run
writes this into the buffer rather than popping an empty one, while the
echo area says =org-agents: 0 findings over 1 file=:

#+begin_example
org-agents: no findings; every property in scope is declared and valid
(1 file in scope, 1 read, 1 entry, 4 declarations)
#+end_example

Read =read= as it is written: how many files the run actually opened,
which on the fast path is fewer than the files in scope.

*A finding is one per name, not one per line.* An undeclared name in use
four thousand times is one finding with a count and one confirmed example
site.  Org's own vocabulary is never asked about, nor this package's
=AGENT_= and =ATTR_= names, nor a =_ALL= suffix, nor =ID=, nor the six
properties ~org-archive-subtree~ writes.  Without those exemptions =ID=
alone would be about thirty-seven thousand findings on the author's corpus.

#+vindex: org-agents-prefilter

*It never refuses.* Setting ~org-agents-prefilter~ to =require= does not
make it refuse: a lint that declined to run would fail its own contract.

#+cindex: seeding a registry, first run

*This command is how a registry gets seeded.* Run it over =all= against an
empty registry and every finding is of the first kind, which is a census
of your corpus's property vocabulary.  Measured on the author's corpus,
that vocabulary is 111 names, once the two drawer delimiters are set
aside.  Declare the ones you meant, ignore the ones you did not, and the
second run is about values rather than names.

The command runs in *two tiers*, because its two questions have different
costs.  The vocabulary question needs no Org semantics and is answered by
one ripgrep census over the whole scope, with each candidate then
confirmed against a real property drawer.  The value question needs
per-entry reading, but only for the *declared* names and only in the files
holding them.  Measured over a 3,616-file scope: 7 to 10 seconds warm and
64 to 110 seconds cold, against a single-tier version that was killed at
600 seconds with no report at all.  Treat that range as an order of
magnitude and not as a benchmark; the same vocabulary-only run over the
same scope measured 3.5 seconds on an idle machine and 12.8 seconds on one
busy with other work, so a figure outside the range is machine load and
not a regression.

** Completing declared values
:PROPERTIES:
:DESCRIPTION: org-agents-allowed-values on Org's own hook.
:END:
#+findex: org-agents-allowed-values
#+vindex: org-property-allowed-value-functions
#+cindex: completion, of property values

A declared vocabulary becomes completion by putting
~org-agents-allowed-values~ on Org's own hook:

#+begin_src emacs-lisp
(add-hook 'org-property-allowed-value-functions
          #'org-agents-allowed-values)
#+end_src

After that, ~org-set-property~ completes declared values in every Org
buffer, wherever the entry lives, which is what Tinderbox's pull-down menu
of suggested values does.  This is the corpus-wide counterpart of Org's own
=NAME_ALL= convention, which offers a vocabulary only in the file or
subtree that spells it.

*The hook is not added for you.* A library has no business mutating a
user's hook, and this one in particular decides what vocabulary is offered
for every property in every Org buffer you open.

The function is not a command; it takes one argument and answers a flat
list of strings, or nil for a property it is not responsible for.  Nil is
the important half: a non-nil answer *shadows* every =NAME_ALL= line in
the corpus, so it answers only for a name the registry declares with a
vocabulary.

#+begin_example
(org-agents-allowed-values "STATUS")       => ("active" "paused" "blocked" "done")
(org-agents-allowed-values "NEXT_REVIEW")  => nil     ; declared, no values
(org-agents-allowed-values "WIDGET")       => nil     ; not declared
#+end_example

A boolean answers ~("true" "false")~ from the two values the reader
synthesizes, so completion needs no special case for the type.  A
vocabulary that is =:ETC= and nothing else is declined, because Org
removes the marker and would be left with nothing after the non-nil answer
had already shadowed the corpus.

** A corpus-wide column view
:PROPERTIES:
:DESCRIPTION: org-agents-attribute-columns, and the recipe it completes.
:END:
#+findex: org-agents-attribute-columns
#+findex: org-agenda-columns
#+kindex: C-c C-x C-c
#+cindex: column view, corpus-wide
#+cindex: displayed attributes

Tinderbox shows a table of chosen attributes across a set of notes, and
lets you edit the values in it.  Org has all of the pieces for that
already: =COLUMNS= formats, ~org-columns~, ~org-agenda-columns~, and
write-back editing in a column view.  Measured, ~org-agenda-columns~
already runs inside an ~org-ql-search~ results buffer, so corpus-wide
displayed attributes *with write-back editing exist today*. What was
missing was the format string, and this command is it.

#+begin_example
M-x org-agents-attribute-columns RET STATUS,NEXT_REVIEW,REVIEWS RET
  => "%ITEM %STATUS %NEXT_REVIEW %REVIEWS{+}"
#+end_example

=%ITEM= comes first, so a column view has something to name its rows by,
then one =%NAME= per attribute in the order you gave, with a ={+}= summary
operator on the numbers. =number= is the one type that gets an operator.

With a prefix argument the command also puts the format on the entry at
point, as the =:COLUMNS:= *property* rather than a =#+COLUMNS:= keyword:
the property is what descendants inherit, and it is what
~org-agenda-columns~ reads for a matched entry.

The recipe, then, is three steps:

1. build the format with this command, and put it where the entries you
   care about will inherit it;
2. run ~org-ql-search~ over the corpus for the entries you want in the
   table;
3. press {{{kbd(C-c C-x C-c)}}} in the results buffer, which is
   ~org-agenda-columns~.

Two names are refused rather than emitted, and each refusal closes the
same hole.  An *undeclared* name is refused, because a =COLUMNS= line
naming a property nothing declares renders an empty column, which looks
exactly like a property nothing has set: the mistake would show up as a
corpus with no data in it rather than as a mistake.  So is a declared name
that a =COLUMNS= format cannot spell, such as =PROJECT.PHASE=, which would
render as a column headed =PROJECT= that nothing ever fills.

** Limitations of the registry
:PROPERTIES:
:DESCRIPTION: What a corpus-scope lint leaves behind.
:END:
#+cindex: limitations, of the registry

*A corpus-scope lint leaves every file in scope visited.*
~org-agents-check-attributes~ opens each file it reads with
~find-file-noselect~ and kills nothing afterwards: a buffer this command
opened is indistinguishable, from inside, from one you had open already.
Over =all= that can be a few thousand buffers, with no message saying so.
They are ordinary file buffers, unmodified, because the lint edits
nothing, so nothing is at risk; but memory and every buffer-list operation
afterwards feel it.

The two-tier split makes this much better in the common case and does not
remove it.  Against an *empty* registry the value tier reads nothing at
all, and the run's whole footprint is the confirmation pass: measured,
about 150 file opens for 112 candidate names, not 3,616.  Against a
registry that declares a name appearing in every file, the tier reads
every file and the old footprint is back.  The clean report's counts say
which happened, which is what =3,616 files in scope, 3,616 read= against
=3,616 files in scope, 0 read= is for.

The remedy is the ordinary one: kill the unmodified Org buffers once you
have worked through the report, with ~clean-buffer-list~, with
{{{kbd(M-x)}}} ~ibuffer~ and =* u=, or by restarting the session you ran
the seeding lint in.  Run the =all= scope deliberately rather than
casually.

* Prototypes
:PROPERTIES:
:DESCRIPTION: Inheritance that relates two entries, not two positions.
:END:
#+cindex: prototype
#+cindex: @samp{PROTOTYPE}, property
#+cindex: inheritance, prototype

Org already has one kind of property inheritance: a value written on an
ancestor is visible to its descendants.  That is inheritance along the
*outline*, and it answers the question "where is this entry filed?".

Prototypes answer a different question: "what kind of thing is this
entry?".  They are Tinderbox's, and like Tinderbox's they have nothing to
do with the outline.  See [[*Prototypes in Tinderbox]] for the idea in
Tinderbox's own words.

** What a prototype is
:PROPERTIES:
:DESCRIPTION: A relation between two entries.
:END:
#+cindex: master, prototype
#+cindex: follower, prototype

A prototype is a relation between two entries.  One entry, the *master*,
holds properties; another entry names it in =:PROTOTYPE:= and thereby
reads through it.  Where the reading entry says nothing about a property,
the master's value answers.

#+begin_src org
,* TODO Audit the prefilter
   :PROPERTIES:
   :PROTOTYPE: Blocked Task
   :END:
#+end_src

That entry's drawer spells no =:STATUS:= at all, and yet its =STATUS=
resolves to =blocked=, because the master named =Blocked Task= says so.

Two facts follow from calling this a relation rather than a position:

- *The master may be any entry.* It need not be an ancestor, a sibling, or
  in the same file.  Nothing about where either entry sits is involved.
- *An entry has one prototype, and a prototype has any number of
  followers.* One is a chain, not a lattice: the master may itself name a
  master, and so on.  That is Tinderbox's rule as well.

** Declaring masters
:PROPERTIES:
:DESCRIPTION: The reserved Prototypes section.
:END:
#+cindex: @samp{Prototypes} section

The registry file carries one reserved top-level heading, =Prototypes=,
whose every entry is a master.  A master is an *ordinary entry whose drawer
holds ordinary properties*: there is no declaration syntax, and none is
wanted, because what a master lends is exactly what it holds.

#+begin_src org
,* Prototypes
,** Task
   :PROPERTIES:
   :STATUS: active
   :OWNER:  johnw
   :END:
,** Blocked Task
   :PROPERTIES:
   :PROTOTYPE: Task
   :STATUS:    blocked
   :END:
#+end_src

=Blocked Task= names =Task= in its own =:PROTOTYPE:=, so the two form a
chain: an entry reading through =Blocked Task= gets =blocked= for =STATUS=
and =johnw= for =OWNER=.

The section is skipped silently by the declaration reader, where any other
top-level entry with no =:ATTR_TYPE:= would be named.  Tinderbox keeps its
own built-in prototypes in a top-level container of the same name.

** Naming a master
:PROPERTIES:
:DESCRIPTION: By name, or by id:UUID.
:END:
#+cindex: @samp{PROTOTYPE}, naming a master
#+vindex: org-id-locations

=:PROTOTYPE:= names a master in one of two ways:

- *by name*, matched against the headings of the registry file's
  =Prototypes= section: =:PROTOTYPE: Blocked Task=;
- *by id*, as =:PROTOTYPE: id:e1000000-0000-0000-0000-000000000009=, which
  resolves to the entry carrying that =:ID:= wherever ~org-id-locations~
  says it lives.  Any entry in the corpus may be a master this way, with no
  registry involved at all.

~org-id-locations~ is the id form's one precondition.  The resolver
consults that table rather than searching for the id, so a reference the
table does not know about is a dangling reference and is reported as one:
see [[*The two diagnostics]].

Outside this package's own =AGENT_= and =ATTR_= vocabularies, =PROTOTYPE=
is one of a short list of properties org-agents reads by name.  The others
are =ID=, which the =children= and =list= views read to build a link and
which the id form above resolves through; the properties the action verbs
read and edit --- =SCHEDULED=, =DEADLINE=, =PRIORITY=,
~org-effort-property~, and =ARCHIVE= read *with inheritance*, which is how
~archive!~ works out its destination and why ~set-property!~ refuses to
write it (see [[*The nine verbs]]); and =COLUMNS=, which
~org-agents-attribute-columns~ writes with a prefix argument (see
[[*A corpus-wide column view]]).  Nothing else in a drawer is read by name
by this package: everything else reaches it through a query you wrote or a
declaration you made.

** The resolution order
:PROPERTIES:
:DESCRIPTION: Where a resolved value comes from, in order.
:END:
#+cindex: resolution order
#+cindex: @samp{ATTR_DEFAULT}, in resolution

Resolving one property at one entry consults four things, in this order,
and stops at the first that answers:

1. *the entry's own drawer*, read with inheritance *off*;
2. *the prototype chain*, nearest hop first;
3. *the registry's* =:ATTR_DEFAULT:= for that name;
4. *nil*.

This is Tinderbox's own checklist, with its two prototype steps --- the
prototype's value, then the prototype's prototype's --- written as one
walk of the chain, and with one step Tinderbox does not need: an
undeclared property has no default to fall back to, where every Tinderbox
attribute is typed and therefore always has one.  See
[[*Prototypes in Tinderbox]] for the passage it comes from.  The chain is
bounded at a thousand hops, which is a guard against a malformed corpus
and not a budget.

Step 1 reads the drawer raw.  A present-but-empty =:NAME:= answers the
empty string, which org-ql's own ~property~ predicate matches, so
resolution must match it too.

With the registry and masters above, and the first four entries of
[[*The example corpus]] --- whose properties that bear on this are these,
and which carry others the resolution does not consult:

#+begin_src org
,* Projects
  :PROPERTIES:
  :OWNER: johnw
  :END:
,** TODO Rewrite the exporter
   :PROPERTIES:
   :STATUS: active
   :END:
,** TODO Audit the prefilter
   :PROPERTIES:
   :PROTOTYPE: Blocked Task
   :END:
,** DONE Ship 0.1
   :PROPERTIES:
   :STATUS: done
   :END:
#+end_src

resolution answers as follows.  The =own= column is ~org-entry-get~ with no
inheritance, which is what a drawer, a grep and org-ql's ~property~ all
see; the other two are ~org-agents-resolve-property~.

| Entry                | own =STATUS= | resolved =STATUS= | resolved =OWNER= |
|----------------------+--------------+-------------------+------------------|
| Projects             | nil          | =active=          | =johnw=          |
| Rewrite the exporter | =active=     | =active=          | nil              |
| Audit the prefilter  | nil          | =blocked=         | =johnw=          |
| Ship 0.1             | =done=       | =done=            | nil              |

Every step of the order is visible in that table. =Projects= spells no
=STATUS= and reaches =active= at step 3, from =:ATTR_DEFAULT:=. =Audit the
prefilter= spells no =STATUS= and reaches =blocked= at step 2, from the
nearest hop of its chain, and =johnw= from the hop beyond it. =Ship 0.1=
answers from its own drawer at step 1, which is why the registry's default
does not override it.

** Why outline inheritance is not in that order
:PROPERTIES:
:DESCRIPTION: Containment is not inheritance.
:END:
#+cindex: outline inheritance, contrasted
#+cindex: containment, is not inheritance

Look again at =Rewrite the exporter= in the table above.  Its parent
=Projects= sets =:OWNER: johnw=, and its resolved =OWNER= is *nil*.

That is not an oversight. *Containment is not inheritance.* A task filed
under a project is not a kind of project; a note filed under =Reading= is
not a kind of reading.  Where a corpus does mean the outline, Org's own
property inheritance already says so, and the query layer spells that axis
=$NAME*= (see [[*The two axes]]). =$NAME^= is this axis.  The two are
orthogonal, and a query has to say which it means because the two answer
differently: over the corpus above, =$OWNER*= finds the two entries under
=Projects= and =$OWNER^= finds =Projects= itself along with the entries
whose chains reach a master that sets it.  The two answers share no entries
at all.

Tinderbox is explicit about this: "inheritance has nothing to do with the
document hierarchy; a note's prototype is not necessarily its container."
Of the five ideas org-agents borrows, this is the one where the agreement
is strongest.

** Reads are virtual
:PROPERTIES:
:DESCRIPTION: Nothing is written into the inheriting entry, and what that costs.
:END:
#+cindex: virtual resolution
#+cindex: grep, and inherited values

Resolution is a *read*. Nothing is ever written into the inheriting entry:
no property is copied down, no subtree is materialised, no cache is
persisted anywhere in your files.  So a master may be changed once and
every follower changes with it, which is the whole point of the mechanism
and is Tinderbox's own promise about it.

The price is worth stating plainly, because a reader will otherwise
discover it at an inconvenient moment.

#+cindex: inherited value, invisible to grep

*Grep does not see an inherited value.* Nor does ~org-entry-get~, nor a
column view, nor org-ql's own ~property~ predicate.  Over
[[*The example corpus]], =grep blocked= finds three lines, all of them in
the registry file and all of them declarations --- the vocabulary, the
face map, and the master's own drawer --- and it finds nothing in
=corpus.org= at all, even though one entry there resolves to =blocked=.

#+findex: property-resolved
#+findex: org-agents-resolve-property

What *does* see it is:

- ~property-resolved~, the org-ql predicate this package defines, which is
  what =$NAME^= expands to.  So the agent whose query is
  ~(property-resolved "STATUS" "blocked")~ matches =Audit the prefilter=,
  which spells no =:STATUS:= anywhere.  See [[*The property-resolved predicate]].
- ~org-agents-resolve-property~, for a caller in Lisp.
- ~org-agents-faces-mode~, which reads the resolved value and is the
  reason the mode is worth having at all.  See [[*Faces from attribute values]].

The rule to carry away is therefore: *an inherited value is real to a
query and invisible to a text search*. Where you need the second, spell
the value in the drawer; where you need one authoritative place to change
it, use a master.

** Names that never travel
:PROPERTIES:
:DESCRIPTION: What a master does not lend.
:END:
#+cindex: non-inherited properties
#+cindex: @samp{AGENT_} properties, never inherited

Three kinds of name answer from the entry's own drawer and stop there,
whatever a master or a registry default says.

- *Every* =AGENT_= *name*, because behaviour does not travel.  A master
  lending its =:AGENT_QUERY:= would make every follower an agent, and a
  registry default for such a name would make every entry in the corpus
  one.  The same reasoning is why an action is not inheritable; see
  [[*The three refusals]].
- =PROTOTYPE= *itself*, because a declared default for it would hand every
  entry in the corpus a master.
- *Org's special properties.* A master's =CATEGORY= is not this entry's.

Measured, with a master that carries =:AGENT_QUERY:=, =:PROTOTYPE:= and
=:CATEGORY:= along with a =:STATUS:=, at a follower that spells only
=:PROTOTYPE: Task=:

#+begin_example
(org-agents-resolve-property "STATUS")       => "active"   ; nearest hop
(org-agents-resolve-property "AGENT_QUERY")  => nil        ; never travels
(org-agents-resolve-property "PROTOTYPE")    => "Task"     ; its own, not the master's
(org-agents-resolve-property "CATEGORY")     => "follower" ; Org's answer, not the master's
#+end_example

Tinderbox has a comparable exclusion, its *intrinsic* attributes, chosen
for a partly different reason and over a different list; see
[[*What it changed]].

** The two diagnostics
:PROPERTIES:
:DESCRIPTION: A dangling reference, and a cycle.
:END:
#+cindex: dangling prototype
#+cindex: prototype cycle

Two things can be wrong with a chain, and each is said *once per update*
rather than once per entry or once per redisplay.

A *dangling reference*, a =:PROTOTYPE:= naming a master that is not there,
is one message naming the entry that made the reference:

#+begin_example
org-agents: no prototype ‘Nonesuch’ named by ‘Dangling’ in …/proto.org:1
#+end_example

Resolution then carries on at the next step of the order, so the entry
still gets the registry's default if there is one.  A dangling reference
costs you the chain and not the answer.

A *cycle* is a ~user-error~ naming the hops:

#+begin_example
org-agents: prototype cycle at ‘Looping’ in …/cycle.org:1: A -> B -> A
#+end_example

#+findex: org-agents-resolve-property-quietly

Two entry points into resolution differ in what they do with a cycle, and
the difference matters if you are writing Lisp against this.
~org-agents-resolve-property~ signals, which is right for a command.
~org-agents-resolve-property-quietly~ reports instead, and is what
residual Lisp and the ~property-resolved~ predicate use, because a
~user-error~ raised from inside org-ql's generated matcher would abort the
whole update over one malformed entry.

** Limitations of prototypes
:PROPERTIES:
:DESCRIPTION: What virtual resolution costs the prefilter.
:END:
#+cindex: limitations, of prototypes

Virtual resolution costs the ripgrep prefilter some of its narrowing, and
it has to: an inheriting entry never spells the value, so the ordinary
pattern would drop its file with no error at all.  A ~property-resolved~
conjunct therefore pushes a *widened* pattern, the local =:NAME:= line or a
=:PROTOTYPE:= line as one alternation; and where the registry declares an
=:ATTR_DEFAULT:= the query could match, an entry spelling *neither* line
matches too, nothing can narrow, and the conjunct stays residual.  Both
cost candidate files and never an answer.  See
[[*Inheritance and pushability]] for the full account.

* Appearance
:PROPERTIES:
:DESCRIPTION: Drawing a headline from a resolved attribute value.
:END:
#+cindex: appearance
#+cindex: faces, from attribute values

In Tinderbox a note's colour is an attribute, and a rule or an agent
action assigns it: "an agent that contains 'urgent tasks' can
automatically change their color in order to draw your attention"
(=tbxman920:2792=).  The
idea is that a document's appearance should follow from its data rather
than from a separate act of formatting.

org-agents keeps the idea and changes the mechanism completely, for one
reason: in Tinderbox, setting =$Color= is a *write* to a note, and here it
would be a write to a text file under version control.  So appearance in
org-agents is a *declaration* that is read, never an action that is
applied.

** Faces from attribute values
:PROPERTIES:
:DESCRIPTION: org-agents-faces-mode.
:END:
#+findex: org-agents-faces-mode
#+cindex: minor mode, for faces

~org-agents-faces-mode~ is a buffer-local minor mode, lighter =" Attrs"=,
which draws a headline in the face that its *resolved* value for a
declared attribute names.  It needs an Org buffer and refuses politely in
anything else.

Resolved is the point of the mode.  An entry that spells only
=:PROTOTYPE: Task=, or that spells nothing at all and takes
=:ATTR_DEFAULT:=, is faced exactly as one that spells the value in its own
drawer.  Grep does not see an inherited value and neither does the drawer
under your eye; the face does, and reading a corpus is what that is for.

Where several declared attributes name faces, every one of them is
consulted in *registry declaration order*, and the first that resolves to
a value it maps wins.

** The ATTR_FACES syntax
:PROPERTIES:
:DESCRIPTION: How an attribute's values are mapped to faces.
:END:
#+cindex: @samp{ATTR_FACES}, syntax

=:ATTR_FACES:= is pipe-separated two-word groups: a value, whitespace, a
face name.

#+begin_src org
:ATTR_FACES: blocked error | paused shadow | done success
#+end_src

Which reads: draw a headline whose resolved =STATUS= is =blocked= in
~error~, =paused= in ~shadow~, and =done= in ~success~. A value the
declaration does not mention maps to no face, and such a headline is left
exactly as Org drew it.

Face names are read with ~intern~ and never with ~read~, because the
registry is data.  A declaration that does not split cleanly into two-word
groups yields no faces, warned once; it costs the faces and not the rest
of the declaration.

** From declaration to headline
:PROPERTIES:
:DESCRIPTION: A worked appearance example.
:END:
#+cindex: faces, worked example

Take the registry's =STATUS= declaration from [[*The registry file]], whose
=:ATTR_FACES:= is the line above and whose =:ATTR_DEFAULT:= is =active=,
and all nine entries of [[*The example corpus]].  Turn the mode on and
fontify.
Measured, headline by headline, with the resolved value beside the ~face~
text property actually on the line:

#+begin_example
Projects                 STATUS=active   face=org-level-1
Rewrite the exporter     STATUS=active   face=(org-todo org-level-2)
Audit the prefilter      STATUS=blocked  face=(error org-todo org-level-2)
Ship 0.1                 STATUS=done     face=(success org-done org-level-2)
Errands                  STATUS=active   face=org-level-1
Renew the passport       STATUS=active   face=(org-todo org-level-2)
Collect the print        STATUS=active   face=(org-todo org-level-2)
Reading                  STATUS=active   face=org-level-1
Tinderbox notes          STATUS=active   face=org-level-2
#+end_example

Three things to read out of that run.

=Audit the prefilter= is drawn in ~error~ although its drawer spells no
=:STATUS:= at all: the value arrives through its prototype chain, which is
exactly why the mode reads the resolved value.

=active= maps to no face, so most of the corpus is left as Org drew it.
The mode is a way of marking the exceptional, not a way of colouring
everything.

The attribute's face is *prepended* to what Org already put there, not
substituted for it.  So =Ship 0.1= reads ~(success org-done org-level-2)~:
the colour follows the attribute while the height, the family and Org's
own done-state face all survive underneath.

** It changes no bytes
:PROPERTIES:
:DESCRIPTION: One font-lock keyword, and nothing else.
:END:
#+cindex: faces, changes no bytes

The whole of this mode is *one font-lock keyword*. No text is inserted, no
property is written into the file, no overlay is created.  The ~face~ text
property that font-lock manages, and removes again, is the entire
mechanism.

Measured on the run above: ~(buffer-modified-p)~ afterwards is nil, and
turning the mode off leaves no ~face~ property behind.  The third headline
of that corpus reads ~(error org-todo org-level-2)~ with the mode on and
~(org-todo org-level-2)~ with it off, which is Org's own answer and
nothing more.

That is what makes the mode safe to leave on in a file under version
control, and it is the difference between reading an attribute for
appearance and writing a =$Color= into a note.

** Faces in every Org buffer
:PROPERTIES:
:DESCRIPTION: global-org-agents-faces-mode.
:END:
#+findex: global-org-agents-faces-mode
#+findex: global-org-agents-mode

~global-org-agents-faces-mode~ turns ~org-agents-faces-mode~ on in *every*
Org buffer, and deliberately not only in those whose text mentions a
declared property.

That is a considered difference from ~global-org-agents-mode~, which does
scan a buffer's text for =:AGENT_QUERY:= before arming it.  The two tests
differ because the two features differ: an agent is spelled in the file it
lives in, so a text scan finds every buffer that has one, while *a value
arriving through a prototype or a registry default is spelled nowhere*. A
text scan would miss precisely the entries this mode exists for.

It is affordable because the matcher answers nil before resolving anything
where nothing declares a face, and because it reads only the entry at its
match and honours the region font-lock hands it.  Measured over a 400-entry
buffer of which one entry is drawn, under a registry declaring two
face-bearing attributes, a twelve-line window costs 5 resolutions where
the whole buffer costs 799; a headline outside the fontified region
carries no ~face~ property at all.  Under a registry declaring one
face-bearing attribute the same figures are 3 against 400.  The cost scales
with what is displayed and with how many attributes name faces, not with
the size of the corpus.

** Precedence, and following an edit
:PROPERTIES:
:DESCRIPTION: Where the face sits in the list, and the one gap.
:END:
#+cindex: font-lock precedence
#+cindex: faces, following an edit

The keyword is added at the *end* of ~font-lock-keywords~ and applies with
~prepend~. Both are load-bearing.  Org's own headline keyword applies only
where no face is set yet, so whichever keyword runs first claims the
headline outright: added at the front, this mode's face destroys
~org-level-N~ and takes the height and the family with it.  Added last and
prepending, it wins attribute by attribute and Org's face survives
underneath, which is the ~(error org-todo org-level-2)~ above.

The face *follows an edit to the value it is drawn from*. The face is on
the headline and the value is in the drawer below it, and an ordinary edit
refontifies only its own line, so the mode extends the region font-lock
was about to redraw to include the headline above the drawer.

*The one gap.* An edit to the *registry*, or to a *master in another
buffer*, is not followed.  A buffer already fontified keeps the colour it
was drawn with until something refontifies it: {{{kbd(M-x)}}}
~font-lock-flush~, or scrolling away and back.  Nothing here watches other
files, and a mode that did would be watching the whole corpus.

** The two refusals
:PROPERTIES:
:DESCRIPTION: No geometry, and no writes.
:END:
#+cindex: refusals, appearance
#+cindex: geometry, not ported

Two things a reader may look for here are refusals rather than omissions,
and both are worth stating in the same breath as the feature.

*No geometry.* Tinderbox's =$Width=, =$Height=, =$Xpos= and =$Ypos=
describe a map view.  Org has no map, so there is nothing in an outline for
them to mean: they are not ported, and no spelling of them is reserved.
See [[*What was deliberately not ported, and why]].

*No writes of any kind from an appearance declaration.* Setting a tag or a
TODO state from a resolved value would be action code arriving through
another door, and *inheritable* action code at that: a master's
declaration running in every follower's file makes per-file trust
meaningless.  Anything that edits your corpus goes through the action-code
trust model or not at all.  See [[*The trust model]].

* Action code
:PROPERTIES:
:DESCRIPTION: Doing something to the entries an agent matched.
:END:
#+cindex: action code
#+cindex: @samp{AGENT_ACTION}, property

An agent may carry an *action* as well as a query: =:AGENT_ACTION:=,
holding a declarative sentence over a fixed vocabulary of nine verbs, each
of which edits the entries the query matched.

This is Tinderbox's =$AgentAction=, and it is the one part of org-agents
that writes outside the agent's own file.  Three refusals are what make
that affordable to reason about, and they come before the syntax because
they are the more important half.

** The three refusals
:PROPERTIES:
:DESCRIPTION: What an action never does, and why.
:END:
#+cindex: refusals, action code

*An action never runs on save, on a timer, or from either minor mode.* The
only thing in this package that runs an action is
~org-agents-apply-actions~, typed.  That is *structural* rather than a
promise kept by discipline: the action text is not part of the plist the
save path reads, so it does not exist as data anywhere along it.  The one
read of =:AGENT_ACTION:= in the whole package is inside that command.

Tinderbox has =$Rule=, performed at frequent intervals, and =$Edict=,
performed at startup and roughly hourly.  Neither is ported.  A Tinderbox
document is one binary file the application owns while it is open; an Org
corpus is thousands of text files under version control that other tools
also write.  Code that edits those files while you are not looking is a
commit nobody authored.  See
[[*What was deliberately not ported, and why]] for the rest of that
accounting, in Tinderbox's own vocabulary.

*An action is not inheritable.* =:AGENT_ACTION:= is read from the entry's
own drawer, with ~org-entry-get~ and no INHERIT argument, and never
through ~org-agents-resolve-property~. So no prototype, no outline
ancestor, no =#+PROPERTY:= line and no ~org-global-properties~ setting can
supply one.  The reason is per-file trust: if any of those could, then the
code that edits your corpus when you act on file A would be written in
file B, and reading a file before trusting it would mean nothing.  This is
a deliberate divergence from Tinderbox, whose =$Rule= is normally
inherited and whose own worked example is a rule inherited from a =Task=
prototype.

*Nothing in the property is ever evaluated.* The parser is a regexp lexer;
a token becomes a function by name construction plus ~fboundp~; arguments
reach a verb as strings.  There is no expression language, no assignment,
no conditional, no iteration, and nothing resembling Tinderbox's
~runCommand~. The worst thing expressible in an =:AGENT_ACTION:= is a
bounded, greppable Org edit.

** Writing an action
:PROPERTIES:
:DESCRIPTION: The declarative sentence, and its syntax.
:END:
#+cindex: action, syntax

An action is a sentence of verbs, applied left to right at every matched
entry:

#+begin_src org
,* Stamp what I reviewed today
  :PROPERTIES:
  :AGENT_QUERY:  (and (todo "TODO") (property "NEXT_REVIEW"))
  :AGENT_ACTION: set-property!(REVIEWED, today) tag!(+reviewed)
  :END:
#+end_src

Every verb's name ends in =!=, which is the convention this vocabulary
uses to mark that it writes.  Arguments go in parentheses, separated by
commas, and may be quoted or bare: a bare argument is anything but a
comma, a parenthesis or a quotation mark, and a quoted argument admits
backslash escapes.  A verb taking no argument, ~archive!~, is written
without parentheses.

The parser reads no buffer, creates none and writes nothing.  Every
diagnostic it can raise fires before the query has run, so a typo does not
even open the corpus:

#+begin_example
org-agents: :AGENT_ACTION: `frobnicate!' is not an action verb
  (there is no `org-agents-action/frobnicate!')
org-agents: :AGENT_ACTION: `archive!' must be the last verb
#+end_example

Everything else is checked in the *plan* phase, at the match, before
anything is written.  That is where a verb learns which buffer it is in,
which is what a check against buffer-local TODO keywords needs.

** The nine verbs
:PROPERTIES:
:DESCRIPTION: The whole vocabulary, and what each refuses.
:END:
#+cindex: action verbs, the nine
#+kindex: C-c C-t

The vocabulary is closed at nine.  Their exact argument lists are in
[[*Action verbs]]; what follows is what each is for and what it will not do.

~set-property!(NAME, VALUE)~ sets a property.  It refuses several names,
and each refusal closes a hole rather than tidying the vocabulary.  Org's
*special properties* are refused with the verb that does edit them named
instead: =TODO= sends you to ~todo!~, =PRIORITY= to ~priority!~,
=SCHEDULED= to ~scheduled!~, =DEADLINE= to ~deadline!~, =TAGS= to ~tag!~.
Any =AGENT_= name and =PROTOTYPE= are refused because an action that could
write them would *plant* an agent, a prototype link or action text into a
file you have never edited, undoing the per-file trust the
non-inheritance rule exists to keep. =ARCHIVE= is refused because it
steers where ~archive!~ puts a subtree, and the dry run would have named
the destination it read before that.

~delete-property!(NAME)~ removes a property.  It is destructive: see
[[*Destructive verbs and batch]].

~tag!(+added -removed)~ adds and removes tags, given whitespace-separated
*signed* terms applied left to right.  An unsigned term is refused:

#+begin_example
org-agents: :AGENT_ACTION: `tag!' term `reviewed' must be `+TAG'
  to add it or `-TAG' to remove it
#+end_example

This is *deliberately not* org-edna's ~tag!~, and the divergence is the
point.  That one hands a whole tag specification to ~org-set-tags~ and
therefore *replaces* the entry's tags.  Over an agent's match set that is a
silent mass deletion, from a verb whose one-word form looks additive.

~todo!(STATE)~ sets the TODO keyword.  STATE is checked against
~org-todo-keywords-1~ *read in the match's own buffer*, because those
keywords are buffer-local and a corpus may spell different ones file by
file.  A *repeating* entry is refused, and this one is a disappointment
taken deliberately: measured, ~org-todo~ on a repeating entry does not
leave it in the state it was asked for at all, but shifts the stamp and
writes =:LAST_REPEAT:=. A dry run cannot show any of that, and the line
you approved said =TODO -> DONE=. Advancing a repeater is a per-entry
judgement, which is what {{{kbd(C-c C-t)}}} is for.

The verb sets the keyword and *nothing else*: no =CLOSED= stamp, no state
note, no statistics cookie refreshed in an ancestor, no tag trigger, and
no org-edna trigger.  That is a consequence of the apply pass binding the
hooks and the logging off, which is what keeps a run inside the rows its
report showed; [[*The blast radius]] gives the list and the argument.  If
you want an entry's whole state change, {{{kbd(C-c C-t)}}} is the command
that does it.

~priority!(LETTER)~ takes one upper-case letter inside
~org-priority-highest~ to ~org-priority-lowest~, and names the range when
it refuses.

~scheduled!(DATE)~ and ~deadline!(DATE)~ take the same shapes and make the
same refusal.  The shape check exists to close a measured hazard:
~(org-read-date nil nil "junk")~ answers with *today's date, silently*, so
a naive version of ~scheduled!(nextweek)~ would mass-schedule a corpus to
today and report nothing wrong.

#+begin_example
org-agents: :AGENT_ACTION: `scheduled!' takes a date `2026-08-27',
  a date and time `2026-08-27 14:00', an offset `+7d', `today' or
  `now' -- not `nextweek'
#+end_example

~effort!(VALUE)~ writes an effort.  The argument stays a *string*, because
Org's effort values are text: =0:30=, =2d=. Nothing in this vocabulary
calls ~string-to-number~ at all.

~archive!~ archives the entry's subtree.  It is destructive and it is
*terminal*: it must be the last verb and may appear once, since it removes
the subtree a later verb would edit.  The parser refuses the ordering
rather than letting an apply pass discover it.  Its destination is computed
without archiving, so the dry run can say where the subtree is about to
go, and computed *again* immediately before archiving, with the subtree
left alone where the two disagree.

** Value keywords
:PROPERTIES:
:DESCRIPTION: today, now, empty, and how to escape them.
:END:
#+cindex: @samp{today}, value keyword
#+cindex: @samp{now}, value keyword
#+cindex: @samp{empty}, value keyword

Three bare words are interpreted rather than stored:

#+attr_texinfo: :table-type table :indic code
- today ::
  An *inactive* date stamp, as =[2026-08-20 Thu]=.
- now ::
  An *inactive* date and time stamp.
- empty ::
  The empty string.

Inactive deliberately: a value written into a property drawer must not put
the entry on the agenda.

The keywords are interpreted *in the verbs and never in the parser*, which
is not an implementation detail you can ignore.  The parser cannot know
which argument is a value, because ~set-property!~'s first argument is a
property *name* and must stay literal.  So a verb interprets its own value
arguments, and a verb that has no value argument interprets nothing.

*A quoted argument is never a keyword.* ~set-property!(REVIEWED, today)~
stores today's date; ~set-property!(REVIEWED, "today")~ stores the five
letters.  Quoting is the escape hatch, and it is the only one.

The date-taking verbs accept ~today~ and ~now~ too, and expand them
themselves rather than handing them to ~org-read-date~, so what is
scheduled is what the word says.  Their other shapes are an ISO date, an
ISO date and time, and an Org offset such as =+7d= or =++2w=.

** The dry run
:PROPERTIES:
:DESCRIPTION: org-agents-apply-actions, from plan to applied.
:END:
#+findex: org-agents-apply-actions
#+cindex: dry run
#+cindex: @samp{*Org Agents Actions*} buffer

Put point in the agent and type {{{kbd(M-x)}}} ~org-agents-apply-actions~.
Nothing is written yet.  What happens first is a *dry run*: every verb is
called in its ~plan~ phase at every match, which writes nothing and is
caught if it does, and the result is a report in =*Org Agents Actions*=,
one line per intended edit.

For the agent in [[*Writing an action]], over [[*The example corpus]]:

#+begin_example
org-agents: 6 edits at 3 entries in 1 file (1 not open before this ran).
  Nothing written yet.
…/corpus.org:7: set-property!(REVIEWED, today)  nil -> [2026-08-20 Thu]
…/corpus.org:7: tag!(+reviewed)  "" -> :reviewed:
…/corpus.org:15: set-property!(REVIEWED, today)  nil -> [2026-08-20 Thu]
…/corpus.org:15: tag!(+reviewed)  "" -> :reviewed:
…/corpus.org:29: set-property!(REVIEWED, today)  nil -> [2026-08-20 Thu]
…/corpus.org:29: tag!(+reviewed)  "" -> :reviewed:
#+end_example

Read the report before answering anything. =FILE:LINE:= comes first on
every line so ~next-error~ walks them; the arrow shows old and new; the
header counts both edits and entries, and says how many of the files were
not already open.  A row that would change nothing says so and is not
counted as an edit, and where no row would change anything the command
says that and asks nothing, because "apply 0 edits?" is not informed
consent.

Then you are asked *once*, about the whole plan:

#+begin_example
org-agents: apply 6 edits at 3 entries in 1 file (1 not open before this ran)?
#+end_example

Answer yes and the edits are applied in order, with the hooks and the
logging that would edit anything the report does not name bound off.  An
error, a =no=, a {{{kbd(C-g)}}}, or an entry that did not end up as its
line said stops at that edit: that line says what happened, and every
later line says =not attempted=. Finally the buffers that were modified
are named:

#+begin_example
org-agents: applied 6, refused 0, failed 0, skipped 0, 0 not attempted;
  modified corpus.org; nothing was saved -- see `*Org Agents Actions*'
#+end_example

*Nothing is saved.* Measured on that run: the buffer is modified and the
file on disk is byte-for-byte what it was.  Not even ~archive!~ saves; the
archive file is left modified like any other buffer, and named.

** The blast radius
:PROPERTIES:
:DESCRIPTION: The rows the report shows, and nothing else.
:END:
#+cindex: blast radius
#+vindex: org-agents-exclude

*The blast radius of a run is the rows the report shows.* That sentence is
the whole of the safety argument, and three properties of the command are
what make it true.

The match set is computed exactly as an update computes it: gated,
prefiltered, with the agent itself dropped from its own match set and
every generated alias excluded by ~org-agents-exclude~. So an agent's
action never edits the agent, and never edits an alias some other agent
wrote.

The plan pass writes nothing, and is checked rather than trusted: every
live buffer's modification tick is taken before the pass and compared
after, because a promise about one buffer is not a promise about the
corpus.

The apply pass runs with hooks and logging bound off, so nothing arrives
in the files that the report did not name.  Thirteen names are bound off:
~org-after-todo-state-change-hook~, ~org-trigger-hook~,
~org-property-changed-functions~, ~org-after-tags-change-hook~,
~org-archive-hook~, ~org-archive-finalize-hook~, ~org-log-done~,
~org-todo-log-states~, ~org-todo-state-tags-triggers~,
~org-provide-todo-statistics~, ~org-log-reschedule~,
~org-log-redeadline~ and ~org-archive-subtree-save-file-p~.  Measured,
each of these through the real command: one function on
~org-after-todo-state-change-hook~ left =:TRIGGERED: yes= on an entry the
query never matched while the report said =1 edit at 1 entry in 1 file=,
and ~org-log-done~ =time= added a =CLOSED:= line no line named.

#+cindex: hooks, and what binding them off costs
#+vindex: org-log-done
#+vindex: org-provide-todo-statistics
#+vindex: org-trigger-hook
That is what the binding buys, and the cost is worth stating just as
plainly: *~todo!~ sets the keyword and nothing else.*  No =CLOSED= stamp
is added or removed, no state note is written --- a note would /prompt/,
in the middle of a run over a corpus --- no statistics cookie in an
ancestor is refreshed, and no tag trigger fires.  ~org-trigger-hook~ is
org-edna's own mechanism, so a corpus with =org-edna-mode= on schedules no
successors and unblocks nothing on the strength of a run here.  Everything
in that list is something {{{kbd(C-c C-t)}}} on the same entry would have
done, and if you want it, that is the command to use.

~org-blocker-hook~ is deliberately *not* bound off: a blocker is your own
refusal to let an entry change, and binding it off would widen a run past
what your configuration allows.  Measured, though, ~org-todo~ fails
*silently* when a blocker blocks --- a ~message~ and a ~throw~, with no
signal --- so a blocked row would otherwise be reported =applied=.  That
is why every applied row is *verified* after the fact: the entry is read
back, and a row whose entry did not end up as its line said is reported as
what happened rather than as success.

** How much one run may edit
:PROPERTIES:
:DESCRIPTION: org-agents-action-limit.
:END:
#+vindex: org-agents-action-limit
#+cindex: limit, on an action run

~org-agents-action-limit~ is how many *entries* one run will edit.  It
defaults to 100, and that default is chosen so that a mistake is
reviewable, not for performance.

A plan over more entries than the limit is *refused* rather than
truncated, naming the count, the limit and the option:

#+begin_example
org-agents: 2 entries matched and `org-agents-action-limit' is 1, so
  nothing was planned; raise the option in init to act on more -- a
  truncated plan would apply a subset you could not predict
#+end_example

Three details of that design are deliberate.  The gate is on *entries* and
not on edits, because entries are what you reason about: an agent matches
four hundred things, not four hundred times two verbs.  The *dry run is
never capped*, whatever the limit is set to, because a cap on planning
would make the report understate what applying would do, which is the one
thing the report may not do.  And raising it is a decision taken *in init*:
the option is risky, so no file can set it for you.

There is deliberately no other bound.  An agent that legitimately stamps
three thousand entries must raise this option before it will run, and that
is the right cost: the three-thousand-entry case is exactly the alarming
one.  Since nothing is saved, the worst case of a bad run is N modified
buffers, reviewable and undoable one at a time, and this option is the
bound on N.

** Destructive verbs and batch
:PROPERTIES:
:DESCRIPTION: delete-property!, archive!, and nobody to ask.
:END:
#+cindex: destructive verbs
#+cindex: batch, and confirmation

Two verbs remove information rather than change it: ~delete-property!~ and
~archive!~. They confirm *at every entry, on every run*. There is no
remembered approval, no option that silences it, and nothing to set.

In batch, or under ~inhibit-interaction~, a confirmation is a *refusal and
not a default*.  The refusal is the prompt it would have asked, with the
reason after it, so a log says exactly which question went unanswered.
For a run holding a destructive verb the prompt names the verb:

#+begin_example
org-agents: apply 2 edits at 2 entries in 1 file, and 1 with nothing to do,
  including the destructive delete-property!?  -- refused, because there is
  no one to ask
#+end_example

and for one holding none it does not:

#+begin_example
org-agents: apply 6 edits at 3 entries in 1 file
  (1 not open before this ran)?  -- refused, because there is no one to ask
#+end_example

The check comes before ~y-or-n-p~ is ever reached, so neither of those
conditions reads standard input and neither can hang.  That matters more
than it looks: measured, in ~-batch~, ~(y-or-n-p "ok? ")~ with a =y= on
standard input returns t, and with standard input closed signals
~end-of-file~ from inside whatever called it.  A script, a CI job, or any
invocation whose standard input happened to carry text would otherwise
have answered yes on your behalf.

** The same command over a selection
:PROPERTIES:
:DESCRIPTION: A stamp, with a prefix argument.
:END:
#+cindex: stamp, over a selection
#+cindex: region, acting on

With a *prefix argument*, ~org-agents-apply-actions~ acts on the entries
the links in the *region* name rather than on the agent's whole match set.
The action text still comes from the agent's own drawer.

That is what makes a stamp fall out of this command: a stamp is this
command pointed at a selection, and the region is the selection.  Select
some of the agent's alias headings, or some rows of its table, or some
items of its list, and only those entries are planned.  The first bracket
link on each line is what is read, using the same reading that recognizes
an alias, so all three views are served by one mechanism, in order and
without repeats.

The prefix argument *is* the request, so what has to be true is that there
is a mark and that it is somewhere other than point.  An empty region, or
none at all, is refused with a message saying what the prefix argument
means.  The two protections of [[*The blast radius]] still hold: the agent's
own entry is skipped, and a generated alias is not a target.

** The trust model
:PROPERTIES:
:DESCRIPTION: In plain words.
:END:
#+cindex: trust model, action code

Stated once, in plain words, because the rest of this chapter is
consequences of it.

*A property drawer is file content, and file content is not trusted.* An
Org file may have arrived from anywhere: a colleague, a repository, a mail
attachment, an export from some other tool.  Anything a file can say to
this package must therefore be something whose worst case you are willing
to accept from a stranger.

So the vocabulary is closed and nothing in it is evaluated: the worst
sentence an =:AGENT_ACTION:= can spell is a bounded Org edit that ripgrep
can find afterwards.  Nothing runs unless you type the command.  Nothing
reaches disk unless you say yes to a report that named every edit.  The
destructive verbs ask again, every time.  The bound on how much one run may
do is raised only from init, which no file can write.

The rule underneath all of it: *file content may only tighten*. A file can
narrow what happens to your corpus; only your init and your keystrokes can
widen it.

** Writing a verb of your own
:PROPERTIES:
:DESCRIPTION: A tenth verb, in your init file.
:END:
#+cindex: action verb, defining
#+findex: org-agents-action/

A verb is resolved by *name construction plus* ~fboundp~: the token
=frobnicate!= becomes the function ~org-agents-action/frobnicate!~ if such
a function is bound, and an error naming both if it is not.  So a tenth
verb is a ~defun~ in your init file with that name.

The contract has three parts:

- The function's first argument is a *phase*, either ~plan~ or ~apply~.
  Its remaining arguments are the verb's own, and they arrive as *strings*
  in the order written.
- In the ~plan~ phase it must *write nothing* and answer a cons of the old
  value and the new, ~(OLD . NEW)~, which is what the report's =old -> new=
  is.  A plan pass that writes is caught.
- In the ~apply~ phase it makes the edit, at point, in the match's own
  buffer.

Because the resolution is by name, defining such a function is what grants
the verb to every =:AGENT_ACTION:= in your corpus.  That is the intended
design and it is also the thing to think about before writing one: a verb
is a capability you are adding to file content, so give it the same
narrowness the nine have.

** Limitations of action code
:PROPERTIES:
:DESCRIPTION: What a corpus-scope run leaves behind.
:END:
#+cindex: limitations, of action code

*Applying actions over a corpus scope leaves every file in scope visited.*
The command reaches its match set through the same collection an update
uses, which opens each candidate file with ~find-file-noselect~ and kills
nothing afterwards.  That is the footprint
[[*Limitations of the registry]] already describes, with one difference that
matters: some of those buffers are now *modified*.

Nothing is saved, which is the point, so the corpus on disk is exactly as
it was.  But a run over an =all= scope can leave a few thousand buffers
open and some tens of them modified, and *there is no corpus-wide undo to
put them back with*. Undo is per buffer, and the report in
=*Org Agents Actions*= is the list of which ones to look at.

The remedies are the ordinary ones, and there are two, used together.  Keep
~org-agents-action-limit~ low enough that a mistake is reviewable.  And
work through the report before doing anything else: ~next-error~ walks the
edits, ~undo~ in a buffer takes back the edits made in it, and
{{{kbd(M-x)}}} ~ibuffer~ with =* u= finds what is still modified.  Run an
action over an unbounded scope deliberately rather than casually, and
prefer an explicit =:AGENT_SCOPE:= list where you can name the files.

For the features org-agents does not have here at all, and why, see
[[*What was deliberately not ported, and why]]: no timer, no startup pass, no
action on an outline edit, and no inheritable action.

** Commands
:PROPERTIES:
:DESCRIPTION: The interactive commands, by name.
:END:

- Command: org-agents-update ::
  Update the agent at point, or the =org-agents= block point sits in.
  With point inside a block, that block alone is written; otherwise the
  whole agent is.  Writes =:AGENT_MATCHED:=, leaves the buffer modified
  and unsaved.  See [[*By hand]].

- Command: org-agents-update-buffer ::
  Update every agent in the current buffer, continuing past failures and
  naming each one that failed.  A dynamic block supplying its own
  =:query= is left alone.  See [[*By hand]].

- Command: org-agents-update-all ::
  Update every agent in the files =org-agents-files= names.  Files are
  left modified rather than saved.  See [[*By hand]].

- Command: org-agents-preview ::
  Read a query from the minibuffer and show what an agent with that query
  would match, over =org-agenda-files=, writing nothing.  Gated exactly
  as an agent's query is.  See [[*Looking before you write]].

- Command: org-agents-insert-dblock ::
  Insert an empty =org-agents= dynamic block at point and leave it
  unwritten.  What {{{kbd(C-c C-x x)}}} offers.  See
  [[*Inserting a block]].

- Command: org-agents-check-attributes ::
  Lint a scope against the attribute registry and report: a property name
  in use that nothing declares, a value that does not parse as its
  declared type, a value outside its declared vocabulary.  Reports into
  =*org-agents attributes*= in =compilation-mode=; edits nothing.  Reads
  its scope from the same vocabulary as =:AGENT_SCOPE:=.  See
  [[*Checking a corpus]].

- Command: org-agents-attribute-columns ::
  Return a =COLUMNS= format string over the named declared attributes,
  =%ITEM= first and a ={+}= summary cookie on an attribute declared
  =number=, as in =%ITEM %STATUS %REVIEWS{+}=.  With a prefix argument,
  also set the result as
  the =:COLUMNS:= *property* of the entry at point, which is what
  descendants inherit and what =org-agenda-columns= reads.  Refuses an
  undeclared name, and a declared name a =COLUMNS= format cannot spell.
  See [[*A corpus-wide column view]].

- Command: org-agents-list-approvals ::
  Pop =*org-agents approvals*=, a listing of every remembered approval
  and refusal with the query text its hash covers.  See
  [[*Reviewing what you approved]].

- Command: org-agents-apply-actions ::
  Print a dry run of what this agent's =:AGENT_ACTION:= would do to the
  entries its query matches, one =FILE:LINE:= line per intended edit, and
  write nothing until the whole plan is agreed to.  With a prefix
  argument, act on the entries the links in the region name instead.  The
  only thing in the package that runs an action.  See [[*The dry run]].

- Function: org-agents-allowed-values ::
  Not a command.  Written for =org-property-allowed-value-functions=: one
  argument, a property name, answering a flat list of the values the
  registry declares for it, or nil for a property it is not responsible
  for.  It is not added to that hook for you.  See
  [[*Completing declared values]].

Three more commands work only in the approvals listing:

- Command: org-agents-approvals-revoke ::
  #+kindex: d
  Forget the approval on this line, in the session and on disk.  Bound to
  {{{kbd(d)}}} in =*org-agents approvals*=.  See
  [[*Reviewing what you approved]].

- Command: org-agents-approvals-refuse ::
  #+kindex: r
  Forget the approval on this line and record the query as refused, which
  the gate consults before anything else and which no later approval
  undoes.  Bound to {{{kbd(r)}}}.  See [[*Reviewing what you approved]].

- Command: org-agents-approvals-unrefuse ::
  #+kindex: u
  Lift a refusal.  The query goes back to needing approval, not to having
  it.  Bound to {{{kbd(u)}}}.  See [[*Reviewing what you approved]].

Three key sequences reach this package, and all three are Org's:

- Key: C-c C-c ::
  Inside an =org-agents= dynamic block, runs =org-update-dblock= and so
  reaches this package's writer.

- Key: C-c C-x x ::
  =org-dynamic-block-insert-dblock=, which offers =org-agents= among the
  block types.

- Key: C-c C-x C-u ::
  =org-dblock-update=: the dynamic block at point, or with a prefix
  argument every dynamic block in the buffer.

** User options
:PROPERTIES:
:DESCRIPTION: All ten, with their defaults.
:END:

Every one of these is marked risky, which means Emacs will not set it
from a file-local variables block without your explicit confirmation.
The reason is stated in each entry.

- User Option: org-agents-files ::
  Default ~("~/org/agents.org")~.  A list of files and directories, or
  the symbol =agenda= for =org-agenda-files=.  Says which files
  =org-agents-update-all= opens *and writes*; a directory contributes the
  Org files below it, recursively.  Risky for that reason.  Not to be
  confused with =:AGENT_SCOPE:=, which says which files an agent reads.
  See [[*By hand]].

- User Option: org-agents-exclude ::
  Default ~(not (property "AGENT_MATCH"))~.  Lisp conjoined into every
  agent query and every preview, appended last so cheap predicates
  short-circuit first.  It is what keeps agents from matching each
  other's generated aliases; set it to nil to match aliases like any
  other entry.  Applied on the Emacs side only, never in the prefilter.
  This value is part of the form the gate approves, so editing it
  invalidates every remembered approval---and no refusal.  See
  [[*The structural gate]].

- User Option: org-agents-prefilter ::
  Default =auto=.  Whether an unbounded scope's files may be narrowed
  with ripgrep before org-ql opens them.  Evaluation is always org-ql's,
  against live buffers; a prefilter only chooses which *files* org-ql
  opens, so it can never change an answer.  Only =active=, =all= and a
  directory scope are ever prefiltered, because =agenda= and an explicit
  file list already name their files.

  #+attr_texinfo: :table-type table :indic code
  - auto ::
    Use ripgrep when =org-agents-rg-executable= is found and the query
    offers a conjunct to push.  Otherwise scan live, with one message
    naming the file count so that the slowness is explained rather than
    mysterious:

    #+begin_example
    org-agents: scope ‘.’ not narrowed (no pushable conjunct); scanning
    6 files live
    #+end_example

    The reason in parentheses is one of =prefiltering off=, =no pushable
    conjunct=, =ripgrep not found= or =ripgrep failed=.

  - require ::
    Refuse an unbounded scope that cannot be narrowed, rather than
    scanning it live, naming the scope and the reason:

    #+begin_example
    org-agents: scope ‘.’ cannot be narrowed (no pushable conjunct) and
    ‘org-agents-prefilter’ is ‘require’; for live evaluation set it to
    ‘auto’, or use ‘agenda’ or an explicit file list
    #+end_example

    For someone who would rather be told that an agent cannot be answered
    affordably than wait for a live walk of a whole corpus.  It refuses a
    /query/; =org-agents-check-attributes= is deliberately outside it and
    scans live instead, because a lint that declined to run would be
    failing its own contract.

  - nil ::
    Never run ripgrep; read every scope live.

  What the prefilter buys is *buffers, not regexp work*, and the
  difference between the two paths over a corpus scope is a difference of
  kind rather than of degree; the measurements are in
  [[*Which scopes get narrowed, and why]].  Risky, because it chooses
  whether a subprocess is spawned at all.  See [[*Bounding a run]].

- User Option: org-agents-rg-executable ::
  Default ="rg"=.  The program the prefilter runs, resolved with
  =executable-find=.  ripgrep 13 or later is wanted, because the
  prefilter passes =--crlf=; the flags were verified against 15.2.0 and
  no other version.  With no ripgrep found, the answer is the same as a
  failed run: the scope is scanned live, with the message that says so.
  Risky, because it names a program that will be run as a subprocess.

- User Option: org-agents-rg-timeout ::
  Default =30=.  Seconds to wait for one prefilter run, or nil for no
  bound.  A bound is needed because nothing else provides one: on an
  unresponsive filesystem a run can take arbitrarily long.  It is a
  deadline over an asynchronous process rather than a timer, because a
  timer set before a synchronous =call-process= to a hanging child never
  fires---Emacs runs no timers while blocked there.  On expiry the answer
  is the same "unavailable" a missing ripgrep gives, so the scope is
  scanned live: a spurious expiry costs a slow correct answer and never a
  wrong one.  The new cost is reentrancy, since waiting on a subprocess
  runs timers; see [[*Limitations of dynamic blocks]] and
  [[*Bounding a run]].  Risky: a file-local nil takes the bound off, and
  a file-local 0 expires every run.

- User Option: org-agents-attributes-file ::
  Default ="~/org/attributes.org"=.  The attribute registry.  Optional: a
  missing or unreadable file declares nothing and says nothing about it.
  Pure data---nothing in it is ever evaluated.  Risky because it says
  which file is read on every property completion in every Org buffer,
  and what vocabulary is then offered.  See [[*The registry file]].

- User Option: org-agents-safe-queries ::
  Default nil.  The record of queries you have approved, managed the way
  =safe-local-variable-values= is: each entry pairs the SHA-1 of a
  printed form with that form's text.  Persisted with
  =customize-save-variable=, which writes nothing unless
  =user-init-file= is set, so where your init is a tangled Org file you
  must set =custom-file= to a file of its own or every approval is
  session-only.  Risky, because it is the record the gate consults.  See
  [[*Remembered approvals]].

- User Option: org-agents-refused-queries ::
  Default nil.  The record of queries you have refused, in the same
  shape.  A refusal is consulted before anything else and no later
  approval undoes it.  Risky for the same reason.  See
  [[*Refused queries]].

- User Option: org-agents-refused-heads ::
  Default =(semantic)=.  Predicate heads the gate refuses before the safe
  list and before any remembered approval, and which
  =org-ql-ask-unsafe-queries= does not override.  Matching is by literal
  symbol, so an alias of an offending predicate must be listed too.
  Risky.  See [[*Refused heads]].

- User Option: org-agents-action-limit ::
  Default =100=, or nil for no limit.  How many *entries* one
  =org-agents-apply-actions= run will edit.  A plan over more is refused
  rather than truncated, naming the count, the limit and this option.
  The dry run is never capped.  The gate is on entries rather than edits
  because entries are what you reason about.  Risky.  See
  [[*How much one run may edit]].

** Agent properties
:PROPERTIES:
:DESCRIPTION: All ten, with their defaults and refusals.
:END:

All ten are read from the entry's *own* drawer, with no inheritance of
any kind: not from an ancestor, not from a prototype, not from a
=#+PROPERTY:= line, not from =org-global-properties=.  A property line
written with nothing after it counts as absent.  Org itself reads the
value =nil= as no value at all, so =:AGENT_VIEW: nil= is an agent with no
view and takes the default.

#+attr_texinfo: :options {Agent Property} AGENT_QUERY
#+begin_deffn
#+cindex: @samp{AGENT_QUERY}, agent property
The agent's query: one line of Lisp, an org-ql S-expression extended with
=$PROP= references.  Required, and the property is what makes an entry an
agent.  Unreadable text is refused by name; Lisp the gate does not admit
is refused as =query not approved=.  An Org property value is one line;
see [[*Putting a query in a property drawer]].
#+end_deffn

#+attr_texinfo: :options {Agent Property} AGENT_VIEW
#+begin_deffn
#+cindex: @samp{AGENT_VIEW}, agent property
=children= (the default), =list= or =table=.  Any other value is refused
rather than rendered.  See [[*Choosing a view]].
#+end_deffn

#+attr_texinfo: :options {Agent Property} AGENT_SCOPE
#+begin_deffn
#+cindex: @samp{AGENT_SCOPE}, agent property
Which files the agent reads: =agenda= (the default), =active=, =all=, a
directory relative to =org-directory=, or a =read=-able list of file
names (a value beginning with a parenthesis).  A directory that is not

#+end_deffn

#+attr_texinfo: :options {Agent Property} AGENT_SORT
#+begin_deffn
#+cindex: @samp{AGENT_SORT}, agent property
=date=, =todo=, =priority=, =reverse=, or a list of those, which org-ql

#+attr_texinfo: :options {Agent Property} AGENT_LIMIT
#+begin_deffn
#+cindex: @samp{AGENT_LIMIT}, agent property
A count, applied after the sort.  No limit when absent.  Anything that is
not a count is refused rather than read as zero.  See

#+end_deffn

#+attr_texinfo: :options {Agent Property} AGENT_COLUMNS
#+begin_deffn
#+cindex: @samp{AGENT_COLUMNS}, agent property
Whitespace-separated column names for a =table= view.  =ITEM_BY_ID= is
the link to the match, wherever in the list it appears; every other name

#+end_deffn

#+attr_texinfo: :options {Agent Property} AGENT_FORMAT
#+begin_deffn
#+cindex: @samp{AGENT_FORMAT}, agent property
Whitespace-separated property names, shown after the link in the

#+end_deffn

#+attr_texinfo: :options {Agent Property} AGENT_ACTION
#+begin_deffn
#+cindex: @samp{AGENT_ACTION}, agent property
What to do to the entries the query matched, as a declarative sentence
over the nine action verbs.  Read only by =org-agents-apply-actions=,
from this entry's own drawer, never inherited, and never evaluated.  See

#+end_deffn

#+attr_texinfo: :options {Agent Property} AGENT_MATCH
#+begin_deffn
#+cindex: @samp{AGENT_MATCH}, agent property
Written by the package on a generated alias, never by hand.  =t= marks a
heading as an alias this package may manage.  See

#+end_deffn

#+attr_texinfo: :options {Agent Property} AGENT_MATCHED
#+begin_deffn
#+cindex: @samp{AGENT_MATCHED}, agent property
Written by the package after an update: the count and an inactive
timestamp, as in =3 [2026-08-20 Thu 17:46]=.  For an agent carrying

#+end_deffn

** Registry properties
:PROPERTIES:
:DESCRIPTION: The four ATTR_ properties, by name.
:END:

Written by you, in the file ~org-agents-attributes-file~ names, in the
drawer immediately under an attribute's heading.  See
[[*The attribute registry]].

#+attr_texinfo: :options {Registry Property} ATTR_TYPE
#+begin_deffn
#+cindex: @samp{ATTR_TYPE}, registry property
The attribute's type: one of =string=, =number=, =date=, =boolean=, =set=
or =list=. Required; this property is what makes an entry a declaration.
The value is compared as text before it is interned, so a misspelling
leaves no symbol behind: the entry is named once and skipped, declaring
nothing.  A bad type costs its entry.  See [[*The six types]].
#+end_deffn

#+attr_texinfo: :options {Registry Property} ATTR_VALUES
#+begin_deffn
#+cindex: @samp{ATTR_VALUES}, registry property
The values the attribute admits, separated by whitespace.  Absent, the
attribute admits anything its type does.  A trailing =:ETC= leaves the
vocabulary open, which is Org's own spelling of that, and reaches Org
unfiltered.  For a =boolean= the property has no meaning and is ignored
with a warning, the reader synthesizing =true= and =false= instead.  See
[[*The declaration]] and [[*Completing declared values]].
#+end_deffn

#+attr_texinfo: :options {Registry Property} ATTR_DEFAULT
#+begin_deffn
#+cindex: @samp{ATTR_DEFAULT}, registry property
The attribute's default, written as text, and the last step of the
prototype resolution order.  It stays the trimmed string the file holds:
never a parsed number, never a decoded time.  A default that does not
validate against the type and the vocabulary is warned about and
discarded, which costs that field and nothing else.  See
[[*The resolution order]].
#+end_deffn

#+attr_texinfo: :options {Registry Property} ATTR_FACES
#+begin_deffn
#+cindex: @samp{ATTR_FACES}, registry property
Pipe-separated two-word groups, =VALUE FACE | VALUE FACE ...=: what
~org-agents-faces-mode~ draws a headline with when the attribute resolves
to VALUE at that entry.  Face names are read with ~intern~ and never with
~read~. A value that does not split cleanly into two-word groups yields no
faces, warned about once, which costs the faces and not the declaration.
See [[*The ATTR_FACES syntax]].
#+end_deffn

** Action verbs
:PROPERTIES:
:DESCRIPTION: The nine verbs of AGENT_ACTION, by name.
:END:

The whole vocabulary of =:AGENT_ACTION:=, applied only by
~org-agents-apply-actions~. Arguments reach a verb as strings and are
never evaluated.  A verb name ends in =!=; a value argument may be one of
the keywords in [[*Value keywords]] unless it is quoted.  See
[[*The nine verbs]].

#+attr_texinfo: :options {Action Verb} set-property! name value
#+begin_deffn
#+cindex: @samp{set-property!}, action verb
Set property NAME to VALUE at each matched entry.  Refuses any of Org's
special properties, naming the verb that does edit it; refuses any
=AGENT_= name and =PROTOTYPE=, because an action may not plant an agent, a
prototype link or action text in another file; refuses =ARCHIVE=, because
it steers where ~archive!~ puts a subtree and the dry run would name the
destination it read before that.
#+end_deffn

#+attr_texinfo: :options {Action Verb} delete-property! name
#+begin_deffn
#+cindex: @samp{delete-property!}, action verb
Delete property NAME at each matched entry.  Destructive: it confirms at
every entry on every run, no remembered approval and no option silences
it, and in batch it is refused rather than assumed.  See
[[*Destructive verbs and batch]].
#+end_deffn

#+attr_texinfo: :options {Action Verb} tag! spec
#+begin_deffn
#+cindex: @samp{tag!}, action verb
Add and remove tags, following SPEC: whitespace-separated *signed* terms
applied left to right, so =tag!(+a -b)= adds =a= and removes =b=. An
unsigned term is refused.  Deliberately not org-edna's ~tag!~, which
replaces an entry's tags.
#+end_deffn

#+attr_texinfo: :options {Action Verb} todo! state
#+begin_deffn
#+cindex: @samp{todo!}, action verb
Set the entry's TODO keyword to STATE, *and nothing else*: no =CLOSED=
stamp, no state note, no statistics cookie in an ancestor, no tag trigger,
no org-edna trigger.  See [[*The blast radius]].  STATE is checked against
~org-todo-keywords-1~ read in the match's own buffer, since those keywords
are buffer-local.  A repeating entry is refused: ~org-todo~ would shift its
stamp and write =:LAST_REPEAT:=, and the dry run cannot show either.
#+end_deffn

#+attr_texinfo: :options {Action Verb} priority! letter
#+begin_deffn
#+cindex: @samp{priority!}, action verb
Set the entry's priority to LETTER: one upper-case letter, inside
~org-priority-highest~ to ~org-priority-lowest~. Anything else is refused,
and the refusal names the range.
#+end_deffn

#+attr_texinfo: :options {Action Verb} scheduled! date
#+begin_deffn
#+cindex: @samp{scheduled!}, action verb
Schedule the entry for DATE. Accepts an ISO date =2026-08-27=, an ISO date
and time =2026-08-27 14:00=, an Org offset =+7d= or =++2w=, or the
keywords =today= and =now=, which this verb expands itself.  Anything else
is refused, because ~org-read-date~ answers unparsable text with today's
date silently.
#+end_deffn

#+attr_texinfo: :options {Action Verb} deadline! date
#+begin_deffn
#+cindex: @samp{deadline!}, action verb
Give the entry a deadline of DATE. The same shapes ~scheduled!~ takes, and
the same refusal.
#+end_deffn

#+attr_texinfo: :options {Action Verb} effort! value
#+begin_deffn
#+cindex: @samp{effort!}, action verb
Set the entry's effort to VALUE, written to ~org-effort-property~. The
argument stays a string, because Org's effort values are text: =0:30=,
=2d=.
#+end_deffn

#+attr_texinfo: :options {Action Verb} archive!
#+begin_deffn
#+cindex: @samp{archive!}, action verb
Archive the entry's subtree.  Takes no argument, and is written without
parentheses.  Destructive, so it confirms at every entry on every run; and
*terminal*, so it must be the last verb and may appear once, which the
parser enforces.  The destination is computed without archiving so the dry
run can name it, and computed again immediately before archiving, with the
subtree left alone where the two disagree.  Nothing is saved: the archive
file is left modified like any other buffer, and named.
#+end_deffn

** Functions for Lisp callers
:PROPERTIES:
:DESCRIPTION: The predicate and the resolver, for your own code.
:END:

- Function: property-resolved name &optional value ::
  #+cindex: @samp{property-resolved}, predicate
  An org-ql predicate: the prototype-aware =property=.  Matches an entry
  whose *resolved* value for NAME is non-nil, or equal to VALUE where one
  is given.  Resolution is the entry's own drawer, then its
  =:PROTOTYPE:= chain nearest hop first, then the registry's
  =:ATTR_DEFAULT:=, so a value the entry does not spell is a match here
  where =property= has none.  VALUE is compared case-sensitively.  This
  is what =$NAME^= expands to.  See
  [[*The property-resolved predicate]] and [[*The resolution order]].

- Function: org-agents-resolve-property name &optional pom ::
  The resolved value of NAME at POM (point by default) as *text*, or nil.
  Signals a =user-error= naming the hops where the prototype chain has a
  cycle.

- Function: org-agents-resolve-property-quietly name &optional pom ::
  The same, with a cycle *reported* rather than signalled.  This is what
  residual Lisp and predicates use, because a =user-error= raised inside
  org-ql's generated matcher would abort the whole update.

- Function: org-agents-attribute name ::
  The registry's declaration of NAME as a plist, or nil.  Keys are
  =:name=, =:type=, =:values=, =:default=, =:faces=, =:doc=, =:file= and
  =:line=.  See [[*The declaration]].

- Function: org-agents-attributes ::
  The declared attribute names, in registry file order.

- Function: org-agents-attribute-valid-p type value &optional values ::
  Whether VALUE is admissible for TYPE, and for VALUES where a vocabulary
  is given.  A predicate, not a diagnosis: it answers yes or no and says
  nothing about why.  See [[*The six types]].

- Function: org-dblock-write:org-agents params ::
  #+findex: org-dblock-write:org-agents
  Org's dynamic-block writer for the =list= and =table= views, and the
  name you will meet in a failure message or a backtrace rather than one
  you would call.  Org reaches it for every =org-agents= block:
  {{{kbd(C-c C-c)}}} inside one, ~org-dblock-update~,
  ~org-update-all-dblocks~, and ~org-agents-update~ on an agent whose view
  needs a block.  PARAMS are the block's own parameters; see
  [[*Block parameters]] for what they may say and
  [[*Limitations of dynamic blocks]] for what a failed render does.

* History and Acknowledgments
:PROPERTIES:
:DESCRIPTION: Whose ideas these are, what changed, and what was left out.
:END:
#+cindex: history
#+cindex: acknowledgments
#+cindex: attribution

The model this package implements is not its own.  Agents, prototypes,
action code and user-defined attributes are Eastgate Systems' Tinderbox,
where they have been in continuous use since 2002 and where its designer,
Mark Bernstein, worked out what they should mean: that a query can be a
note, that inheritance should relate two notes rather than describe where
either sits, and that a document should be able to act on itself.  What
follows is an Emacs implementation of those ideas over Org outlines,
arrived at by reading the Tinderbox manual and asking what each idea
would have to become to be honest in a plain-text corpus under version
control.  It is not affiliated with or endorsed by Eastgate Systems, and
the divergences catalogued in this chapter are this package's
responsibility and not Tinderbox's.

** Tinderbox
:PROPERTIES:
:DESCRIPTION: What it is, who makes it, and why its model is worth borrowing.
:END:
#+cindex: Tinderbox, what it is
#+cindex: Eastgate Systems, Inc.
#+cindex: Bernstein, Mark

Tinderbox is a Macintosh application for notes, published by Eastgate
Systems, Inc. and designed by Mark Bernstein.  Its own manual describes
/The Tinderbox Way/ as "a book about the design and philosophy of
Tinderbox written by Tinderbox designer Mark Bernstein"
(=tbxman920:1171=).  Its copyright notice reads "Tinderbox is © Copyright
2002-2021 by Eastgate Systems, Inc." (=tbxman920:5626=), which is the
whole of what this manual knows about how long these ideas have been in
use.

A Tinderbox document holds notes, each with a large space of named, typed
attributes; those attributes drive everything else, including what a note
looks like, what inherits from what, which notes an agent gathers, and
what an action does.  Every claim this manual makes about how Tinderbox
/behaves/ is supported by a quotation from the *v9.2* manual, cited by
line number in its plain-text edition as =tbxman920:LINE=.  The version
matters: later releases may differ, and nothing here should be read as a
description of any version but that one.  Where this manual describes
Eastgate or its product rather than the software's behaviour, and carries
no citation, the statement is the author's own and Eastgate's site is the
authority.

What makes the model worth borrowing into Emacs is not any one of its
features but the shape of the whole.  Tinderbox treats a query as a thing
you can keep, treats describing an object and filing it as different
acts, and treats a document as something that can be asked to maintain
itself.  Org has the raw material for all three --- a query language, a
property drawer, dynamic blocks --- and had assembled none of them that
way.

The debt is one of ideas only.  No Tinderbox code, data format or asset
is used, referenced or reproduced here, and nothing in this package was
derived from any of them; the correspondence was worked out from the
published manual.

** What org-agents took
:PROPERTIES:
:DESCRIPTION: The five concepts, in Tinderbox's terms, and where each one lives.
:END:
#+cindex: correspondence with Tinderbox

Five concepts were taken, and they are named here as Tinderbox names them.
[[*Agents in the Tinderbox tradition]] introduces each one with the
quotations that describe it; this section is the summary and the map.

#+attr_texinfo: :table-type table :indic asis
- Agents ::
  #+cindex: agent, as a Tinderbox concept
  "Agents are notes that search your Tinderbox document continuously for
  notes that meet the agent's criteria.  If an agent finds a note that
  satisfies its criteria, it automatically places an alias of that note
  inside the agent" (=tbxman920:1015--1016=).  Here: an ordinary Org entry
  carrying =:AGENT_QUERY:=, which is what makes it an agent, exactly as
  =$AgentQuery= is what makes a Tinderbox note one.  Its matches become
  child aliases, a list, or a table.  See [[*Views]] and [[*Updating]].
- User Attributes ::
  #+cindex: user attribute, as a Tinderbox concept
  "You can add your own user attributes to any Tinderbox document"
  (=tbxman920:1531=), each with a type, a default, a suggested vocabulary
  and a description (=tbxman920:1534--1536=, =1472--1475=).  Here: the
  registry file, one top-level entry per attribute.  See
  [[*The attribute registry]].
- Prototypes ::
  #+cindex: prototype, as a Tinderbox concept
  "[I]t shares all the properties of the prototype, except where we
  specify otherwise" (=tbxman920:1683=), by a checklist that consults the note,
  then its chain, then the default (=tbxman920:1739--1746=), and
  independently of the outline: "inheritance has nothing to do with the
  document hierarchy" (=tbxman920:1751=).  Here: =:PROTOTYPE:=, resolved
  in that order, virtually.  See [[*Prototypes]] and
  [[*The resolution order]].
- Action Code ::
  #+cindex: action code, as a Tinderbox concept
  "An action describes a change made on one or more notes"
  (=tbxman920:2795=), and an agent may carry one (=tbxman920:2543--2545=).
  Here: =:AGENT_ACTION:=, over nine verbs.  See [[*Action code]].
- Appearance from attribute values ::
  #+cindex: appearance, as a Tinderbox concept
  Tinderbox's own example is an agent holding urgent tasks, which "can
  automatically change their color in order to draw your attention"
  (=tbxman920:2792=).  Here:
  =:ATTR_FACES:= and =org-agents-faces-mode=.  See [[*Appearance]].

Two smaller borrowings deserve their own mention.  The =set= and =list=
attribute types are Tinderbox's, unordered-unique and ordered
respectively: "Lists are strings separated by semicolons"
(=tbxman920:1428=), and "Sets are best though of as a special form of
List.  Sets only hold one instance of any given value"
(=tbxman920:1439=).  The distinction is taken; the coercion Tinderbox
performs with it is not, and [[*What it changed]] says so.  And the
relative date words =today= and =now= that
the action verbs accept are Tinderbox's too: for a date value "you can
also use the terms yesterday, today, and tomorrow, and add or subtract
units of time" (=tbxman920:1398--1399=).

[[*The vocabulary map]] gives the whole correspondence as one table, with
a pointer for each row.

** What it changed
:PROPERTIES:
:DESCRIPTION: The five deliberate divergences, with the reason for each.
:END:
#+cindex: divergences from Tinderbox

Five things were changed rather than dropped.  In each case the idea
survives and the mechanism does not, and in each case the reason is the
difference in medium: a Tinderbox document is one binary file that one
application owns while it is open, and an Org corpus is thousands of
plain-text files under version control that other tools also write.

#+attr_texinfo: :table-type table :indic asis
- The query language is org-ql's, not Tinderbox's ::
  Tinderbox agent queries are written in Tinderbox's own expression
  language.  Reimplementing that over Org would have produced a second
  query engine to sit beside the one Org users already have.  So a query
  here is an org-ql S-expression, with a =$PROP= reference layer on top of
  it and no engine of its own.  See [[*The query language]].
- An update happens when you ask for one ::
  #+cindex: continuous evaluation, and its absence
#+findex: org-agents-update
#+findex: org-agents-update-buffer
#+findex: org-agents-update-all
#+findex: org-agents-mode
  Tinderbox agents "scan your document constantly" (=tbxman920:2528=) on
  a priority-driven timer.  org-agents' run on =org-agents-update=,
  =org-agents-update-buffer=, =org-agents-update-all=, or a save under
  =org-agents-mode=.  A timer that rewrote a corpus would put edits into
  files nobody was looking at, and stamps into commits nobody made.  One
  consequence is a property Tinderbox has no use for: =:AGENT_MATCHED:=
  records *when the answer was last computed*, which a continuously
  updating agent never needs to say.  Another is that an update which
  changes nothing restores the old stamps, so that a save reaches disk
  byte-identical.  See [[*Updating]].
- An alias is a heading, not a proxy ::
  #+cindex: alias, and why it is not a proxy
  In Tinderbox, "the attribute values of an alias are almost always
  identical to the values of the original note … If you make the original
  note red, the alias will be red; if you make the alias green, the
  original note will also be green" (=tbxman920:1555--1556=), and "if the
  original note is deleted, all its aliases are also deleted"
  (=tbxman920:1557=).  An org-agents alias is a heading holding a link:
  ordinary Org text, written by one render and reaped by the next.
  Editing
  it edits nothing but itself.  Org has no facility for a bidirectional
  proxy, and pretending otherwise would be worse than admitting it.  In
  exchange there is a contract Tinderbox does not need, under which an
  alias you have written under stops being the package's to delete.  See
  [[*The alias contract]].
- Attributes are declared in a file, not in a document inspector ::
  Tinderbox's user attributes are declared through a dialog and stored in
  the document.  Here they are declared in an ordinary Org file, so that
  the declarations are greppable, diffable, and reviewable in a pull
  request like anything else --- and so that a corpus with no declarations
  at all still works.  The cost is that a corpus can drift from its
  declarations, which is why there is a lint.  See [[*Checking a corpus]].
- The action language became a vocabulary ::
  Tinderbox action code is a full expression language, with assignment,
  conditionals, iteration, user-defined functions, and =runCommand= to
  reach outside the document altogether (=tbxman920:2879--2882=).
  org-agents' is nine verbs, parsed by a regexp lexer, resolved by name
  construction plus =fboundp=, receiving their arguments as strings, and
  never evaluated.  The reason is where the text comes from: a Tinderbox
  document is one file you opened deliberately, while an Org corpus is
  thousands of files, any of which may have arrived from somewhere else.
  A
  language in a property is code from a file.  See [[*Action code]].

Three smaller changes, for completeness.  =set= and =list= members are
separated by whitespace rather than semicolons, because whitespace is
what Org's own =NAME_ALL= convention uses and therefore what
=org-property-get-allowed-values= already reads; and the uniqueness a set
means is *validated* here where Tinderbox coerces it, so a repeated member
is a lint finding rather than a silently dropped duplicate.  Tinderbox's
boolean coercions --- "the number 0,
the empty string, and the date =never= are considered to be false"
(=tbxman920:1391--1392=) --- are not ported: here those are values that
fail to be booleans, and the lint says so, rather than values silently
read as false.  And a number may not carry an exponent, though Tinderbox
allows "either an integer or a floating point (decimal) number, positive
or negative" (=tbxman920:1426=), because =1e3= in an Org drawer is far
more likely to be a product code than a thousand.

** What was deliberately not ported, and why
:PROPERTIES:
:DESCRIPTION: The absences, each with its reason.
:END:
#+cindex: non-ports, deliberate
#+cindex: rule, and why there is none
#+cindex: edict, and why there is none
#+cindex: geometry attributes, and why there are none

Some of Tinderbox's mechanisms were left out on purpose, and an honest
account says which, and why, rather than leaving a reader to conclude they
were merely missed.  Nothing in this section is a plan; each entry is a
decision.  The line number after each name is where the Tinderbox v9.2
manual describes the thing that is not being ported.

#+attr_texinfo: :table-type table :indic asis
- =$Rule= (frequent timer), =tbxman920:2800= ::
  Code that edits files while you are not looking, in a corpus under
  version control, is a commit nobody authored.  Structurally impossible
  here: the action text is not on the save path at all.
- =$Edict= (startup, then roughly hourly), =tbxman920:2801=, =2907= ::
  The same objection, on a slower clock.
- =$OnAdd=, =tbxman920:2798= ::
  It fires on an edit to the outline, which is the same objection again.
- inheritable actions --- a =$Rule= from a prototype, =tbxman920:2897= ::
  Per-file trust.  If an action could arrive from a prototype, an
  ancestor, a =#+PROPERTY:= line or =org-global-properties=, then the
  code that edits your corpus when you act on file A is written in file
  B, and reading a file before trusting it means nothing.
- =$Width=, =$Height=, =$Xpos=, =$Ypos=, =tbxman920:1529=, =1562= ::
  They describe the map view.  Org has no map, so there is nothing in an
  outline for them to mean.  No spelling is even reserved.
- the alias/original live proxy, and the =original= designator, =tbxman920:1555--1557=, =1566--1567= ::
  An Org alias is a heading holding a link.  Org has no facility for a
  bidirectional proxy, and an alias has no attributes of its own to
  distinguish from the match's.
- =$PrototypeBequeathsChildren= --- materialised child inheritance, =tbxman920:1730--1733= ::
  A copy made at assignment time silently stops tracking its source,
  which is the opposite of what virtual resolution is for --- and it
  would mean writing subtrees into files on the strength of one
  property.
- =$AgentPriority=, =tbxman920:2549= ::
  It exists to schedule a timer, and there is no timer.
- the =Action= attribute type, =tbxman920:1454--1456= ::
  Its values "are evaluated as such when used".  The registry is pure
  data; a type like this is precisely what could not be ported without
  giving that up.
- the =color=, =file=, =interval= and =URL= types, =tbxman920:1375--1453= ::
  Not implemented.  =URL= in particular would be an Org link, which Org
  already has.
- the =dictionary= type, =tbxman920:3172=, =4141--4147= ::
  Not implemented.  "A dictionary collects pairs of strings separated by a
  colon", which an Org property value holding one line could carry and
  nothing in this package would understand.

Three of those deserve their reasoning spelled out, because they are
the ones a Tinderbox reader will miss most.

#+cindex: timer, and why there is none
*The timer.*  Tinderbox's =$Rule= runs "at frequent intervals"
(=tbxman920:2800=) and its =$Edict= "at startup and then at intervals of
approximately one hour" (=tbxman920:2907=).  Both are sound in a document
one application owns.  In a corpus of plain files under version control
they are not: a rule is a piece of code that edits your files while you
are not looking, and the result is a diff nobody wrote.  Here the only
thing that runs an action is =org-agents-apply-actions=, typed, and the
refusal is structural rather than disciplined --- the action text is not
part of the data the save path reads, so there is no hook it could be
reached from.  See [[*The three refusals]], and
[[*Updating]], which states the same absence from the other direction: as
a limitation of the updating feature rather than as an act of
attribution.

#+cindex: inheritable action, and why there is none
*Inheritable actions.*  A Tinderbox rule is normally inherited; the
manual's own worked example is a rule "inherited from the Task prototype"
(=tbxman920:2897=).  Here =:AGENT_ACTION:= is read from the entry's own
drawer, with no inheritance of any kind and never through the prototype
resolver.  Inheritance of behaviour and per-file trust cannot both hold:
if a master in one file could lend an action to a follower in another,
then reading a file before trusting it would tell you nothing about what
acting on it will do.

#+cindex: materialised inheritance, and why there is none
*Materialised inheritance.*  Tinderbox can copy a prototype's children
into a note that adopts it, and says of the copies:

#+begin_quote
Note that these "inherited" notes are created at the time the prototype
is assigned; adding or removing children to the prototype at some later
time will not affect notes that already use the prototype.

--- /Children of Prototypes/, =tbxman920:1730--1731=
#+end_quote

A copy made at assignment time is a copy that has stopped tracking its
source, which is the opposite of what makes virtual resolution worth
having: that one change at the master reaches every follower.  It would
also mean this package writing whole subtrees into files on the strength
of a single property.

Two absences are not divergences at all but agreements, and are recorded
here so that they are not mistaken for gaps.  Tinderbox's "inheritance
has nothing to do with the document hierarchy" (=tbxman920:1751=) is
exactly this package's position, and =$NAME*= and =$NAME^= exist as two
spellings because of it.  And Tinderbox's own non-inherited set --- its
intrinsic attributes, which "are never inherited from prototypes"
(=tbxman920:1560=) --- has a recognisably similar motive to this
package's, which excludes =AGENT_*= because behaviour does not travel,
=PROTOTYPE= itself because a declared default for it would hand the whole
corpus one master, and Org's special properties because a master's
=CATEGORY= is not yours.  The lists differ; the instinct does not.

** Org and org-ql
:PROPERTIES:
:DESCRIPTION: What this package does not reimplement, and who wrote it.
:END:
#+cindex: Org, acknowledgment of
#+cindex: org-ql, acknowledgment of
#+cindex: Dominik, Carsten
#+cindex: Porter, Adam

org-agents is a thin layer, and it is thin because of what it stands on.

Org mode is Carsten Dominik's, maintained since by Bastien Guerry, Ihor
Radchenko and many others.  Everything this package treats as given ---
the outline, the property drawer, links, the agenda, dynamic blocks,
column view, tags, TODO keywords, planning lines, and the plain-text
format that makes all of it inspectable by other tools --- is Org's.  See
[[*What Org already had]] for the parts of Tinderbox's model that were
already present, and therefore not written again here.

#+findex: property-resolved
#+findex: org-agents-preview
org-ql is Adam Porter's.  It is the evaluation engine: every match this
package reports was found by org-ql in a live buffer, and the query
language documented in [[*The query language]] is org-ql's with a
reference layer on top.  The one predicate org-agents defines,
=property-resolved=, is an =org-ql-defpred= and behaves like any other
org-ql predicate.  =org-agents-preview= hands a query to =org-ql-search=.
Where this manual is thin about what a predicate means, org-ql's own
manual is the place to look.

Two single-file modules from the author's Emacs configuration,
=org-ql-ext= and =org-ext=, are load-time dependencies; the =property-ts=
predicate that several examples here rely on comes from the first of
them.

#+cindex: org-edna, acknowledgment of
#+cindex: Dunn, Ian
org-edna is Ian Dunn's, and the shape of [[*Action code]] is its debt.  A
vocabulary of verbs whose names end in =!= to mark that they write, and a
verb resolved by constructing =PREFIX-action/NAME= and asking whether it is
~fboundp~ --- which is what makes [[*Writing a verb of your own]] possible
--- are both org-edna's design, and so is the idiom this package's lexer
uses.  What differs is what the two are for: org-edna's vocabulary is open
and its arguments are read as Lisp, because an entry's own trigger is
something you wrote; org-agents' is nine verbs, closed, taking strings,
never evaluated, applied only by an explicit command and only after a dry
run, because the text comes out of a corpus of files any of which may have
arrived from somewhere else.  The divergence that will surprise an
org-edna user is named where it arises: this ~tag!~ is additive and never
sets a tag list.  There is also one thing this package deliberately does
not extend: ~org-trigger-hook~, which is org-edna's own mechanism, is
bound off during an apply pass, so a corpus with =org-edna-mode= on gets
no triggers from a run here.  See [[*The blast radius]].

* The example corpus
:PROPERTIES:
:DESCRIPTION: The two files every example after the tutorial was run over.
:APPENDIX: t
:END:
#+cindex: corpus, the examples'
#+cindex: registry file, the examples'
#+cindex: reproducing the examples

Every worked example in this manual after [[*Tutorial]] was run over the
two files printed here.  They are given in full so that you can build
them and check any example for yourself; where an example needs anything
else --- a second file, a prototype that dangles, a registry with a
mistake in it --- the node says so and prints what it added.

=corpus.org= is the tutorial's =work.org= with more properties on its
entries, a =:OWNER:= worth querying for, and one more subtree, so that
there is something for =:URL:=, =:REVIEWS:=, =:LOCATION:=, =:TOPICS:= and
a prototype chain to be read from.  Nine entries, and the =:ID:= values
are short and readable only so that the links the examples write fit on a
printed line:

,#+title: Corpus

   :STATUS:      active
   :END:

   :END:

   :PROPERTIES:
   :ID:          ship-0-1
   :REVIEWS:     9
   :STATUS:      done
   :END:

   :PROPERTIES:

   :NEXT_REVIEW: 2026-08-21

   :END:

   :PROPERTIES:
   :ID:          collect-print
   :LOCATION:    Altadena

   :PROPERTIES:
   :ID:          tinderbox-notes

#+end_example

=attributes.org= is the registry, and it is the file

declarations and two masters:

,#+title: Attributes

,* STATUS
  :PROPERTIES:
  :ATTR_TYPE:    string
  :ATTR_VALUES:  active paused blocked done
  :ATTR_DEFAULT: active
  :ATTR_FACES:   blocked error | paused shadow | done success
  :END:
  The state of a piece of work, independent of its TODO keyword.

,* NEXT_REVIEW
  :PROPERTIES:
  :ATTR_TYPE: date
  :END:
  The day this entry should next be looked at.

,* REVIEWS
  :PROPERTIES:
  :ATTR_TYPE:    number
  :ATTR_DEFAULT: 0
  :END:
  How many times this entry has been reviewed.

,* Prototypes
,** Task
   :PROPERTIES:
   :STATUS: active
   :OWNER:  johnw
   :END:
,** Blocked Task
   :PROPERTIES:
   :PROTOTYPE: Task
   :STATUS:    blocked
   :END:
#+end_example

#+vindex: org-agents-attributes-file
#+vindex: org-agenda-files
#+vindex: org-directory
Put both in a directory, add =corpus.org= to =org-agenda-files=, point
~org-agents-attributes-file~ at =attributes.org=, and point
=org-directory= at the directory.  Agents go in a third file of their own;
the examples print the agent as they use it, so any file will do.
=corpus.org= is not itself an agent file and needs no entry in
~org-agents-files~.

Two things about this corpus are deliberate, because several examples turn
on them.  =Projects= carries no =:ID:=, which is why an example that
matches it renders a =file:= link rather than an =id:= one.  And
=Audit the prefilter= and =Collect the print= reach =:OWNER: johnw=
through the prototype chain while spelling nothing themselves, which is
what makes the difference between the two axes visible: see
[[*The two axes]] and [[*The resolution order]].

#+cindex: date, in the examples' output
Every example was run on 2026-08-20, which is what the =:AGENT_MATCHED:=
stamps and the relative-date queries in this manual are relative to.  A
run today will stamp today, and an example whose query names a window
around the present --- =(property-ts $NEXT_REVIEW :from -7 :to 30)= is the
one --- will answer about today's window and not about that one.
